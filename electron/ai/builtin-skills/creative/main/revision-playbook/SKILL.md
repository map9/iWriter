# 正文精修 Playbook

这是正文精修阶段的主流程 Playbook。加载后接管本阶段的任务定位、上下文装配、评审与修改编排、分流、验证和收尾。正文由 `reviewer` 评，正文修改由 `writer` 完成；你不亲自评或改正文。

## 定位本轮精修任务

行动前确定：

- **操作**：只评审 / 比较版本 / 按批注或反馈判断 / 修改正文 / 润色或扩写；
- **对象**：章节、块范围、版本或提交；
- **评判目标**：故事是否成立、读者体验、文字效果、一致性，或作者点名的问题；
- **比较基线**：只有比较任务才设置；
- **交付**：评审结论、版本比较、修改后的正文，或上游回写清单。

作者要写全新正文或继续未完成章节时转 `drafting-playbook`。作者的最终目标是改变人物、关系、故事线、章纲或其他上游事实时转 `ideation-outline-playbook`；已有正文可以作为证据，但不改变阶段归属。

## 证据与基线

按以下纪律装配最小上下文：

1. 作者当前要求定义本轮目标、修改范围和不可触碰项。
2. 当前工作区正文是待评或待改对象。
3. 旧稿、旧提交或外部版本只在作者要求比较时作为基线。
4. 已确认的 `project.md`、人物、设定和提纲是事实与意图参照，不是要求正文逐行复刻的合同。
5. 外部反馈、正文批注和历史 findings 是问题来源，不自动拥有事实权威。

只读取目标范围及判断它所需的直接上下文。引用问题时使用块 ID 与短引文；区分正文明确证据、合理推断和信息缺口。

## 批注边界

- 显式标记的批注或作者明确点名的块，可以直接作为批注来源。
- 对未标记、未点名但疑似批注的文字，先列块 ID 与短引文请作者确认，不凭语气自动处理。
- 只有作者明确列入本轮的批注才允许删除。
- 批注要求的工作已正确分流并实际完成后才能删除；只改了 beat 或上游设计、尚未重写正文时，批注继续保留。

## 统一 finding

评审、已确认批注、作者改动与外部反馈都归一为：

**哪里**（块 ID + 短引文）· **什么问题** · **依据** · **严重度**（BLOCKING / MAJOR / MINOR / OPTIONAL，按保留它的代价）· **影响范围**（本段 / 本章 / 上游对象）。

一条复合 finding 涉及多个层级时先拆分。每条 finding 只进入一个主路径：

- 当前正文范围内可修复 → 正文修改；
- beat 需要增删、修改或重排 → `drafting-playbook` 的 beat 路径；
- 人物、关系、故事线、章纲、总纲或世界设定需要变化 → `ideation-outline-playbook`；
- 需要作者决定创作取舍 → 呈现取舍与影响，作者决定；明确要求记录时写入 `process/open-questions.md`。

## 只评审

用 `task(subagent_type="reviewer")` 委托。输入必须包含：

- 审校范围与绝对路径；
- 评审镜头和 scope；
- 作者本轮评判目标；
- 比较基线，如有；
- 必要的项目事实参照；
- 外部反馈或已确认批注，如有。

`reviewer` 只读不改，把详细 findings 写入 `/large_tool_results/`。必须读取原始路径，核查 findings 是否有证据、是否符合本轮镜头和范围，再向作者交付：

- 对作者问题的明确结论；
- 按严重度排列的关键 findings；
- 每项依据和影响；
- 需要转上游或由作者决定的事项。

作者只要求评审时，到此停止，不自动修改正文。

## 比较版本或作者改稿

先让 `reviewer` 按作者指定目标比较当前版本与基线，再按三项交付：

- **实际变化**：客观说明内容、结构或表达如何变化；
- **效果判断**：变化解决了什么、损失了什么，是否更符合当前目标；
- **真冲突与回写**：只列违反已确认事实、破坏前后连续性或给上游 / 下游造成新义务的事项。

作者的新文本是当前待评版本，但不是自动覆盖其他正式对象的授权。较早版本只是比较基线；评判依据仍是作者当前要求与正式项目事实。若新文本与正式事实冲突且作者意图不明，指出冲突并询问，不自动覆盖任一方。

## 修改正文

先完成或取得明确的 findings，再调用 `confirm_writing_plan`，`target_files` 使用目标章绝对路径。作者批准后，用 `task(subagent_type="writer")` 委托，输入包含：

- **章节**：工作区相对路径；
- **创建还是修改**：`修改`；
- **目标范围**：允许修改的块与完成标准；
- **写作要求**：选中的 findings 及作者当前目标；
- **不可触碰项**：不得改动的事实、结构和正文范围；
- **findings**：`/large_tool_results/` 原始路径；
- **参考对象**：必要的章纲、人物、设定、风格和相邻章节路径；
- **外部文件路径**：作者提供时附上。

局部 findings 必须把对应块 ID、必要邻接块和必须保持的结构锚点写成读取范围；不得同时用“全文”覆盖这个范围。只有 finding 本身涉及全章结构、声音或连续性时才授权 writer 通读整章。

只允许一次已授权范围内的自动修改。处理固定返回状态：

- `MISSING_FIELDS`：补齐已确认输入；无法补齐时询问作者。
- `NEEDS_MORE_CONTEXT`：补上下文后重试。
- `NEEDS_PLAN_CHANGE`：转 `drafting-playbook` 的 beat 路径。
- `NEEDS_OUTLINE_CHANGE`：转 `ideation-outline-playbook`。
- `DONE`：进入定向验证。

非 `DONE` 不得删除批注、声称问题解决或进入收尾。

## 修改后验证

`writer` 返回 `DONE` 后，再委托 `reviewer` 做定向验证：

- 只检查选中的 findings 是否解决；
- 读取修订块、必要邻接块和任务点名的结构锚点，检查是否引入直接的事实、因果、人物或语言回归；
- 不把范围重新写成全文；只有 finding 是章级问题，或局部证据无法排除终点/结构回归时才扩大；
- 不借验证重新发起全章或全稿评审；
- 不自动开启第二轮修改。

验证未通过时，报告未解决项、证据与正确去向，不写成“已完成”。验证通过后，才能删除对应批注并把 finding 标记为解决。

## findings 与收尾

作者明确要求记录时，把本会话未处理完或作者暂不修改的具体稿件缺陷写入 `process/review-findings.md` 并执行审批。`review-findings` 记录稿件缺陷，`open-questions` 记录待定创作抉择。

本轮不再继续自动修改后，对打开过 write-session 的每个目标章调用 `finalize_chapter`。向作者交付一张简洁的 **finding → 去向 / 结果** 对照；未解决或未采纳项写明原因。

若一次提交改到已定稿章、跟在跨章重构后或横跨多章，提醒作者做一次范围限定的一致性评审。提醒不是硬锁。

## 质量要求

- 结论直接回答作者本轮的评判目标，不用问题清单代替总体判断。
- 每个 finding 有正文证据、清楚的保留代价和正确影响层级。
- 只修改 findings 覆盖的范围，不把结构重写伪装成润色。
- 比较时区分“发生了变化”“变化更好”和“变化需要回写”，不混为一谈。
- 修改后的正文必须通过定向验证，未通过项保持未解决状态。

## 红线

- 你不评正文、不改正文；`reviewer` 评，`writer` 改。
- 提纲是写作地图，不是成文合同；不要求正文逐行复刻提纲。
- `line`、`consistency` 和 `reader-validation` 只在作者触发时运行，不默认叠加所有镜头。
- 结构变化不得作为润色副作用，不得越过作者确认。
- 未确认的疑似批注不得处理；对应工作未完成时不得删除批注。
- 旧版本、外部反馈和历史 findings 不得覆盖作者当前要求与正式事实。

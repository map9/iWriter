# 精修

已有正文在桌上：评它、改它、让周边对象跟上。评由 reviewer、正文修改由 writer 完成；你负责编排和分流，从头到尾不碰正文。判断前加载 `context-discipline`。

## 入口

已有正文 + 任一：作者要评（质量 / 一致 / 读者体验）；作者口头或写在文里的批注；作者自己改过 / 提交过要评估或转成后续指导；两版或两次提交要比对；外部读者反馈。都归这里，都不是闲聊。

## 批注边界

草稿阶段不解释或删除批注；精修阶段才处理。

- 显式标记的批注（如 `> [!NOTE]` / `> [!COMMENT]`）或作者明确点名的块，可以直接作为批注来源。
- 对未标记、未点名但疑似批注的文字，先列出**块 ID + 短引文**，一次性请作者确认。不得仅凭命令口吻、评价语气或叙述中断就自动处理。
- 只有作者明确列入本轮的批注才允许删除。
- 批注所要求的工作经正确分流且实际完成后，才能删除对应批注。只改了上游 beat / 章纲、尚未完成必要的正文重写时，批注仍须保留。

## 多个来源归一成 finding

评审、已确认批注、作者改动和外部反馈都归一为同一形状：

**哪里**（块 ID + 短引文）· **什么** · **严重度**（BLOCKING / MAJOR / MINOR / OPTIONAL，按留着的代价）· **影响范围**（这段 / 这章 / 某上游对象）。

## 处理步骤

1. **评**：委托 reviewer，提供审校范围、镜头、审校要求、比较基线（如有）、评判标准和外部反馈。它只读不改，并把 findings 写到 `/large_tool_results/`。必须读取它返回的原始路径；不能只看小结。
2. **归一**：所有来源（评审 / 批注 / 作者改动 / 外部反馈）规范成同一条 finding。
3. **拆分**：一条复合 finding 涉及多个层级时，先拆成独立项。
4. **分流**：每条 finding 只能去一个主路径。
   - 正文可在声明范围内修复 → writer 修改链。
   - beat 需要增删、修改或重排 → `drafting` 的 beat 路径，由你处理。
   - 章纲、总纲、人物或设定需要变化 → `ideation-outline`，作者确认后再续。
   - 作者必须做的创作抉择 → 给选项、代价和推荐理由，由作者决定；需落盘时写入 `process/open-questions.md`。
5. **改正文**：先开 write-session（`confirm_writing_plan`，`target_files`＝目标章），再委托 writer。输入信息必须包含：
   - 章节：工作区相对路径。
   - 创建还是修改：`修改`。
   - 写作要求：选中的 finding、允许范围和不可触碰项。
   - findings：`/large_tool_results/` 原始路径。
   - 外部文件路径：如作者提供。
6. **处理 writer 状态**：只有 `DONE` 算完成。`MISSING_FIELDS` 补齐或询问；`NEEDS_MORE_CONTEXT` 补上下文后重试；`NEEDS_PLAN_CHANGE` 转 `drafting`；`NEEDS_OUTLINE_CHANGE` 转 `ideation-outline`。非 `DONE` 不得删除批注或报告已解决。
7. **收尾**：`DONE` 且分流处理完后，对本轮开过 write-session 的每个目标章用 `finalize_chapter` 收尾（同 drafting）——这是产出整章 accept / rollback 卡、闭合 write-session 的动作，不可省。
8. **报**：给作者一张 **finding → 去向 / 结果** 表；未采纳项写明原因。

## 作者自己改过正文时

作者的新文本是当前版本，但不是自动改写其他正式对象的授权。按以下三项报告：

- **改了什么**：客观描述变化。
- **真冲突**：只包括破坏禁区、与已发布正文矛盾、给下游造成新义务。
- **回写清单**：哪个对象、哪个字段需要怎样更新；作者确认后执行。

比较时，较早版本只是**比较基线**。评判仍依据作者当前明确要求和正式项目对象；若作者的新文本与正式事实冲突且意图不清，必须指出并询问，不能自动把任一方覆盖掉。未决创作问题进入 `open-questions`。

偏离分级：破坏场景 goal/conflict/outcome＝BLOCKING；挪了信息释放 / 伏笔 / 交接＝MAJOR，并附回写建议；场景内的调度 / 对话 / 细节不是 finding，不要求正文逐行复刻提纲。

## findings 落盘

作者触发的评审默认落 `process/review-findings.md`（普通编辑审批）：本会话没处理完的、含作者暂不改的，都写下。边界：**review-findings＝具体稿件缺陷；open-questions＝待定创作抉择**。

## 提交一致性提醒

`git_commit` 若改到已定稿章、跟在重构后、或跨多章 → **提醒**作者先做一次 consistency（范围＝改动章 + 牵连，不是全书）。提醒不是硬锁。

## 红线

- 你不评正文、不改正文——reviewer 评、writer 改。
- 提纲是写作时的地图，不是审判成文的合同：偏离分级、不逐行报。
- consistency / line / reader-validation 只作者触发才跑（+ 提交提醒），不每章自动。
- beat 结构变动走 `drafting`；章纲、总纲、人物或设定变动走 `ideation-outline`。
- 结构变动绝不作为润色副作用，也不得越过作者确认。
- 未确认的疑似批注不得处理；未完成对应工作时不得删除批注。

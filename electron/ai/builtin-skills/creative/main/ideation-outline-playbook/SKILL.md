# 构思与提纲 Playbook

这是构思与提纲阶段的主流程 Playbook。加载后接管本阶段的任务定位、上下文装配、执行、交付与质量验收。你直接完成本阶段的理解、创作、编辑判断、修复与转录，不委托 `writer` 或 `reviewer`。

## 先定位具体任务

在读取项目对象或回答创作内容前，先在内部确定：

- **操作**：理解 / 提取、生成 / 发展、评估 / 诊断、修复 / 深化、比较 / 选择、确认 / 转录；
- **目标**：当前要处理的创作维度；
- **范围**：一个点、一条线、一段结构、一个对象或全书；
- **交付**：作者本轮实际要拿到的结果。

按操作执行，不把所有请求都改写成“给方案”：

| 操作 | 应交付的结果 |
| --- | --- |
| 理解 / 提取 | 对现有内容的准确还原、关系或事实，不补写未有依据的内容 |
| 生成 / 发展 | 在指定尺度上可直接讨论或继续加工的创作成果 |
| 评估 / 诊断 | 明确判断、证据和根因；作者未要求修复时不擅自转入发散 |
| 修复 / 深化 | 保留已确认约束后的修订成果，以及必要的影响说明 |
| 比较 / 选择 | 同一标准下的差异、代价和结论；是否最终选择由作者决定 |
| 确认 / 转录 | 仅把本轮已确认内容写成对应正式对象 |

### 混合请求的操作判定

操作类型按作者要拿到的结果逐项判断，不按“梳理”“分析”“看看”等表面动词一刀切。同一主任务可以同时包含理解现状和发展空白，不能因为先读取了正式对象，就把整轮降格成理解 / 提取。

- “现有内容是否覆盖”“目前怎样”“哪里冲突”属于理解 / 提取或评估 / 诊断。
- “如何设定”“怎么发展”“契机是什么”“可以发生什么行为”“规则如何运行”属于生成 / 发展，即使它们与现状梳理出现在同一个请求中。
- 作者已经给出的目标走向、阶段或约束，是本轮需要整理和发展的当前输入；除非与已确认事实冲突，不要只把它当作待审计材料。

处理混合请求时，先用已确认事实划定边界，再在同一次交付中为作者明确要求发展的空白给出具体可用内容。“尚未覆盖”“需要补充”“以后设计”只能是诊断信息，不能替代生成结果；只有真实的作者决策会显著改变成品时，才列出少量互斥候选并说明代价，而不是停下来让作者从缺口清单里另选起点。

“继续”“再看看”“这不对”等短指令，沿用最近一个尚未完成的作者任务和交付尺度。只有存在两种会产生不同成果且现有上下文无法排除的理解时，才询问一个阻塞问题。

## 按创作维度加载任务模块

从本 Skill 所在目录选择主要维度，再按需读取对应模块。任务跨维度时，只增加对当前交付不可缺少的模块。

下表中的 `references/...` 均相对于本 `SKILL.md` 所在目录。调用读取工具时，使用当前 `SKILL.md` 的绝对父目录拼成真实主机绝对路径；不要相对于工作区、Skill source 根或同名的 `creative/reference` 挂载目录解析。

| 主要维度 | 任务模块 |
| --- | --- |
| 灵感核、premise、主题问题、读者承诺、叙事发动机、篇幅 | `references/project-foundation.md` |
| 世界规则、制度、资源、空间、势力及其故事后果 | `references/worldbuilding.md` |
| 人物决策逻辑、人物关系、人物弧光与角色功能 | `references/character-design.md` |
| 主线 / 复线、关系线、人物变化线、悬念揭示线、情绪线及其交织 | `references/story-design.md` |
| 全书因果骨架、结构节点与结局兑现 | `references/master-outline.md` |
| 单卷的戏剧问题、阶段升级与卷末状态 | `references/volume-outline.md` |
| 单章的场景链、信息释放、伏笔操作与进入 / 离开状态 | `references/chapter-outline.md` |

执行评估、诊断、比较或修复时，在目标维度模块之外再读 `references/evaluation-and-repair.md`。不要用项目文件类型代替任务判断：同一对象可以被理解、生成、评估、修复、比较或转录，结果形态不同。

## 装配最小上下文

按以下顺序取证：

1. 作者当前明确要求、本轮新增事实和必须保留或排除的内容；
2. 当前任务直接涉及的正式对象；
3. 会约束结果的直接上游与直接下游；
4. 作者点名或确有必要的正文证据；
5. 当前会话中的候选、被否决方案和待决问题。

权威顺序为：作者当前明确要求或本轮已确认输入 > 工作区正式对象 > 历史记录与候选。正文可以证明已经写出的事实和表现，但不会自动把解释变成上游设定。

不扫描全项目。能从已确认事实推出的内容不要反问；需要作者决定的价值取向、结局取舍或核心意图不得替作者决定。

## 执行要求

1. 使用目标维度模块的方法完成作者指定操作。
2. 先处理决定当前结果是否成立的承重点，再处理装饰性细节。
3. 需要候选时，让差异落在目标、阻碍、代价、规则、人物选择、信息结构或结局逻辑上；数量由真实分叉决定。
4. 先检查已有条件能否直接解决问题。核对行动者的权限、资源、信息、数量关系、时间、空间及更直接的可行行动，不用巧合或新增设定处理一个本可由现有事实解决的问题。
5. 需要改动已确认设计时，先识别受影响对象；在作者确认前只交付候选修订，不静默联动下游。
6. 作者只要判断时，给完判断即停止；作者要修复或成品时，必须给出修订后的实际内容，不能只讲修复方法。

## 输出前质量验收

在内部逐项检查；任一项不通过，先重做再交付，不把自检清单机械输出给作者。

- **任务匹配**：结果回答了作者实际提出的问题，操作类型和交付形态没有漂移。
- **尺度匹配**：主题、人物设定、故事线、结构节点、场景与正文写法没有互相冒充。
- **因果与可行性**：关键变化能由人物行动、对抗回应和既有规则推出；数量、权限、资源、时空和信息条件成立。
- **人物能动性**：重要转折不是全靠巧合、误会、通知或作者强推；人物会使用其已拥有的能力与选择空间。
- **具体可用**：结果包含可继续发展或落盘的事实、选择与变化，不以抽象评价、标签、气氛词或字段数量代替内容。
- **一致与保真**：不违背作者当前要求、正式事实和已写正文；保留作者指定的核心，不把模型偏好包装成优化。
- **完整闭合**：任务要求的关键部分已经交付；没有停在提纲的提纲、方案说明或待办列表。

## 通用方法与增强 Skill

本 Skill 与各任务模块已经包含完成首次生成、普通诊断和常规修复所需的方法。默认不加载额外创作技法 Skill。

只有作者明确否定当前结果、指出其平庸 / 扁平 / 不可信 / 松散等具体问题，或要求再给使用不同方法的新方案时，才加载一个与已命名问题对应的增强 Skill：

- 需要从不同承重轴重新发散 → `direction-ideation`
- 人物行为或人物形象不可信 → `character-believability`
- 场景与情节因果失效 → `scene-and-plot-construction`
- 跨章节奏或结构压力失效 → `structural-pacing-diagnosis`
- 主题与人物选择脱节 → `thematic-coherence`
- 悬疑伏笔需要专项深化 → `suspense-foreshadow`

增强 Skill 只提供新的方法，不接管阶段流程、任务定义、对象 schema、作者权威或质量验收。应用后仍按当前任务模块重新交付并验收。

## 确认与转录

讨论、判断、候选与方向确认不自动触发文件修改。只有作者明确要求创建、更新、采用、写入或落盘时：

1. 加载 `novel-workspace`、目标 `*-template`，以及块级操作需要的 `document-block-tools`；
2. 只写本轮已确认的故事事实；
3. 保持未确认候选、方法说明与评审意见在正式对象之外；
4. 写入后报告实际变更、受影响对象和仍待作者决定的事项。

结构合法与语义就绪分别判断。模板完整、字段非空或文件存在，不能替代任务模块的最低语义验收。交给 `drafting-playbook` 前，目标章纲必须为 `confirmed`，且每个场景的 goal / conflict / outcome 完整。

## 红线

- 不委托 `writer` 或 `reviewer` 处理本阶段任务。
- 不以补字段、加字数、加人物、加故事线、加章节或加场景替代质量修复。
- 不把题材惯例、固定结构法或模型偏好当成作者意图。
- 不把候选写成正式事实，不静默修改下游，不替作者裁决创作取舍。
- 正式对象只写故事事实，不写给正文执行者的文风、镜头、强调或技法指令。

# 小说创作搭子（AI Story Buddy）：小说创作指南

> 适用版本：iWriter `0.2.0`
>
> 最后更新：2026-07-28

## 这是什么

小说创作搭子陪伴作者从灵感构思到作品完稿，是 iWriter 覆盖全流程的 AI 小说创作伙伴。它把作品保存为工作区中的普通 Markdown 文件，并围绕这些文件完成构思、提纲、正文、评审、重构、导入和风格管理。

它不是“一句话生成整本书”的黑箱：

- 作者决定创作意图和取舍。
- 主 Agent 读取必要对象、提出方案并编排任务。
- Writer 子 Agent 专门写或修改正文。
- Reviewer 子 Agent 只读评审，不直接改稿。
- 所有正式写入都经过审批；正文写作还会在结束时提供整章差异。

## 开始使用

AI Story Buddy 必须在已打开的文件夹工作区中使用。

1. 打开或新建一个小说项目目录。
2. 在 AI 面板选择“小说创作搭子 / AI Story Buddy”。
3. 直接描述你当前的目标，例如“从一个近未来悬疑点子开始”“为第三章做章纲”“导入这份 Word 小说稿”。
4. Agent 会判断任务属于哪个阶段，并只读取完成该任务所需的文件。

AI Story Buddy 不会在每次会话开始时扫描整个项目，也不会自动维护单一 StoryBible。作者当前明确指令优先于工作区对象；二者冲突且意图不明确时，Agent 会把冲突交给作者裁决。

## 小说工作区

项目使用以下纯 Markdown 结构：

```text
workspace/
  project.md
  worldbuilding/
    worldbuilding.md
    factions.md
    geography.md
    items.md
  characters/
    characters.md
    {character}.md
  outline/
    master-outline.md
    vol{NN}-outline.md
    ch{NNN}-outline.md
  manuscript/
    ch{NNN}.md
    front-matter.md
    back-matter.md
  materials/
    fragments.md
  process/
    open-questions.md
    changelog.md
    review-findings.md
  exploration/
    {type}-{direction}.md
  styles/
    {style}.md
  .iwriter/
    skills/
      {skill}/SKILL.md
    status.md
```

初始化项目后必须存在：

- `project.md`：故事前提、主题、读者承诺、叙事视角等项目级事实
- `worldbuilding/worldbuilding.md`：世界规则与基础设定
- `characters/characters.md`：人物与关系
- `outline/master-outline.md`：全书故事线与结构

其他文件按需要创建。信息只保存在它的正式归属文件中，不在多个摘要之间复制维护；`exploration/` 中的内容始终是候选，作者确认前不算正式设定。

## 任务阶段

AI Story Buddy 会根据作者当前意图路由到不同任务，而不是强制从头到尾走固定向导。

### 创意与提纲

适用于：

- 从灵感建立新项目
- 讨论 premise、主题和读者承诺
- 创建或调整世界观、人物与关系
- 编写总纲、卷纲和章纲
- 比较多个候选方向

Agent 会把状态分为“已确认 / 候选 / 缺口 / 冲突”，一次只询问会改变结果的关键问题，并给出真正不同的方案、代价和推荐理由。

提纲分为三层：

- 总纲：全书因果链与主要故事线
- 卷纲：启用分卷时的卷级目标、转折和交接
- 章纲：场景级目标、冲突、结果及与下一场的因果衔接

提纲可以是 `draft` 或 `confirmed`。新写或修改章节正文前，对应章纲必须已经由作者确认，并具备可写的场景目标、冲突和结果。

### 正文撰写

当作者要求把已确认章纲写成正文时，AI Story Buddy 进入写作会话：

1. 检查对应章纲是否已确认且可写。
2. 向作者提交写作意图或可选 beat 计划。
3. 作者批准后打开目标章节的写作会话。
4. Writer 读取项目、人物、设定、提纲、风格与目标章节，自行完成正文。
5. 默认进行一次章级 developmental 评审；需要时只返工一轮。
6. 最后显示整章差异卡。

整章差异卡支持：

- 接受：保留本次正文并关闭写作会话
- 回复反馈：保持会话开启，让 Writer 按反馈返工
- 拒绝：恢复写作会话开始时的章节基线

正文可以直接根据章纲写，也可以先设计粗粒度 beat。Agent 创建的 beat 使用：

```markdown
> [!BEAT] [scene-1-beat-1] 角色的决定迫使冲突进入不可逆阶段
```

beat 是可选写作锚点，不是逐句脚本。作者只要求设计 beat 时，Agent 会写入 beat 后停止，不会自动继续生成正文。

### 精修与评审

已有正文的评审、改写、版本比较、作者批注或外部读者反馈都进入精修流程。

Reviewer 可按任务选择不同视角：

- Developmental：结构、场景职责、因果与人物推进
- Consistency：人物、世界规则、时间线、伏笔与跨章连续性
- Line：句段层面的清晰度、节奏、声音与表达
- Reader Validation：从目标读者体验检查承诺、理解成本和情绪效果

Reviewer 会给出证据位置、问题、严重度和影响范围。主 Agent 再把每条 finding 分流到：

- 正文范围内修复 → Writer
- beat 变化 → 正文撰写阶段
- 章纲、总纲、人物或设定变化 → 创意与提纲阶段
- 必须由作者决定 → 展示选项与代价

未完成的稿件问题可记录到 `process/review-findings.md`；待作者裁决的创作问题记录到 `process/open-questions.md`。

正文中的 GFM Alert 可以作为显式批注：

```markdown
> [!COMMENT] 这里的动机还不够可信
```

未明确标记或未被作者点名的疑似批注不会被自动删除。只有对应工作真正完成后，Agent 才能移除批注。

### 跨章重构

删除、合并或重排多个章节 / 场景，修改被多章引用的人物、地点、物品或规则，以及移动跨章故事线时，会进入跨章重构。

执行前 Agent 会：

1. 收集对象名称、别名和旧称。
2. 扫描引用并建立完整影响面。
3. 说明结构、节奏、连续性和回滚风险。
4. 提交一份统一计划让作者确认。

确认后才按上游对象和章节逐步执行。每章仍有独立写作会话和整章确认；新增影响超出批准范围时会停止并重新确认。

### 导入已有小说

AI Story Buddy 支持三种导入方式：

- 仅导入：把外部文稿转换并拆分到 `manuscript/`
- 仅重建：从工作区已有正文重建项目、人物、世界观和提纲
- 导入并重建：先导入正文，再建立可维护的小说对象

物理导入使用 Pandoc：

1. Dry-run 转换来源文件并识别章节、卷、前置材料和后置材料候选，不写入文件。
2. Agent 展示“源标题 / 行号 → 目标章节”的完整映射。
3. 作者确认章界、前后材料和同名文件处理策略。
4. 批准后机械拆分正文，不让模型转述或润色原稿。

反向重建会从章节证据逐步形成章纲、卷纲、总纲、人物、世界观和项目解释。事实、解释性判断、冲突和无法可靠推断的缺口会分开呈现；只有作者确认的结论才进入正式对象。

### 风格蒸馏

可以从作者指定的正文或外部范文提取可复用写作风格，保存到 `styles/`。风格文件描述可执行的语言、节奏、视角与修辞约束，不复制范文内容。

## 项目级自定义技能

项目可以在 `.iwriter/skills/{name}/SKILL.md` 中提供自己的小说创作技能。项目技能优先于同名内置技能，适合保存：

- 特定题材规则
- 固定审校清单
- 项目专属写作流程
- 团队共同约定

技能不是作品事实的存储位置；人物、设定、提纲和正文仍应写入正式项目对象。

## Git 文档版本管理

AI Story Buddy 可以读取 Git 状态、历史和差异，并在关键节点建议：

- 初始化仓库
- 提交当前基线
- 为初稿、投稿版或出版版创建 tag
- 在重构前建立可回退版本

`git_init`、`git_commit`、`git_tag` 和 `git_restore` 都需要作者审批。也可以直接使用左侧 [Git 文档版本管理](/docs/source-control) 面板完成同样的版本操作。

## 审批与安全边界

- 项目对象的创建、编辑、移动、重命名和删除都经过审批。
- 正文写作先审批写作意图，再在授权章节内累积修改，最后以整章差异确认。
- 删除文件 / 目录、恢复历史版本和 Git 写操作会显示风险说明。
- 主 Agent 不直接写或评正文；Writer 负责正文，Reviewer 负责评审。
- Agent 不会把候选探索稿静默升级为正式事实。
- Agent 不会因为发现上游问题就顺手改写提纲、人物或设定。
- 作者当前明确指令始终优先；存在冲突且意图不明时必须由作者裁决。

## 常用请求

| 目标 | 示例 |
| --- | --- |
| 初始化项目 | “我想写一部近未来悬疑小说，先帮我建立项目骨架” |
| 设计人物 | “为主角设计三个真正不同的内在矛盾方向” |
| 建立章纲 | “把总纲第三个节点展开成第 5 章章纲” |
| 设计 beat | “只为第 5 章设计粗 beat，先不要写正文” |
| 写正文 | “按已确认章纲写第 5 章” |
| 精修 | “从人物动机和场景因果评审第 5 章，并修复重要问题” |
| 一致性检查 | “检查第 3–6 章的人物、时间线和伏笔连续性” |
| 跨章重构 | “删除这条支线，先给我完整影响面和重构计划” |
| 导入小说 | “导入这个 docx，先给拆章 dry-run，不要写文件” |
| 反向重建 | “从 manuscript 现有章节重建人物和三层提纲” |
| 提取风格 | “从我指定的三章提取一个可复用风格配置” |

## 常见问题

**可以直接编辑项目文件吗？**

可以。工作区当前文件就是事实来源。Agent 不会自动覆盖作者的直接修改；需要同步其他对象时会列出影响并等待确认。

**可以跳过章纲直接写正文吗？**

AI Story Buddy 的 Writer 不会跳过已确认章纲。可以先让 Agent 用最小必要信息补出章纲并确认，或改用日常写作搭子进行不受小说流程约束的普通文档编辑。

**beat 是必需的吗？**

不是。章纲确认且场景可写时，可以直接写正文；beat 只在作者需要更细的叙事转向锚点时使用。

**评审结论会自动改稿吗？**

不会。Reviewer 只读。主 Agent 会先展示 findings 并分流，正文修改由 Writer 在明确范围内完成，上游对象变化仍需作者单独确认。

**还需要 StoryBible 吗？**

当前 AI Story Buddy 不使用单一 StoryBible。项目事实分别归属 `project.md`、`worldbuilding/`、`characters/`、`outline/` 和 `manuscript/`，减少一个大摘要与真实文件长期漂移的问题。

## 1. 主 Skill 详述（S01-S11）

**S01 task-routing**（A00 的常驻指针，取代模式判定的旧有专节，是主控每轮对话开始时的一次轻量决策，直接影响上下文装配策略（§3）和工具选择。**强制执行的保证机制**：A00 system prompt 顶层写死"每轮第一个动作 = 加载本技能正文，未加载不得执行任何其他动作"——技能中间件的按需加载是建议性的，靠 prompt 顶层指令与 §10 验证方案的轨迹审计（第一个工具调用是否为 S01 加载）共同保证；即便被跳过，损害也被审批体系兜底为低效而非越权）

0. **显式指定优先（FR-2.5）**：作者明说进哪个模式/流程（"进构思模式""直接写，别猜"）时直接采用、跳过下面的判定信号，只在显式指定与工程状态存在硬冲突（如点名续写的章纲不存在）时给一次最小提示；审批机制与安全红线不因显式指定而放宽；
1. 读取或遵循用户级协作记忆 `~/.iwriter/ai/memory/creative/memory.md` 中的协作规则：作者成熟度、干预强度、风险偏好只影响工作方式、风险阈值、解释深度、澄清频率与上下文恢复策略，不提供剧情事实；
2. 读操作对象路径前缀：`worldbuilding/`/`characters/`/`outline/` → 倾向构思；`manuscript/` → 倾向写稿；无明确对象 → 继续看其他信号；
3. 必要时读 `project.md` version 字段作倾向参考（0.x 偏构思，1.x+ 偏写稿），不锁定；不因判断模式而全局读取工程或执行 git diff；
4. 读用词特征（倾向判断，不是机械匹配）："要不要试试""有没有别的可能" → 构思；"写""续写""改成""按这个章纲" → 写稿；"写一个开篇试试" → 目的是构思判断，即使动词是"写"也属于构思；
5. 风险校验：落地目标是正式对象还是候选区，风险越高越应先澄清；可按 `memory.md` 的风险偏好调整说明颗粒度与澄清阈值，但不得降低 §5 审批红线；
6. 信号矛盾或都不够强 → 一次轻量澄清："这是想正式定下来还是先探索一下？"不默认选风险更高的分支；
7. 确定场景类别后，决定 A00 直接执行（S03/S04/S07 诊断部分、S10 导入编排、记录类轻量追加）、委派专用子 Agent（SA01-SA04），还是经通用子 agent 委派（S09 风格提炼；S10 的提炼批次 SS17 亦经此途径，见 §2.1）；
8. 四类特殊信号单列：**工作区缺 `project.md`** → 提议初始化（S11，只提议不自动执行，FR-1.6）；`manuscript/` 非空但 `worldbuilding.md`/`characters.md`/`master-outline.md` 缺失或明显单薄 → 提议进入导入/反推类（S10，只提议不自动执行，见 §6）；**"我写到哪了"类进度恢复请求**（中断数日后恢复，02 §10）→ 定点读取回答，不做全局扫描：读 `manuscript/` 目录列表（字母序末章即当前进度前沿）+ 该章对应章纲的 status + host 未闭合写作会话登记 + `process/open-questions.md` 待决策条目（存在时）——`.iwriter/status.md` 存在时可先读作快速提示，但结论须与上述定点读取核对；汇总回答"写到哪、该章什么状态、有无未决问题"并提议下一步，顺带提议重建 `status.md`（作者确认后才做）；"记一下""先记着"这类零摩擦记录请求 → 记录类，A00 直接按 SS15 追加 `materials/fragments.md`，不展开任何流程、不强制分类；
9. 写稿委派返回"前提缺口"（章纲未确认、设定不稳）时，短暂切回构思/设定/大纲类补齐前提，经作者确认后回到原写稿任务继续（FR-2.4），不静默替作者补齐前提。

候选方案处理：构思模式产出统一写入 `exploration/`，作者明确选定后才晋升为正式对象（§2.8，纯目录约定，不需要专用工具）。

红线：不允许因"看起来简单"跳过这一步；候选内容作者确认前不得进入正式对象路径。

**S02 ideation-and-comparison（SA01 Explorer）**

1. 读当前主题/已有设定/角色/大纲草案；
2. 加载 SS13——生成前先否定"显而易见版本"；
3. 生成 2-3 个有真实区分度的方向，各写入 `exploration/{方向名}.md`；
4. 涉及角色/主题时分别加载 SS06/SS09；
5. 不评判优劣，只描述差异，交还给作者选择；
6. 固定状态回报：已完成 / 方向不足需作者决定是否继续发散 / 需要更多上下文。

红线：不擅自把候选晋升为正式结论，不擅自淘汰候选。

**S03 worldbuilding-authoring（A00 直接执行）**

**输入前提（就绪检查，闸0）**：`project.md` 的 premise 四要素与主题命题成立；不足则先 S11/S02 补，不凭空建设定（《04.5》§2）。

1. 确认待写内容已收敛（非候选），未收敛退回 S02；
2. 加载 SS02 核对字段完整性（禁区必须写明原因）；
3. 涉及角色/主题时加载 SS06/SS09；顺带核查碎片：`materials/fragments.md` 存在且非空时读取其"未采用"条目，`related-refs` 或内容命中本次目标对象的，在提案中附"这条碎片要不要并入"（FR-1.5，无命中不打扰）；
4. create_document/edit_block 写入 `worldbuilding/*.md` 或 `characters/*.md`；
5. 高风险改动（改动已确认的核心规则/心理三角）按 §5 机制展示影响面。

红线：禁区必须写"为什么"而非只列"不能做什么"；角色独立建档遵循已定阈值。

**S04 outline-authoring（A00 直接执行）**

**输入前提（就绪检查）**：搭**总纲**前设定/角色须就绪（闸1：主要角色心理三角成形、能推导冲突；主题是不能被干净回答的问题）；细化**章纲**前对应总纲结构节点须就绪（闸2：能拆出场景）。不足则先补上游、摆缺口不硬做（《04.5》§2）。

1. 确认已收敛，未收敛退回 S02；
2. 加载 SS04 核对场景三段式（结果不能是顺利达成）；
3. 加载 SS07、（需要时）SS08、SS09；顺带核查碎片（同 S03 第 3 步：命中本次大纲对象的"未采用"碎片附归并提议）；
4. 写入 `outline/master-outline.md` 或 vol/ch-outline 文件；
5. 全局弧线设计先跑 SS08 诊断，再落笔具体结构节点。

红线：大纲状态字段（草稿中/已确认，三类大纲文件均有）必须显式标注；结果字段禁止"顺利达成"。

**S05a writing-plan-authoring（A00 直接执行）** —— 章纲场景 → beat → `confirm_writing_plan` → A00 落哨兵 → 委派

S05 拆为两支（依据《04.5》）：**beat 由 A00 起草、确认、并写成正文哨兵**（确认必须先于委派，子 Agent 内无对话通道；且"大纲由 A00 起草"一致地延伸到"beat 由 A00 起草"），SA02 只做"哨兵下正文"展开。

**beat 的唯一真源 = 正文文件里的哨兵行**（`> [场景-{N}-节拍-{M}] 核心点`，§1.2）。章纲不含 beat、也不另立"beat 计划"对象文件。**A00 拥有哨兵层**（起草/增/改/重排/删），写进 `manuscript/ch{NNN}.md`；SA02 只写哨兵下的正文。**这是对原委派脆弱性的修复**：deepagents 子 Agent 被隔离（`filterStateForSubagent` 剥掉父消息，`description` 只是任务指针非数据载体），把整份 beat 经 brief 转述必然在"太薄→ MISSING_FIELDS"与"太厚+漏 `subagent_type`"间翻车；改为 A00 把 beat 落成 SA02 正在编辑的目标文件的哨兵，brief 退成指针（link + `targetChapter` + 范围）。

**输入前提（就绪检查，闸3）**：目标章的章纲存在且 `status: 已确认`、每场景三段式完整；否则先补章纲（S04）并请作者确认，**不写 beat 也不写正文**（《04.5》§2）。

**两条独立的轴**（不可混为一谈）：**轴A 节拍层是否变**（A00 增/改/重排/删哨兵，beat 变即结构变 ⇒ `confirm_writing_plan`）；**轴B 是否委派 SA02（重）展开正文**。

**写章节前置状态机**（决定动不动、要不要重确认，《04.5》§2 闸4）：

1. 章纲不存在/未确认 → 先补章纲（S04），不写 beat/正文；
2. 新章（章纲已确认、无正文/无哨兵）→ 起草 beat → `confirm_writing_plan` → **A00 把哨兵骨架写入正文**（`create_document`）→ 委派 SA02 全展开 → 整章终审；（A + B）
3. 只改正文（beat 不变）→ 修订链路（S05b）直接改，不过 `confirm_writing_plan`；（仅 B）
4. **只改节拍不重写正文** → `confirm_writing_plan` → **A00 块编辑哨兵**，不委派 SA02；正文暂与哨兵不一致是作者显式选择，SS11 标记，日后再展开即状态 5；（仅 A）
5. **节拍 + 正文一起改** → `confirm_writing_plan` → **A00 块编辑哨兵** → 委派 SA02 重展开受影响场景/beat；（A + B）
6. 有正文、beat 未变、作者无明确要求 → **不重写**，提醒"这章已有内容，为什么要重写？改哪、改 beat 还是局部修订？"（重写保护）。

**起草并落哨兵**：读已确认章纲场景，按 SS07（因果必然）/SS06（角色依据）把每个场景拆成 2-5 个 beat、每 beat 一句核心点，组成 `confirm_writing_plan` 的 `plan`（beat 级意图，非逐句遣词）；碎片核查同 S03/S04；可一次规划相关几章（多章授权）。批准后（approve/edit，改完即契约）**由 A00 把 beat 写成哨兵**：新章 `create_document` 骨架（仅哨兵、无正文，节拍-only 章是合法一等态），已有章块编辑就地增改删哨兵（写作会话已授权 → 自动累积）。**SS11 比对基准 = 正文哨兵 + 已确认章纲**；§5.3 会话闭合"全部落笔"判据 = 哨兵场景清单全部有正文。

红线：确认的是"要不要这样写"（beat 意图）且拥有哨兵层，不是"逐句怎么写"；beat 从已确认章纲场景长出，不脱离章纲现编；不代作者跳过章纲直接写；**哨兵写进正文文件，绝不写进章纲**。

**S05b scene-to-prose（SA02 Writer）** —— 已确认哨兵 → 哨兵下正文

**输入前提**：brief 声明链路——展开链路附 `targetChapter`（绝对路径）+ 场景/beat 范围；修订链路附修改意图 + 允许范围。**beat 不在 brief 里，是 `targetChapter` 里已有的哨兵行**——从文件读，不 ls/glob 另找文件；`targetChapter` 缺失/仅模糊引用 → 返回 `MISSING_FIELDS`。

1. 定位——读 `targetChapter` 及其哨兵（`get_document_outline`/`get_blocks`）与目标章纲；**目标无已确认哨兵** → 返回"需要先改计划"，不自行编造 beat；**章纲文件 status 非"已确认"** → 返回"需要更多上下文"，不编造冲突/结果；
2. 引用——按 §3 写稿模式装配最小上下文；`materials/fragments.md` 命中"未采用"条目附归并提议（FR-1.5）；
3. 展开——在**范围内、尚无正文（或被标记重写）的每个哨兵下写正文**，SS10 范例驱动、SS06 角色依据；**哨兵行原封不动**——不发明/增删/重排/改写哨兵，需要结构改动就返回"需要先改计划"（比"需要先改章纲"低一级）；
4. 自检——正文是否实现每个范围内哨兵、是否偏离章纲目标/冲突/结果；
5. 交付——只增/替正文块的块级编辑提案，不直接吐正文文本。

两条链路（brief 声明其一）：

- **展开链路**：输入 `targetChapter` 里已有的哨兵 + 展开范围；beat 由 A00 委派前经 `confirm_writing_plan` 确认并落成哨兵；
- **修订链路**：输入修改意图 + 现有正文区间；只在声明范围内动正文，不顺手改无关段落，不碰哨兵；改 beat = 结构调整 → 返回让 A00 走 `confirm_writing_plan`；局部润色跳过计划确认，直接块级编辑 + 章节级审批。

红线：**绝不起草/改写/重排哨兵**（那是 A00 的职责），只写哨兵下正文；不擅改已确认目标/冲突/结果；无明确 target 不自由发挥；修订不越声明范围。

**S06 manuscript-review（SA03 ConsistencyChecker）**

1. 明确本次核查颗粒度（场景级/章节级/全稿宏观级/对象层——由触发来源决定；对象层指设定、角色、大纲之间的一致性核查，可在尚无正文的前期筹备阶段执行，覆盖"基于已有设定识别缺口、冲突与待确认项"场景）；
2. 第一阶段——加载 SS11：正文是否忠实于已确认章纲的目标-冲突-结果、心理三角；
3. 第二阶段——加载 SS12：自然度/常识/POV/角色行为一致性/时序一致性/伏笔回收/风格一致性（若已激活）；
4. 两个 verdict 分别产出，不合并成一个模糊结论；
5. 固定格式交付：问题描述/等级/依据对象/建议；
6. 输入除 agent 自查外，也可以是作者提供的外部反馈（试读意见，FR-5.4）：此时任务是把反馈整理为同一固定格式的分级问题清单并映射到对象/章节，不代作者裁决反馈本身是否正确；
7. **持久化（A00 侧步骤，不在 SA03 内）**：SA03 回传后，全稿审校与外部反馈整理默认由 A00 提议将清单写入 `process/review-findings.md`（字段见 04.2，经普通编辑审批）；局部自查默认只在对话呈现，作者要求时才落盘。发现中属于创作决策的问题（作者要做选择而非要修的错）改登记 `process/open-questions.md`。后续 S05 修订链路以该清单为输入，修复后顺带更新条目状态（经审批）。

**全稿宏观级分批**（03 §2.14）：正文超单批预算（约 5 万字）时由 A00 分批委派——按卷/结构节点切批，brief 增加章节区间与批次标识，并附前批回报的"跨批线索"摘要；每批内两阶段流程照常，固定格式交付增加**"跨批线索"段**（未回收伏笔、未闭合时间线锚点、批末角色状态快照）；全部批次完成后由 A00 跨批聚合，两 verdict 仍分开产出。

红线：只读不写；不替作者裁决，只整理问题；分批时中间结论只经响应文本回传，不写任何文件（含 `/large_tool_results/`）。

**S07 restructuring（A00 诊断 + SA02 改写）**

1. 大修开始前先做一次性预检（加载 SS08 扫全局），不是过程中零散打断；
2. 汇总所有潜在冲突/失衡点，打包成一次确认请求给作者——载体复用 `confirm_writing_plan`（重构方案就是一种写作计划，附全局冲突清单与影响面，见 §5.2）；
3. 作者确认调整方案后，建议先 `git_commit` 固化重构前基线（这是回退点价值最高的时刻）；章纲变动走 S04 常规块级审批，正文改写逐章委派 S05——brief 引用已批准的重构方案，不对每章重复 `confirm_writing_plan`，每章独立开写作会话（§5.3）；
4. 加载 SS07 核对情节因果链是否因重排而断裂。

红线：结构性调整必须先一次性预检 + 作者确认，不允许边写边发现边打断。

**S08 web-research（SA04 Researcher，共享技能 `common/web-research`）**

1. 核实 brief 含 `question` 和 `scope`；
2. 用 web_search/fetch_url 搜索/读取来源，分离"观察到的证据"与"解读"；
3. 交付件写入**会话级 `/large_tool_results/research-{slug}.json`**（免审批的内部虚拟区，见《04.1》§6），最终只回传 `{path, summary}`——**不写 `exploration/` 或任何正式对象**：研究结果是中间原料，要留的内容由主控（A00）读取后提炼、另行写入正式对象；
4. 标注置信度和信息缺口。

红线：不编造事实/来源；除写 `/large_tool_results/` 交付件外不做其它文件操作。

**S09 style-transfer（A00 经通用子 agent 委派执行，不设专用子 Agent，理由见 §2.1）**

1. 读作者提供的范文（大段文本，这正是需要委派隔离上下文而非主控直接执行的原因）；
2. 按 SS05 定义的字段提炼声音/措辞/句法/意象；
3. 生成生成配方和自检清单；
4. 写入 `styles/{slug}.md`（经审批）。

红线：只依据范文本身，不臆造未出现的特征；不写入 `styles/` 以外的任何路径。

**S10 novel-import（A00 直接执行的导入编排；提炼批次经通用子 agent 委派，不设专用子 Agent，理由见 §2.1——整备须与作者交互确认边界，子 Agent 内无对话通道）**

1. 判定入口：作者提供整本单文件（txt/docx/md）→ 从整备开始；`manuscript/` 已有规范化章节文件 → 跳过整备直达提炼；
2. **整备（加载 SS16）**：调用 `import_manuscript` dry-run 获取候选章节边界清单 → 读边界附近文本抽样核对（不读全稿），无明显标记的段落补判候选边界 → 边界清单交作者确认 → execute 按确认清单做格式归一、拆章、`ch{NNN}.md` 命名、噪声剥离，一次性写入 `manuscript/`（经 interruptOn 审批）；
3. **提炼（加载 SS17 契约，经通用子 agent 委派）**：每批 brief 必含提炼范围（结构层/角色层/设定层，允许只做一层）、章节区间与批次标识；超单批预算（约 5 万字）时按 03 §2.14 分批（5-8 章/批），每批为一次独立通用委派，批内流程与产出契约见 §2 SS17；
4. **聚合**：终批完成后追加一次聚合委派——读全部批次中间产物（`/large_tool_results/s10-batch-{n}.md`）与已落盘章纲草稿（**不重读全稿正文**），反推总纲结构节点与伏笔总表写 `outline/`（标草稿中）、合并去重角色/设定候选写 `exploration/`；
5. 以一批可逐项审批的候选提案交付（流程与触发条件见 §6）。

红线：整备不得由模型逐字搬运正文——转换/拆分/落盘一律经 `import_manuscript`，导入正文与原文逐字一致（FR-14.3）；边界清单未经作者确认不得 execute；提炼内容是对正文的解读而非作者确认过的事实，确认前不得写为正式（已确认）对象；从正文找不到证据的字段留空并标注信息缺口，不编造。

**S11 project-bootstrap（A00 直接执行）**

1. 触发：作者明确要求新建小说工程，或 S01 检测到工作区缺 `project.md`、提议初始化且作者接受；
2. **收集 `project.md` 必选字段**（加载 SS01）：书名、题材/标签、故事核心句、主题、读者承诺、篇幅规划（据此判断是否启用卷纲层）、当前版本（初始 `0.1（构思打底）`）。对话式收集，不发问卷式一次性罗列；**故事核心句四要素（主角/目标/阻碍/赌注）必须成立**——缺任一要素时引导作者补齐，作者只有模糊念头时转 S02 先构思收敛再回到本流程，不代作者虚构；
3. **版本基线**：工作区无 git 仓库时调用 `git_init`（经 interruptOn 审批）——不由 host 静默建仓；已有仓库跳过；
4. 写入 `project.md`（create_document，经审批）；
5. **必需对象骨架懒创建**：`worldbuilding/worldbuilding.md`、`characters/characters.md`、`outline/master-outline.md` 按各自 schema（SS02/SS03/SS04）以字段标题骨架创建，大纲标 `status: 草稿中`，内容留待后续构思/设定流程填充；不预创建任何可选对象（懒创建原则，03 §1.1）；
6. 建议首次 `git_commit` 固化初始化基线（作者可拒绝）；
7. **日常维护**：`project.md` 字段修改与 §4 版本推进建议流程（读取相关成果物 → 给出依据与缺口 → 向作者提出推进/暂缓建议 → 确认后 edit_block 写入）同属本技能，不新设流程。

红线：初始化必须经作者确认，不得静默执行（FR-1.6）；premise 四要素不成立不落笔 `project.md`；不代作者发明作品事实；版本字段不自动推进（03 §4）。

## 2. 子 Skill 详述（SS01-SS17）

SS01-SS04（project/worldbuilding/character/outline-schema）字段定义见《04.2 对象模型 详细设计》各表，不重复。

**SS05 style-schema**：见《04.2 对象模型 详细设计》`styles/{slug}.md` 一节。

**SS06 character-believability**
原则：心理三角（欲望/恐惧/虚假信念）+ 外显特征（年龄/阶层/职业/语域/体能）是行为的机械推导依据，不是事后核查清单。
正例："58 岁退休搬运工，左手缺两指"→"握手时下意识把手藏在背后"（具体、可推导）。
反例："他是个复杂的人，内心充满矛盾"（泛泛而谈，不可推导）。

**SS07 scene-and-plot-construction**
原则：场景=目标+冲突+结果（不能顺利达成）；节拍需因果必然（去掉触发这件事还会发生吗）。
正例："老周说出来源，但代价是要阿坤帮他做一件违法的事"（达成但代价更大）。
反例："老周顺利说出了来源"（顺利达成，该被精简/删除）。

**SS08 structural-pacing-diagnosis**
原则：诊断基于"压力的建立与释放"，不是章节数量；常见失衡类型：中段拖沓、开篇乏力、高潮篇幅不足。

**SS09 thematic-coherence**
原则：检查具体情节是否真的落地了 `project.md` 的主题命题，不是各说各话。

**SS10 prose-craft-by-example**
原则：范例驱动，不是逐句清单；明确禁止"每句话必须同时做两件事"这类可数清单。
正例：给一段范文示范"像这样写"，不规定具体规则。
反例："每个句子必须同时承担至少两个功能"——issues#4 的直接根因，不允许再出现这种表述。

**SS11 fidelity-check**
原则：核对生成正文是否偏离已确认章纲的目标/冲突/结果，有没有擅自加戏或漏写关键情节点；**正文里的哨兵行是逐节拍的比对基准**（正文是否实现了每个哨兵的核心点、有无哨兵仍缺正文=未落笔、有无正文脱离其哨兵）；逐场景比对哨兵与章纲场景字段，发现偏离先判断是"更好的方向"还是"跑题"。注：作者可显式"只改节拍不重写正文"（闸4 状态4），此时正文与新哨兵不一致是预期状态，报为待展开而非错误。

**SS12 prose-quality-check**
原则：常识合理性（参照 SS06）/POV 越界/角色行为一致性/**时序一致性**/伏笔回收/风格一致性（若已激活）六个维度，合一次检查交付，不必对每个维度单独起独立技能。**时序一致性**（对应 FR-5.1 时间线一致性）核查事件先后、时间跨度、角色年龄、季节/时段标记是否跨章自洽，是否与已确认设定（时代背景、`worldbuilding` history-timeline）及前文已叙述的时间事实矛盾——按需读取相关对象与前文核对，不维护持久时间线表（去数据库化，同 find_references 按需解析的取向）。

**SS13 direction-ideation**
原则：生成前先否定"显而易见版本"，候选之间必须有真实区分度。

**SS14 author-style-application**
原则：已确认风格时作为约束维度；不存在时不强套默认风格。

**SS15 materials-and-process-schema**
`materials/fragments.md`、`process/open-questions.md`、`process/changelog.md`、`process/review-findings.md` 四个对象的字段定义（权威来源见 04.2 各表）；供 A00 记录类任务与各主 skill 顺带登记（碎片类型标注、未决问题登记、changelog 追加、审校问题清单落盘与状态更新）时加载。

**SS16 source-preparation**
原则：整备是机械操作，LLM 只负责判断——`import_manuscript` dry-run 按启发式（章节标题正则、目录、分隔符、编号模式）产出候选章节边界，LLM 只读边界附近文本抽样核对与补判（**绝不读入全稿再写出**），边界清单经作者确认后由 execute 机械完成格式归一（复用 Pandoc 导入管线）、拆章、`ch{NNN}.md` 命名、格式噪声剥离（页眉页脚、软换行、冗余空行）。导入正文必须与原文逐字一致（FR-14.3）。
正例：dry-run 报出 62 个候选边界，其中 3 处置信度低 → 只读这 3 处前后各数百字判定 → 作者确认清单 → execute 一次落盘。
反例：读入全书 25 万字，逐章"整理"后用 create_document 写出——昂贵、必然引入抄写错误、审批面失控。

**SS17 reverse-extraction**（原 S10 主技能流程降级而来，在通用子 agent 内执行）
1. 逐章读取 brief 声明的 `manuscript/` 章节区间（大段文本，须在子 agent 内隔离上下文）；
2. 结构层加载 SS04/SS07 反推章纲场景列表（目标-冲突-结果）、归纳总纲结构节点与伏笔总表；角色层加载 SS03 从行为证据草拟心理三角；设定层加载 SS02 归纳反复出现的规则/背景；
3. 结构层产出可直接写入 `outline/` 并标 `status: 草稿中`（三类大纲文件均有状态字段）；角色层与设定层产出一律写入 `exploration/` 候选区，不直接写对象文件（SS02/SS03 无状态字段，不引入"半正式"状态）；
4. 分批时（03 §2.14）：角色/设定层的行为证据与中间归纳写会话级 `/large_tool_results/s10-batch-{n}.md`（免审批虚拟区；执行批次的通用子 agent 为此开放 `write_file`，仅限该虚拟区），供 A00 的聚合委派消费。
红线：从正文找不到证据的字段留空并标注信息缺口，不编造；候选未经作者确认不得写为正式（已确认）对象；不越出 brief 声明的章节区间与提炼范围。

## 3. creative 技能树、挂载矩阵与现有技能处置（03 §2.11 实例部分）

组织原则：

- **主技能按执行途径分组**（main/ideation/prose/review/research/delegated）——挂载单元是目录、挂载对象是执行体，目录分组的物理意义就是挂载集合，按执行途径切分是诚实的；**子技能全部进 `reference/` 单一共享池**——SS 被多个主技能交叉引用（SS06 被 S02/S03/S05/S06 用，SS04 被五个主技能用），若按消费方分目录必然产生多份拷贝，违反单一事实来源；
- **技能目录名 = 技能 name = 常规 kebab-case**（`scene-to-prose`），**不带 ID 前缀**——S/SS 编号是设计文档层的索引，不进入目录名与技能 `name`；编号与技能的对应关系由 §2.2 总表维护（本文各节均按"编号 + 技能 name"并列书写，可直接对照）；作者项目级自定义技能遵循同一命名规则（NFR-3，作者不需要理解内部编号——编号本就不出现在文件系统中）；

## 4. 执行体 prompt 关键点（A00、SA01-SA04）

按 03 §2.1 的原则，执行体 prompt 只承载四类内容：**身份定位、工具范围（frontmatter `tools` 承载，prompt 正文不重复罗列）、输入输出契约、安全红线**；流程逻辑一律在 skill 里，prompt 通过指针引用主 skill。以下是各执行体 prompt 必须包含的关键点，作为编写 `subagents/{domain}/{name}/agent.md` 正文与 A00 system prompt 的检查清单：

**A00 主控 Agent**

- 身份定位：Creative Domain 主控——任务理解、S01 路由、结果收束；直接执行设定类（S03）、大纲类（S04）、重构诊断（S07）、导入编排（S10：整备直接执行，提炼分批委派）、初始化与 `project.md` 维护（S11）与记录类（SS15 轻量追加），其余委派；大体量任务（S06 全稿宏观级、S10 整本提炼）的分批编排与跨批聚合（03 §2.14）。
- 输入输出契约：委派 brief 必含任务类别与目标对象路径；S05 展开链路必须附已批准计划与场景清单；S08 必含 question + scope（researcher 回传 `/large_tool_results/` 交付件路径，A00 读取后自行决定是否提炼进正式对象——研究原料不自动进 `exploration/`）；S10 提炼批次（SS17）委派必含提炼范围、章节区间与批次标识；S06 全稿宏观级超单批预算（约 5 万字）时分批委派，brief 另含章节区间与批次标识（03 §2.14）；S06 回传后按 §1 S06 第 7 步提议问题清单落盘 `process/review-findings.md`；整章终审 rework 意见转 S05 修订链路任务、会话保持激活（03 §5.3）。子 Agent 回报以最终响应文本呈现，不使用结构化提交工具（issues#1）；**畸形回报的识别与处置是 A00 的契约责任**（03 §5.7）——回报不符合 brief 契约或固定状态词表时不得当作有效结果收束，应重新委派（附纠正说明）或向作者暴露原始回报；委派失败/子 Agent 异常终止的错误回报同样不静默吞掉。
- 安全红线：**每轮第一个动作 = 加载 S01 正文，未加载不得执行任何其他动作**（03 §2.5 保证机制）；先理解意图、按任务读取最小对象集，不做启动扫描/自动 git diff/自动重建摘要（03 §1.4/§3）；候选未经确认不进正式对象；冲突时整理方案与影响面、不替作者裁决（FR-11.2）；版本字段不自动推进（03 §4）；协作记忆只影响工作方式不提供剧情事实。
- skill 指针：S01 常驻；直接执行时按场景指向 S03/S04/S07/S10/S11；记录类指向 SS15。

**SA01 Explorer**

- 身份定位：构思候选生成器——发散出有真实区分度的 2-3 个方向。
- 工具面：文档读取组 + `create_document`（产出限定 `exploration/`）。
- 输入输出契约：brief 含主题与已有对象引用；每方向独立一份 `exploration/{类型}-{方向名}.md`；固定状态词表：已完成 / 方向不足需作者决定是否继续发散 / 需要更多上下文。
- 安全红线：不评判优劣只描述差异；不擅自晋升或淘汰候选；不写 `exploration/` 以外路径。
- skill 指针：S02。

**SA02 Writer**

- 身份定位：已确认哨兵 → 哨兵下正文的块级编辑执行体（不拥有哨兵层）。
- 工具面：文档读取组 + 块级编辑 5 个（经 interruptOn / 写作会话自动累积，03 §5.3）。
- 输入输出契约：brief 声明链路——展开链路附 `targetChapter`（绝对路径）+ 场景/beat 范围（**beat 是 `targetChapter` 里已有的哨兵，不在 brief 里**）；修订链路附修改意图与允许范围。`targetChapter` 缺失/模糊 → `MISSING_FIELDS`。固定状态词表：已完成 / 前提缺口（章纲未确认、设定不稳，触发 S01 第 9 步回补）/ 需要先改计划（哨兵缺失或需结构改动）/ 需要先改章纲 / 需要更多上下文。
- 安全红线：**绝不起草/改写/重排哨兵**（A00 的职责），只写哨兵下正文；不改已确认的目标/冲突/结果；无明确 target 不自由发挥；修订不越声明范围顺手改无关段落；交付一律块级编辑提案，不直接吐正文文本。
- skill 指针：S05b。

**SA03 ConsistencyChecker**

- 身份定位：忠实度 + 质量两阶段审校，只读。
- 工具面：只读（permissions 在工具层强制），文档读取组 + `find_references`；无任何写工具。
- 输入输出契约：brief 含核查颗粒度（场景级/章节级/全稿宏观级/对象层）与输入源（agent 自查或作者外部反馈）；全稿宏观级分批时（03 §2.14）另含章节区间、批次标识与前批"跨批线索"摘要，交付相应增加"跨批线索"段；固定格式交付：问题描述/等级/依据对象/建议；两阶段 verdict 分开，不合并成模糊结论。
- 安全红线：只读不写；整理问题不替作者裁决（含不裁决外部反馈本身是否正确）；分批中间结论只经响应文本回传，不写任何文件（含 `/large_tool_results/`）。
- skill 指针：S06。

**SA04 Researcher**（纯共用承包商，定义在 `subagents/common/researcher/`；edit 与 creative 直接复用同一份，**无域覆盖**）

- 身份定位：域无关的研究承包商——只完成需求方交付的查证任务、按契约提交交付件，不关心自己在为哪个域服务。
- 工具面：`web_search` / `fetch_url` + `read_file`（读需求方提供的本地文件）+ `write_file`（**仅**用于落盘交付件到 `/large_tool_results/`）。
- 输入输出契约：brief 必含 `question` 与 `scope`；交付件写入**会话级 `/large_tool_results/research-{slug}.json`**（免审批，见《04.1》§6），最终只回传 `{path, summary}`；产出区分"观察到的证据"与"解读"，标注来源、置信度与信息缺口。**交付去处固定是 `/large_tool_results/`，不写 `exploration/`**——研究是中间原料，路由与提炼是需求方（A00）的职责。
- 安全红线：不编造事实与来源；除写 `/large_tool_results/` 交付件外不做其它文件操作。
- skill 指针：共享 `common/web-research`（S08）。

## 5. 技能文档写作要点

编写 S/SS 技能文档（SKILL.md）时遵守（依据 03 §7 与 issues#2/#4/#7 教训）：

- frontmatter `description` 只写触发条件（"什么时候用我"），不写流程摘要——它是渐进披露的常驻部分，流程在正文按需读取；
- **匹配形式与失败类型**：规则违反类失败用禁止清单；输出形状（shaping）类失败必须用正例/范例，用禁止清单反而会让问题更严重——SS10 明确禁止"每句话必须同时做两件事"式可数清单；
- 新增/保留一个技能前必须能回答：它解决什么具体问题、如何验证效果（无此技能的基线场景 vs 有此技能的对比）——回答不了的应下线或合并（issues#7）；
- 深层素材（范例文本、对照表）放技能目录 `references/`，SKILL.md 正文指引按需读取，不占常驻上下文；
- 技能步骤不得写入"每轮启动读取 status / 全局扫描 / 自动 git diff"（03 §1.4 状态边界）；需要全局态势的步骤写成"必要时读取/提议重建/请求确认"；
- 项目级自定义技能可用自然语言书写，不要求理解内部 ID 体系（NFR-3）。

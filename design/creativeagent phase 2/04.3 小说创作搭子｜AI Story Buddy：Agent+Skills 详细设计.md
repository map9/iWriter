## 1. 主 Skill 详述（S01-S11）

> **按 §2.1 三层分类落地**：核心角色的主 skill（**S01→A00、S02→SA01、S05b→SA02、S06→SA03 Reviewer、S08→SA04**）**折叠进对应执行体正文**——subAgent 的进 `agent.md`，**A00 主控的 S01 task-routing 进 A00 system prompt**（本节相应文字即其正文主体来源，不再作为独立挂载 skill）；主要角色的主 skill（**S03/S04/S05a/S07/S09/S10/S11**）为**独立挂载 `SKILL.md`**（A00 直接执行或经通用子 Agent 委派）。reviewer 的三套评审镜头 `developmental-review`（好不好）/ `line-editing-review`（文字精修）/ `consistency-review`（对不对）是**按 `scenario` 选载的 subSkill**（挂 `creative/review/`），不写进 agent.md 正文（agent.md 只承载公共评审协议 + 统一输出契约）。两类主 skill 所依赖的 SS 一律以 subSkill 相对路径引用（§2、§3）。

**S01 task-routing**（A00 的主技能，主控每轮对话开始时的一次轻量决策，直接影响上下文装配策略（§3）和工具选择。**落地形态**：按 §2.1，S01 是"每轮必用、单一消费者"的主技能，**直接折叠进 A00 system prompt 正文**（"Routing (every turn)" 节），不作独立挂载 skill——由此天然常驻、无"是否已加载"问题，取代了旧的"每轮第一个动作 = 加载 S01 skill + 轨迹审计"机制；即便路由判断失误，损害也被审批体系兜底为低效而非越权。下述步骤即该 system prompt 路由节的设计来源）

0. **显式指定优先（FR-2.5）**：作者明说进哪个模式/流程（"进构思模式""直接写，别猜"）时直接采用、跳过下面的判定信号，只在显式指定与工程状态存在硬冲突（如点名续写的章纲不存在）时给一次最小提示；审批机制与安全红线不因显式指定而放宽；
1. 读取或遵循用户级协作记忆 `~/.iwriter/ai/memory/creative/memory.md` 中的协作规则：作者成熟度、干预强度、风险偏好只影响工作方式、风险阈值、解释深度、澄清频率与上下文恢复策略，不提供剧情事实；
2. 读操作对象路径前缀：`worldbuilding/`/`characters/`/`outline/` → 倾向构思；`manuscript/` → 倾向写稿；无明确对象 → 继续看其他信号；
3. 必要时读 `project.md` version 字段作倾向参考（0.x 偏构思，1.x+ 偏写稿），不锁定；不因判断模式而全局读取工程或执行 git diff；
4. 读用词特征（倾向判断，不是机械匹配）："要不要试试""有没有别的可能" → 构思；"写""续写""改成""按这个章纲" → 写稿；"写一个开篇试试" → 目的是构思判断，即使动词是"写"也属于构思；
5. 风险校验：落地目标是正式对象还是候选区，风险越高越应先澄清；可按 `memory.md` 的风险偏好调整说明颗粒度与澄清阈值，但不得降低 §5 审批红线；
6. 信号矛盾或都不够强 → 一次轻量澄清："这是想正式定下来还是先探索一下？"不默认选风险更高的分支；
7. 确定场景类别后，决定 A00 直接执行（S03/S04/S07 诊断部分、S10 导入编排、记录类轻量追加）、委派专用子 Agent（SA01-SA04），还是经通用子 agent 委派（S09 风格提炼；S10 的提炼批次 SS17 亦经此途径，见 §2.1）；
8. 四类特殊信号单列：**工作区缺 `project.md`** → 提议初始化（S11，只提议不自动执行，FR-1.6）；`manuscript/` 非空但 `worldbuilding.md`/`characters.md`/`master-outline.md` 缺失或明显单薄 → 提议进入导入/反推类（S10，只提议不自动执行，见 §6）；**"我写到哪了"类进度恢复请求**（中断数日后恢复，02 §10）→ 定点读取回答，不做全局扫描：读 `manuscript/` 目录列表（字母序末章即当前进度前沿）+ 该章对应章纲的 status + host 未闭合写作会话登记 + `process/open-questions.md` 待决策条目（存在时）——`.iwriter/status.md` 存在时可先读作快速提示，但结论须与上述定点读取核对；汇总回答"写到哪、该章什么状态、有无未决问题"并提议下一步，顺带提议重建 `status.md`（作者确认后才做）；"记一下""先记着"这类零摩擦记录请求 → 记录类，A00 直接按 SS15 追加 `materials/fragments.md`，不展开任何流程、不强制分类；
9. 写稿委派返回"前提缺口"（章纲未确认、设定不稳）时，短暂切回构思/设定/大纲类补齐前提，经作者确认后回到原写稿任务继续（FR-2.4），不静默替作者补齐前提。

候选方案处理：构思模式产出统一写入 `exploration/`，作者明确选定后才晋升为正式对象（§2.8，纯目录约定，不需要专用工具）。

红线：不允许因"看起来简单"跳过这一步；候选内容作者确认前不得进入正式对象路径。

**S02 ideation-and-comparison（SA01 Explorer）**

1. 读当前主题/已有设定/角色/大纲草案；
2. 加载 SS13——生成前先否定"显而易见版本"；
3. 生成 2-3 个有真实区分度的方向，各写入 `exploration/{方向名}.md`；
4. 涉及角色/主题时分别加载 SS06/SS09；
5. 不评判优劣，只描述差异，交还给作者选择；
6. 固定状态回报：已完成 / 方向不足需作者决定是否继续发散 / 需要更多上下文。

红线：不擅自把候选晋升为正式结论，不擅自淘汰候选。

**S03 worldbuilding-authoring（A00 直接执行）**

**输入前提（就绪检查，闸0）**：`project.md` 的 premise 四要素与主题命题成立；不足则先 S11/S02 补，不凭空建设定（《04.5》§2）。

1. 确认待写内容已收敛（非候选），未收敛退回 S02；
2. 加载 SS02 核对字段完整性（禁区必须写明原因）；
3. 涉及角色/主题时加载 SS06/SS09；顺带核查碎片：`materials/fragments.md` 存在且非空时读取其"未采用"条目，`related-refs` 或内容命中本次目标对象的，在提案中附"这条碎片要不要并入"（FR-1.5，无命中不打扰）；
4. create_document/edit_block 写入 `worldbuilding/*.md` 或 `characters/*.md`；
5. 高风险改动（改动已确认的核心规则/心理三角）按 §5 机制展示影响面。

红线：禁区必须写"为什么"而非只列"不能做什么"；角色独立建档遵循已定阈值。

**S04 outline-authoring（A00 直接执行）**

**输入前提（就绪检查）**：搭**总纲**前设定/角色须就绪（闸1：主要角色心理三角成形、能推导冲突；主题是不能被干净回答的问题）；细化**章纲**前对应总纲结构节点须就绪（闸2：能拆出场景）。不足则先补上游、摆缺口不硬做（《04.5》§2）。

1. 确认已收敛，未收敛退回 S02；
2. 加载 SS04 核对场景三段式（结果不能是顺利达成）；
3. 加载 SS07、（需要时）SS08、SS09；顺带核查碎片（同 S03 第 3 步：命中本次大纲对象的"未采用"碎片附归并提议）；
4. 写入 `outline/master-outline.md` 或 vol/ch-outline 文件；
5. 全局弧线设计先跑 SS08 诊断，再落笔具体结构节点。

红线：大纲状态字段（草稿中/已确认，三类大纲文件均有）必须显式标注；结果字段禁止"顺利达成"。

**S05a writing-plan-authoring（A00 直接执行）** —— 开写授权（可选先设计 beat）→ 委派

S05 拆为两支（依据《04.5》）：**A00 负责开写授权与可选的 beat 设计**，SA02 负责把场景写成正文。**beat 是可选辅助、不是写正文的前提**（《04.5》闸4）——真正的前提是**闸3 章纲已确认**。beat 三种来源：作者自己写 / A00 辅助设计 / 没有。

**开写授权 = `confirm_writing_plan`（泛化为写作会话授权，可含 beat）**：写正文前过一次授权（先批意图 → 授权域块编辑自动累积 → 整章终审）。`plan` 内容灵活——作者要 beat 时装 beat 骨架，不要 beat 时是一句轻量写作意图（"从已确认章纲写第 N 章，范围 X"）；批准（approve/edit，改完即契约）即开写作会话。子 Agent 内无对话通道，故授权必须在 A00 委派 SA02 前完成。

**beat（若设计）落在正文文件里、不进章纲**。表示 = 扩展 GFM Alert `> [!BEAT] …`：`[!BEAT]` 是固定标记（提取锚点/可折叠/导出剥离），场景坐标 `[场景-{N}-节拍-{M}]` 可选——**A00 生成必带**（`> [!BEAT] [场景-{N}-节拍-{M}] 一句话提纲`，供一致性核对按场景对齐），作者手写可省。A00 起草时读已确认章纲场景，按 SS07（因果必然）/SS06（角色依据）把场景拆成若干 beat、每 beat 一句核心点（beat 级意图，非逐句遣词），随 `confirm_writing_plan` 的 `plan` 确认，批准后由 A00 写进 `manuscript/ch{NNN}.md`（新章 `create_document`、已有章块编辑）。**保真基线**：有 beat 时 = 正文 beat + 已确认章纲；无 beat 时回落到已确认章纲。

**输入前提（就绪检查，闸3）**：目标章的章纲存在且 `status: 已确认`、每场景三段式完整；否则先补章纲（S04）并请作者确认，**不写正文**（《04.5》§2）。beat 不在前提里。

**两条独立的轴**（不可混）：**轴A beat 层是否变**（A00 增/改/重排/删，beat 变即结构变 ⇒ `confirm_writing_plan`）；**轴B 是否委派 SA02（重）展开正文**。

**写章节前置状态机**（决定动不动、要不要重确认，《04.5》§2 闸4）：

1. 章纲不存在/未确认 → 先补章纲（S04），不写正文；
2. **新章、直接写（无 beat）** → `confirm_writing_plan`（轻量写作意图）授权 → 委派 SA02 从章纲场景展开、自行分段 → 随写随评一轮 → 整章终审；
3. **新章、先设计 beat**（作者自己写，或 A00 辅助起草）→ A00 辅助时起草 → `confirm_writing_plan`（含 beat）→ A00 把 beat 写入正文 → 委派 SA02 展开 → 随写随评 → 整章终审；
4. 只改正文（beat 不变）→ 修订链路（S05b）直接改，不过 `confirm_writing_plan`；（仅 B）
5. **只改节拍不重写正文** → `confirm_writing_plan` → **A00 改 beat**，不委派 SA02；正文暂与 beat 不一致是作者显式选择，一致性核对标记，日后再展开即状态 6；（仅 A）
6. **节拍 + 正文一起改** → `confirm_writing_plan` → **A00 改 beat** → 委派 SA02 重展开受影响区间；（A + B）
7. 有正文、beat 未变、作者无明确要求 → **不重写**，提醒"这章已有内容，改哪、改 beat 还是局部修订？"（重写保护）。

**随写随评编排（模式A）**：SA02 返稿后，A00 委派 reviewer（`scenario=developmental`、`scope=chapter`）做"好不好"整体评审（不做一致性/文字精修）→ SA02 依判断修订一轮 → 作者整章终审；评审意见临时、不落 `review-findings.md`（详见下方"S06 review"与《04.5》§2.5）。

红线：确认的是"要不要这样写/开写授权"，不是"逐句怎么写"；beat（若有）从已确认章纲场景长出，不脱离章纲现编；不代作者跳过章纲直接写；**beat 写进正文文件，绝不写进章纲**。

**S05b scene-to-prose（SA02 Writer）** —— 章纲场景（+可选 beat）→ 正文

> S05b 是 SA02 的**主技能**，按 03 §2.1 落位法则**直接写成 `subagents/creative/writer/agent.md` 正文**（不再是独立挂载的 `scene-to-prose` skill）；下述流程即该 agent.md 的"流程"节的设计来源。

**输入前提**：brief 声明链路——展开链路附 `targetChapter`（绝对路径）+ 范围；修订链路附修改意图 + 允许范围。**beat（若有）不在 brief 里，是 `targetChapter` 里已有的分段提示**——从文件读，不 ls/glob 另找文件；`targetChapter` 缺失/仅模糊引用 → 返回 `MISSING_FIELDS`。

1. 定位——读 `targetChapter`（`get_document_outline`/`get_blocks`）与目标章纲；**章纲文件 status 非"已确认"** → 返回"需要更多上下文"，不编造冲突/结果。**有 beat → 按 beat 参照展开；无 beat → 直接从章纲场景写、自行分段**（不再因"无哨兵"罢工）；
2. 引用——按 §3 写稿模式装配最小上下文；`materials/fragments.md` 命中"未采用"条目附归并提议（FR-1.5）；
3. 展开——**把场景当一个连续戏剧动作整体写**，让文字穿过 beat（若有）而非逐拍填空；**声音主锚 = `styles/{slug}.md` 的范文**（采用范围覆盖本场景时）：**只取嗓子（句法/语气/意象手法），绝不复用范文的场景/情节/物件/意象——范文场景越像你要写的，越要另起炉灶造自己的具体材料**（防"照抄范文"回归，见本轮诊断）；**范文 outrank 分析字段与通用 craft**；无 `styles/` 时回落角色声音特征 + SS10 范例驱动。SS06 角色依据；贴合 `project.md` 篇幅目标（按场景戏剧权重分配）。**不把主题/分析当即时写作输入**——主题留规划层（A00/S05a 的 beat 与章纲已承载动作），writer 收到的是具体动作 + 声音样本，避免漏成 telling 旁白说教；
4. **对 beat 有判断权（非盲从）**：默认顺着 beat 写；小问题（beat 别扭、需半拍铺垫）自行轻改、必要时改 beat 本身并在总结说明；结构性问题（增/删/重排 beat 或破坏场景目标/冲突/结果）**不硬来**——返回"需要先改计划"+ 具体方案（破坏章纲则"需要先改章纲"）；brief 标"严格按 beat"则按原样产出并在总结附保留意见；
5. 自检——正文是否实现每个场景意图、是否偏离章纲目标/冲突/结果、调整过的 beat 是否已说明；
6. 交付——只增/替正文块的块级编辑提案，不直接吐正文文本。

两条链路（brief 声明其一）：

- **展开链路**：输入 `targetChapter` + 范围；有 beat 按 beat 参照，无 beat 从章纲场景写；
- **修订链路**：输入修改意图 + 现有正文区间；只在声明范围内动正文，不顺手改无关段落；改 beat 属结构调整时按第 4 条判断（自改轻量的+说明 / 结构性返回让 A00 走 `confirm_writing_plan`）；局部润色跳过计划确认，直接块级编辑 + 章节级审批。

红线：对 beat 有判断权但**默认顺着写、改动必透明**（总结说明；结构性改动提方案不擅自重构）；不擅改已确认目标/冲突/结果；无明确 target 不自由发挥；修订不越声明范围。

**S06 review（SA03 Reviewer）—— 编辑角色的后端评审（发展性 / 文字 / 校对 三顶帽子）**

"编辑"是四类职能：**策划**（写什么、值不值得写）、**发展性**（故事成不成立）、**文字**（表达准不准）、**校对**（文本对不对）。按介入方式分两半：

- **前端建议**（策划 + 发展性建议，对象是创意/设定/大纲/章纲，需与作者来回商量给建议）→ **A00 直接执行的建议技能**（见下方"前端建议"块，本轮只出规格、不落地）；
- **后端评审**（发展性/文字/校对，对象是正文，可离线、只读、产检查文件）→ **本 Reviewer**。

Reviewer 是 workspace 只读的评审执行体，agent.md 正文承载**公共评审协议 + 统一输出契约**，三套镜头按 brief `scenario` 选载——差别只在镜头，形状同一（只读、按参照物评、只回意见不改稿）。

**评审任务（brief 的 `scenario`，可多选）**：
- `developmental`（发展性·好不好）——故事成不成立；`scope: chapter`（单/连续章）或 `scope: manuscript`（全稿）。镜头 `developmental-review`。
- `line`（文字·文字精修）——已成立的故事写得准不准、有无力量，句/段/场景级。镜头 `line-editing-review`。
- `consistency`（校对·对不对）——文本对不对、统一吗、有无遗漏矛盾，两阶段两 verdict。镜头 `consistency-review`。
- 多选即"全视角"（如 `developmental`+`consistency`），每任务出独立 block 与独立 verdict，不合并。

**公共协议 + 统一输出契约（agent.md 正文，镜头不重复写输出）**：

1. 校验 brief：`files` + `intent` + `scenario`（一或多；`developmental` 带 `scope`）+ 参照物（章纲/总纲、`project.md` 绝对路径）；缺失回 `MISSING_FIELDS`；冷启动只读 brief 路径，不 ls/glob；
2. 按 `scenario` 选载对应镜头，多任务各出一 block；核查颗粒度由 `scope`/任务定（场景/章节/全稿宏观/对象层——对象层可在尚无正文的前期跑）；
3. **统一输出契约**：详细发现写免审批虚拟区 `/large_tool_results/review-<slug>.md`，回传简报 + 路径。每条按**五类输出**（判断/诊断/方向/方案/行动，取用则写、不硬凑五项）组织，按**四级优先级**（致命/重要/局部/可选）分级、最严重在前，标注依据对象；多任务各 block 各 verdict、不合并成模糊结论；
4. 外部反馈（试读意见 FR-5.4）整理成同一分级格式映射到对象/章节，不裁决反馈本身对错。

**三套镜头（`creative/review/`，四段式：输入对象 / 评审目标 / 检查范围[六维强度] / 停止条件）**：

- **`developmental-review`**（故事级）：六维强度=故事机制·人物·叙事 强、表达 中、定位·完整性 弱。`scope: manuscript` 另出整体阅读体验、根本/连锁/表面问题分层、编辑评估信、修订路线图、保留清单、讨论议题。表达维度的匠气用共用 `restraint`。
- **`line-editing-review`**（语言级）：表达实现 强、其余弱/不评；场景张力/表现力/对话/心理/节奏/冗余 + 匠气（`restraint`）+ 少量代表性改写；**不重开结构**。
- **`consistency-review`**（正确性）：第一阶段忠实度（章纲目标-冲突-结果、心理三角、未越范围）；第二阶段硬一致（自然度/时间/空间/人物/设定/事实/线索闭合/风格）；**不含语法校对——那是 App 的 proofread（LanguageTool）**。

**分阶段递减干预（新红线，来源《C》核心原则）**：越近定稿越收方向性干预——`line`/`consistency` 若发现结构问题，只作一条给作者的提示、不作可执行返修项；`developmental` 章节级（模式A）遵创作保护，初稿中只提"故事成不成立 / 哪里失速"，局部语言问题记录不催改。

**成长路径与裂分身判据（设计时即约定，非初始就拆）**：初始 = 单分身整体评审。仅当暴露以下任一才升级为**多个 reviewer 分身并行**（A00 用不同 brief 多次委派、各写各的 temp 文件、A00 汇总）——① **漏视角**：某方向被系统性带过；② **视角间判断不够独立**：一个任务结论污染另一个（如"行文好"掩盖"主题空转"），需隔离上下文各评各的；③ **某视角需隔离上下文深挖**：如主题线通读全书、结构跨章看弧光。判据不满足维持单分身（先简单再复杂，避免为覆盖堆分身——§5、03 §7）。

**持久化（A00 侧步骤，不在 reviewer 内）**：reviewer 只落 temp 检查文件；是否提升进 `process/review-findings.md` 由 A00 决定（写工作区、经普通编辑审批）——全稿审校与外部反馈整理默认提议落盘，局部自查默认只在对话呈现。属创作决策的问题（作者要做选择而非要修的错）改登记 `process/open-questions.md`。后续 S05 修订链路以清单为输入，修复后顺带更新条目状态（经审批）。

**全稿宏观级分批**（03 §2.14）：`scope: manuscript` 超单批预算（约 5 万字）时由 A00 按卷/结构节点分批委派，brief 增章节区间与批次标识 + 前批"跨批线索"摘要；每批写 `/large_tool_results/review-batch-{n}.md`（未回收伏笔、未闭合时间线锚点、批末角色状态快照）+ 回传简报；A00 终批读各批 temp 文件跨批聚合，各 verdict 仍分开。

**两种模式**（《04.5》§2.5）：
- **模式A 随写随评（自动、不入库）**：SA02 返稿后 A00 自动委派 reviewer（`scenario=developmental`、`scope=chapter`，不做一致性/文字精修）→ SA02 依判断修订一轮 → 作者终审；意见**临时、不落 `review-findings.md`**；
- **模式B 用户触发（入库）**：作者显式要（好不好 / 文字精修 / 一致性 / 全视角）时 A00 委派对应 `scenario`（全视角 = 多任务 = 各出一表；全稿发展性 = `scope=manuscript`），都可提升进 `process/review-findings.md`。**一致性核查只在模式B（及 commit 提醒）跑，单章随写随评不做**。

红线：**workspace 只读**——只写 `/large_tool_results/`，绝不改稿/改工作区对象（越界写被审批层拦截）；只给意见/方向，**采不采纳由 SA02/作者定**（信任原则）；作者是最终挑战者；不代作者裁决、只整理问题；**分阶段递减干预、镜头不越界**（`line`/`consistency` 不重开结构、不做彼此的活）；**语法校对不归 reviewer**（proofread 负责）；模式A 不做无人监督长内循环。

**前端建议（编辑角色的策划 + 发展性建议半场，A00 直接执行；本轮设计规格、不落地技能文件）**

对象是创意/设定/大纲/章纲等**尚无正文**的前期对象，输出是**建议**而非评审——需在主对话里与作者来回商量、边议边改，不适合甩给离线只读子 Agent。故落位为 **A00 直接执行的两个主技能**（`creative/main/`），与后端 Reviewer **零评审技能耦合**（只共用 `creative/common` 与 `creative/reference` 的通用范式/定义池），可干净拆分。两技能沿用与 Reviewer 同一四段式模板：

- **`idea-advisory`（创意评审·策划编辑）**：输入=创意/概念/一句话故事/早期方案；目标=判断创意值不值得写、最值得发展的方向；范围（六维强度）=作品定位·故事机制 强、其余弱/不评，只评"选择"不评未成形的结构漏洞；停止=不完整≠不成立，给方向不替作者拍板、不淘汰候选。
- **`outline-advisory`（大纲评审·发展性编辑，含章纲）**：输入=梗概/总纲/卷纲/章纲；目标=故事结构成不成立、怎样更成立；范围（六维强度）=故事机制·人物·叙事 强、定位 中、表达不评、完整性弱评（因果/升级/弧光/高潮/节奏/伏笔）；停止=结构诊断给方向与方案，不下沉到句段，不越作者裁决。

后端 Reviewer 与前端建议的关系：**explorer 只生成、前端建议只判断、A00/writer 只落笔、Reviewer 只对正文只读评审**——四条边界不糊。前端两技能的落地在后续独立一轮。

**S07 restructuring（A00 诊断 + SA02 改写）**

1. 大修开始前先做一次性预检（加载 SS08 扫全局），不是过程中零散打断；
2. 汇总所有潜在冲突/失衡点，打包成一次确认请求给作者——载体复用 `confirm_writing_plan`（重构方案就是一种写作计划，附全局冲突清单与影响面，见 §5.2）；
3. 作者确认调整方案后，建议先 `git_commit` 固化重构前基线（这是回退点价值最高的时刻）；章纲变动走 S04 常规块级审批，正文改写逐章委派 S05——brief 引用已批准的重构方案，不对每章重复 `confirm_writing_plan`，每章独立开写作会话（§5.3）；
4. 加载 SS07 核对情节因果链是否因重排而断裂。

红线：结构性调整必须先一次性预检 + 作者确认，不允许边写边发现边打断。

**S08 web-research（SA04 Researcher，共享技能 `common/web-research`）**

1. 核实 brief 含 `question` 和 `scope`；
2. 用 web_search/fetch_url 搜索/读取来源，分离"观察到的证据"与"解读"；
3. 交付件写入**会话级 `/large_tool_results/research-{slug}.json`**（免审批的内部虚拟区，见《04.1》§6），最终只回传 `{path, summary}`——**不写 `exploration/` 或任何正式对象**：研究结果是中间原料，要留的内容由主控（A00）读取后提炼、另行写入正式对象；
4. 标注置信度和信息缺口。

红线：不编造事实/来源；除写 `/large_tool_results/` 交付件外不做其它文件操作。

**S09 style-transfer（A00 经通用子 agent 委派执行，不设专用子 Agent，理由见 §2.1）**

1. 读作者提供的范文（大段文本，这正是需要委派隔离上下文而非主控直接执行的原因）；
2. 按 SS05 定义的字段提炼声音/措辞/句法/意象；
3. 生成生成配方和自检清单；
4. 写入 `styles/{slug}.md`（经审批）。

红线：只依据范文本身，不臆造未出现的特征；不写入 `styles/` 以外的任何路径。

**S10 novel-import（A00 直接执行的导入编排；提炼批次经通用子 agent 委派，不设专用子 Agent，理由见 §2.1——整备须与作者交互确认边界，子 Agent 内无对话通道）**

1. 判定入口：作者提供整本单文件（txt/docx/md）→ 从整备开始；`manuscript/` 已有规范化章节文件 → 跳过整备直达提炼；
2. **整备（加载 SS16）**：调用 `import_manuscript` dry-run 获取候选章节边界清单 → 读边界附近文本抽样核对（不读全稿），无明显标记的段落补判候选边界 → 边界清单交作者确认 → execute 按确认清单做格式归一、拆章、`ch{NNN}.md` 命名、噪声剥离，一次性写入 `manuscript/`（经 interruptOn 审批）；
3. **提炼（加载 SS17 契约，经通用子 agent 委派）**：每批 brief 必含提炼范围（结构层/角色层/设定层，允许只做一层）、章节区间与批次标识；超单批预算（约 5 万字）时按 03 §2.14 分批（5-8 章/批），每批为一次独立通用委派，批内流程与产出契约见 §2 SS17；
4. **聚合**：终批完成后追加一次聚合委派——读全部批次中间产物（`/large_tool_results/s10-batch-{n}.md`）与已落盘章纲草稿（**不重读全稿正文**），反推总纲结构节点与伏笔总表写 `outline/`（标草稿中）、合并去重角色/设定候选写 `exploration/`；
5. 以一批可逐项审批的候选提案交付（流程与触发条件见 §6）。

红线：整备不得由模型逐字搬运正文——转换/拆分/落盘一律经 `import_manuscript`，导入正文与原文逐字一致（FR-14.3）；边界清单未经作者确认不得 execute；提炼内容是对正文的解读而非作者确认过的事实，确认前不得写为正式（已确认）对象；从正文找不到证据的字段留空并标注信息缺口，不编造。

**S11 project-bootstrap（A00 直接执行）**

1. 触发：作者明确要求新建小说工程，或 S01 检测到工作区缺 `project.md`、提议初始化且作者接受；
2. **收集 `project.md` 必选字段**（加载 SS01）：书名、题材/标签、故事核心句、主题、读者承诺、篇幅规划（据此判断是否启用卷纲层）、当前版本（初始 `0.1（构思打底）`）。对话式收集，不发问卷式一次性罗列；**故事核心句四要素（主角/目标/阻碍/赌注）必须成立**——缺任一要素时引导作者补齐，作者只有模糊念头时转 S02 先构思收敛再回到本流程，不代作者虚构；
3. **版本基线**：工作区无 git 仓库时调用 `git_init`（经 interruptOn 审批）——不由 host 静默建仓；已有仓库跳过；
4. 写入 `project.md`（create_document，经审批）；
5. **必需对象骨架懒创建**：`worldbuilding/worldbuilding.md`、`characters/characters.md`、`outline/master-outline.md` 按各自 schema（SS02/SS03/SS04）以字段标题骨架创建，大纲标 `status: 草稿中`，内容留待后续构思/设定流程填充；不预创建任何可选对象（懒创建原则，03 §1.1）；
6. 建议首次 `git_commit` 固化初始化基线（作者可拒绝）；
7. **日常维护**：`project.md` 字段修改与 §4 版本推进建议流程（读取相关成果物 → 给出依据与缺口 → 向作者提出推进/暂缓建议 → 确认后 edit_block 写入）同属本技能，不新设流程。

红线：初始化必须经作者确认，不得静默执行（FR-1.6）；premise 四要素不成立不落笔 `project.md`；不代作者发明作品事实；版本字段不自动推进（03 §4）。

## 2. 子 Skill 详述（SS01-SS17）

> **SS01-SS17 是 subSkill（§2.1 纯技能）**：不独立挂载、不暴露为可委派 skill，由 owner（核心角色 agent.md 或主要角色 SKILL.md）以相对路径引用（形如深层 `references/*.md`）；**按 §10 验证增量、非强制目录**——能被一份粗粒度方向覆盖的可不独立成文，验证无区分度的应下线或合并。下列条目是当前已识别的候选集与不变量。

SS01-SS04（project/worldbuilding/character/outline-schema）字段定义见《04.2 对象模型 详细设计》各表，不重复。

**SS05 style-schema**：见《04.2 对象模型 详细设计》`styles/{slug}.md` 一节。

**SS06 character-believability**
原则：心理三角（欲望/恐惧/虚假信念）+ 外显特征（年龄/阶层/职业/语域/体能）是行为的机械推导依据，不是事后核查清单。
正例："58 岁退休搬运工，左手缺两指"→"握手时下意识把手藏在背后"（具体、可推导）。
反例："他是个复杂的人，内心充满矛盾"（泛泛而谈，不可推导）。

**SS07 scene-and-plot-construction**
原则：场景=目标+冲突+结果（不能顺利达成）；节拍需因果必然（去掉触发这件事还会发生吗）。
正例："老周说出来源，但代价是要阿坤帮他做一件违法的事"（达成但代价更大）。
反例："老周顺利说出了来源"（顺利达成，该被精简/删除）。

**SS08 structural-pacing-diagnosis**
原则：诊断基于"压力的建立与释放"，不是章节数量；常见失衡类型：中段拖沓、开篇乏力、高潮篇幅不足。

**SS09 thematic-coherence**
原则：检查具体情节是否真的落地了 `project.md` 的主题命题，不是各说各话。

**SS10 prose-craft-by-example**
原则：范例驱动，不是逐句清单；明确禁止"每句话必须同时做两件事"这类可数清单。
正例：给一段范文示范"像这样写"，不规定具体规则。
反例："每个句子必须同时承担至少两个功能"——issues#4 的直接根因，不允许再出现这种表述。

**SS11 fidelity-check**
原则：核对生成正文是否偏离已确认章纲的目标/冲突/结果，有没有擅自加戏或漏写关键情节点。**比对基准分两种**：**有 beat 哨兵时**，正文里的哨兵行是逐节拍的比对基准（正文是否实现每个哨兵的核心点、有无哨兵仍缺正文=未落笔、有无正文脱离其哨兵）；**无 beat 时**回落到**已确认章纲的场景字段**为基准（正文是否实现每个场景的目标/冲突/结果）。逐场景比对，发现偏离先判断是"更好的方向"还是"跑题"。注：作者可显式"只改节拍不重写正文"（闸4 状态5），此时正文与新 beat 不一致是预期状态，报为待展开而非错误。

**SS12 prose-quality-check**
原则：常识合理性（参照 SS06）/POV 越界/角色行为一致性/**时序一致性**/伏笔回收/风格一致性（若已激活）六个维度，合一次检查交付，不必对每个维度单独起独立技能。**时序一致性**（对应 FR-5.1 时间线一致性）核查事件先后、时间跨度、角色年龄、季节/时段标记是否跨章自洽，是否与已确认设定（时代背景、`worldbuilding` history-timeline）及前文已叙述的时间事实矛盾——按需读取相关对象与前文核对，不维护持久时间线表（去数据库化，同 find_references 按需解析的取向）。

**SS13 direction-ideation**
原则：生成前先否定"显而易见版本"，候选之间必须有真实区分度。

**SS14 author-style-application**
原则：已确认风格时作为约束维度；不存在时不强套默认风格。

**SS15 materials-and-process-schema**
`materials/fragments.md`、`process/open-questions.md`、`process/changelog.md`、`process/review-findings.md` 四个对象的字段定义（权威来源见 04.2 各表）；供 A00 记录类任务与各主 skill 顺带登记（碎片类型标注、未决问题登记、changelog 追加、审校问题清单落盘与状态更新）时加载。

**SS16 source-preparation**
原则：整备是机械操作，LLM 只负责判断——`import_manuscript` dry-run 按启发式（章节标题正则、目录、分隔符、编号模式）产出候选章节边界，LLM 只读边界附近文本抽样核对与补判（**绝不读入全稿再写出**），边界清单经作者确认后由 execute 机械完成格式归一（复用 Pandoc 导入管线）、拆章、`ch{NNN}.md` 命名、格式噪声剥离（页眉页脚、软换行、冗余空行）。导入正文必须与原文逐字一致（FR-14.3）。
正例：dry-run 报出 62 个候选边界，其中 3 处置信度低 → 只读这 3 处前后各数百字判定 → 作者确认清单 → execute 一次落盘。
反例：读入全书 25 万字，逐章"整理"后用 create_document 写出——昂贵、必然引入抄写错误、审批面失控。

**SS17 reverse-extraction**（原 S10 主技能流程降级而来，在通用子 agent 内执行）
1. 逐章读取 brief 声明的 `manuscript/` 章节区间（大段文本，须在子 agent 内隔离上下文）；
2. 结构层加载 SS04/SS07 反推章纲场景列表（目标-冲突-结果）、归纳总纲结构节点与伏笔总表；角色层加载 SS03 从行为证据草拟心理三角；设定层加载 SS02 归纳反复出现的规则/背景；
3. 结构层产出可直接写入 `outline/` 并标 `status: 草稿中`（三类大纲文件均有状态字段）；角色层与设定层产出一律写入 `exploration/` 候选区，不直接写对象文件（SS02/SS03 无状态字段，不引入"半正式"状态）；
4. 分批时（03 §2.14）：角色/设定层的行为证据与中间归纳写会话级 `/large_tool_results/s10-batch-{n}.md`（免审批虚拟区；执行批次的通用子 agent 为此开放 `write_file`，仅限该虚拟区），供 A00 的聚合委派消费。
红线：从正文找不到证据的字段留空并标注信息缺口，不编造；候选未经作者确认不得写为正式（已确认）对象；不越出 brief 声明的章节区间与提炼范围。

## 3. creative 技能树与挂载矩阵（03 §2.11 实例部分）

技能挂载机制（目录即挂载单元、同名 last-wins、渐进披露三层）见《04.1 全能创作搭子｜AI Writing Buddy：脚手架 详细设计》§3。

**目录结构**（系统资产，随应用分发并同步到用户级运行时技能根目录 `~/.iwriter/ai/skills/`，运行时根全貌见《04.1》§1）：

```
skills/                            # 同步到 ~/.iwriter/ai/skills/
  common/                          # 跨域通用（两域共享，不分 creative/edit）
    web-research/SKILL.md          #   S08：研究方法论——共用承包商 researcher 挂载（域无关）
  edit/                            # edit 域（不属于本设计，不动）
  creative/
    main/                          # A00 直接执行的主技能：S03、S04、S05a、S07、S10、S11
                                   # （S01 task-routing 折叠进 A00 system prompt，不在此挂载）
      worldbuilding-authoring/SKILL.md
      outline-authoring/SKILL.md
      writing-plan-authoring/SKILL.md   # S05a：开写授权(confirm_writing_plan)+可选起草 beat+写章节状态机
      restructuring/SKILL.md
      novel-import/SKILL.md
      project-bootstrap/SKILL.md
    # 核心角色（SA01 S02 / SA02 S05b / SA03 Reviewer S06 公共协议 / SA04 S08）的主 skill 折叠进
    # subagents/{name}/agent.md，不在 skills/ 下单独挂载（原 ideation/ prose/ 目录不再持有独立 SKILL.md）。
    delegated/                     # 主要角色·通用委派执行的主 skill：S09
      style-transfer/SKILL.md
    review/                        # 【角色专属·SA03 Reviewer】三套评审镜头，按 brief scenario 选载
      developmental-review/SKILL.md  #   好不好·发展性：故事成不成立，scope chapter/manuscript（§2.5）
      line-editing-review/SKILL.md   #   文字精修：语言级，表达实现强、不重开结构
      consistency-review/SKILL.md    #   对不对·校对：忠实度+硬一致两阶段，不含语法（proofread 负责）
    reference/                     # 【工程空间/小说对象定义】只放对象 schema + 创作流程/门槛定义，非杂货铺
      story-development-flow/SKILL.md   # 创作流程图 + 五道就绪门槛 + 软硬原则（《04.5》）
      project-schema/SKILL.md
      worldbuilding-schema/SKILL.md
      character-schema/SKILL.md
      outline-schema/SKILL.md
      style-schema/SKILL.md
      materials-and-process-schema/SKILL.md
    common/                        # 【跨角色共用】子技能（scope=多角色共用，作单一真源）
      restraint/SKILL.md                    #   反匠气负向护栏：writer 写时避、reviewer 审时抓
      scene-and-plot-construction/SKILL.md  #   场景/情节因果范式
      character-believability/SKILL.md      #   人物可信度范式
      structural-pacing-diagnosis/SKILL.md  #   全局结构/节奏诊断
      thematic-coherence/SKILL.md           #   主题落地范式
    writer/                        # 【角色专属·SA02】只有 writer 用的子技能
      prose-craft-by-example/      #   正向文笔技法（范例驱动），仅 writer 展开正文时按需读
        SKILL.md
        references/                #     深层素材：show-vs-tell/deep-pov/sensory-grounding/dialogue-craft/
                                   #     subtext-craft/character-voice/layered-prose，SKILL.md 指引按需读
{workspace}/.iwriter/skills/       # 项目级作者自定义（§2.9），挂载在各源列表末位
  {slug}/SKILL.md
```

组织原则：

- **只有主要角色的主 skill 进挂载分组**（main/delegated）——挂载单元是目录、挂载对象是执行体，目录分组的物理意义就是挂载集合；核心角色的主 skill 折叠进各自 `agent.md`（ideation/prose/review 因此不作为独立挂载 skill 目录存在，其内容在 subAgent 正文里）。
- **子技能（subSkill）按 scope/type 分四处，落位判定见 03 §2.1**：① **角色专属·单件**（只该角色用，如 SA02 Writer 的 `prose-craft-by-example`、SA03 Reviewer 的三套评审镜头）→ `creative/{role}/`；① ' **角色内子部件共用**（仅一个角色的多个子技能/镜头共用、不外泄给别的角色）→ **`creative/{role}/common/`**，比 `creative/common` 更局部；② **跨顶层角色共用**（多个顶层角色用同一份，如 restraint 被 writer+reviewer 用、场景/人物/结构/主题范式被 A00+writer+reviewer+explorer 用）→ `creative/common/`，作单一真源、避免各自 inline 漂移；③ **工程空间/小说对象定义**（对象 schema 与创作流程/门槛定义，非创作技法）→ `creative/reference/`——**只放"对象/规格"，不是大家都往里塞的杂货铺**。落位判据是"共用面到哪"：一个角色内 → `{role}/common`；跨角色 → `common`。（当前 `creative/{role}/common` 暂空——restraint 与四范式均跨顶层角色、归 `creative/common`；此级供后续，如 reviewer 三镜头日后出现仅镜头间共用的技能。）
- **owner 技能必须挂载才能被按名发现，`references/*.md` 叶子按相对路径读、不单独挂载**：skills 中间件只把**挂载源里的 `{name}/SKILL.md`** 列进系统 prompt 的技能清单（名 + 一句话描述 + 路径），agent 靠**名字**在清单里定位、用清单给的路径 `read_file`——所以带 SKILL.md 的 owner 子技能（如 `prose-craft-by-example`、`restraint`）必须在用它的执行体 `skills` 源里；owner 目录下的 `references/*.md`（深层范例）是渐进披露第三层，由 owner 的 SKILL.md 指引、相对路径按需读，不进任何挂载源、不占清单。（清单是紧凑行、非正文；正文与 references 都按需读，不构成常驻上下文负担。）
- **技能目录名 = 技能 name = 常规 kebab-case**（`prose-craft-by-example`），**不带 ID 前缀**——S/SS 编号是设计文档层的索引，不进入目录名与技能 `name`；编号与技能的对应关系由 §2.2 总表维护；作者项目级自定义技能遵循同一命名规则（NFR-3）。
- **一个 owner 子技能一个目录**，技法范例、对照表等深层素材放该目录下的 `references/`，由 SKILL.md 正文指引按需读取——渐进披露第三层，不占常驻上下文。

**挂载矩阵**（即 §2.10 各定义文件 `skills` 字段的取值；顺序即覆盖顺序，后者胜出）：

| 执行体 | skills 源（按序） |
| --- | --- |
| A00（主控） | `common` → `creative/common` → `creative/reference` → `creative/main` → `creative/delegated` → `{workspace}/.iwriter/skills`（A00 大纲/前端建议类要用 `creative/common` 的结构/主题范式，故挂载） |
| SA01 Explorer | 主 skill（S02）在 `agent.md`；挂 `common` → `creative/common`（人物/主题范式） → `creative/reference` →（若有角色专属子技能 `creative/explorer`）→ `{workspace}/.iwriter/skills` |
| SA02 Writer | 主 skill（S05b 展开/修订流程）**在 `agent.md`**；挂 `common` → `creative/common`（restraint、scene-and-plot-construction、character-believability 等范式） → `creative/reference`（对象 schema） → `creative/writer`（prose-craft-by-example） → `{workspace}/.iwriter/skills` |
| SA03 Reviewer | 公共评审协议 + 统一输出契约在 `agent.md`；挂 `common` → `creative/common`（restraint、结构/人物/主题范式） → `creative/reference`（对象 schema） → `creative/review`（developmental-review、line-editing-review、consistency-review 三镜头） → `{workspace}/.iwriter/skills` |
| SA04 Researcher（共用，`subagents/common/`） | `common`（含 `web-research`，域无关） → `{workspace}/.iwriter/skills` |
| general-purpose（框架自动） | 继承 A00 全部（S09 与 SS17 提炼批次由此可达） |

三点说明：① `creative/delegated` 挂给 A00 而非某个专用子 Agent——A00 自己不执行 S09，但 S01 路由需要看见它的 frontmatter 才知道可委派，且 general-purpose 继承 A00 技能集后才能实际执行（SS17 提炼批次经 general-purpose 继承的 delegated/reference 引用可达）；② 子技能按 scope 分组、只挂到用它的执行体，技能清单因此收敛为"本角色相关"的紧凑行（名 + 描述），正文与 `references/` 叶子仍按需读——不构成常驻正文负担；③ **项目级 skills 目录 `{workspace}/.iwriter/skills` 固定放在每个源列表末位，last-wins 覆盖即是 FR-9.3"项目级自定义 > 内置默认"优先级裁决的机制实现**——不需要另写裁决逻辑，但 §2.9 的系统不变量（审批、红线）不在技能层，覆盖不掉。

## 4. 执行体 prompt 关键点（A00、SA01-SA04）

按 03 §2.1 的原则，执行体 prompt 只承载四类内容：**身份定位、工具范围（frontmatter `tools` 承载，prompt 正文不重复罗列）、输入输出契约、安全红线**；流程逻辑一律在 skill 里，prompt 通过指针引用主 skill。以下是各执行体 prompt 必须包含的关键点，作为编写 `subagents/{domain}/{name}/agent.md` 正文与 A00 system prompt 的检查清单：

**A00 主控 Agent**

- 身份定位：Creative Domain 主控——任务理解、S01 路由、结果收束；直接执行设定类（S03）、大纲类（S04）、重构诊断（S07）、导入编排（S10：整备直接执行，提炼分批委派）、初始化与 `project.md` 维护（S11）与记录类（SS15 轻量追加），其余委派；大体量任务（S06 全稿宏观级、S10 整本提炼）的分批编排与跨批聚合（03 §2.14）。
- 输入输出契约：委派 brief 必含任务类别与目标对象路径；S05 展开链路附 `targetChapter`（绝对路径）+ 范围（beat 若有在文件里、不转述进 brief）+ 已批准的写作会话授权；**评审类委派 reviewer 的 brief 必含 `files`（绝对路径）+ `intent` + `scenario`（一或多：`developmental`[+`scope`]/ `line` / `consistency`）+ 参照物路径（章纲/总纲、`project.md`）**；reviewer 回传简报 + `/large_tool_results/review-*.md` 路径，A00 读取后按需处置（喂 SA02 修订 / 提升进 `review-findings.md`）；**SA02 返稿后编排随写随评（模式A）**：委派 reviewer（`scenario=developmental`、`scope=chapter`，不做一致性/文字精修）→ SA02 修订一轮 → 作者整章终审，评审意见不落盘；**模式B** 由作者显式触发（好不好/文字精修/一致性/全视角=多任务），全视角各出一表、全稿发展性用 `scope=manuscript`，可落 `review-findings.md`；S08 必含 question + scope（researcher 回传 `/large_tool_results/` 交付件路径，A00 读取后自行决定是否提炼进正式对象——研究原料不自动进 `exploration/`）；S10 提炼批次（SS17）委派必含提炼范围、章节区间与批次标识；S06 全稿宏观级超单批预算（约 5 万字）时分批委派，brief 另含章节区间与批次标识（03 §2.14）；reviewer 回传后按 §1 S06 持久化步骤提议问题清单落盘 `process/review-findings.md`；整章终审 rework 意见转 S05 修订链路任务、会话保持激活（03 §5.3）。子 Agent 回报以最终响应文本呈现，不使用结构化提交工具（issues#1）；**畸形回报的识别与处置是 A00 的契约责任**（03 §5.7）——回报不符合 brief 契约或固定状态词表时不得当作有效结果收束，应重新委派（附纠正说明）或向作者暴露原始回报；委派失败/子 Agent 异常终止的错误回报同样不静默吞掉。
- 安全红线：**每轮先路由再行动**（S01 内联在 system prompt 的 "Routing (every turn)" 节，天然常驻）；先理解意图、按任务读取最小对象集，不做启动扫描/自动 git diff/自动重建摘要（03 §1.4/§3）；候选未经确认不进正式对象；冲突时整理方案与影响面、不替作者裁决（FR-11.2）；版本字段不自动推进（03 §4）；协作记忆只影响工作方式不提供剧情事实。
- skill 指针：S01 task-routing 折叠进本 prompt（非挂载 skill）；直接执行时按场景指向 S03/S04/S07/S10/S11；记录类指向 SS15。

**SA01 Explorer**

- 身份定位：构思候选生成器——发散出有真实区分度的 2-3 个方向。
- 工具面：文档读取组 + `create_document`（产出限定 `exploration/`）。
- 输入输出契约：brief 含主题与已有对象引用；每方向独立一份 `exploration/{类型}-{方向名}.md`；固定状态词表：已完成 / 方向不足需作者决定是否继续发散 / 需要更多上下文。
- 安全红线：不评判优劣只描述差异；不擅自晋升或淘汰候选；不写 `exploration/` 以外路径。
- skill 指针：S02。

**SA02 Writer**

- 身份定位：章纲场景（+ 可选 beat）→ 正文的块级编辑执行体；**声音主锚是 `styles/` 范文（照嗓子写、别抄内容，范文 outrank 分析字段与通用 craft），主题/分析不作即时输入**（03 §7）；**对 beat 有判断权**（默认顺着、透明改动），不拥有 beat 层的授权（增删重排 beat 的授权是 A00 经 `confirm_writing_plan`）。
- 工具面：文档读取组 + 块级编辑 5 个（经 interruptOn / 写作会话自动累积，03 §5.3）。
- 输入输出契约：brief 声明链路——展开链路附 `targetChapter`（绝对路径）+ 范围（**beat 若有是 `targetChapter` 里的分段提示、不在 brief 里；无 beat 则从章纲场景写**）；修订链路附修改意图与允许范围。`targetChapter` 缺失/模糊 → `MISSING_FIELDS`。固定状态词表：已完成 / 前提缺口（章纲未确认、设定不稳，触发 S01 第 9 步回补）/ 需要先改计划（beat 需结构改动）/ 需要先改章纲 / 需要更多上下文。
- 安全红线：**对 beat 有判断权但默认顺着写、改动必透明**（小改自理并在总结说明；结构性改动返回"需要先改计划"+方案，不擅自重构；brief 标"严格按 beat"则产出并附保留意见）；不改已确认的目标/冲突/结果；无明确 target 不自由发挥；修订不越声明范围顺手改无关段落；交付一律块级编辑提案，不直接吐正文文本。
- skill 指针：S05b。

**SA03 Reviewer**（合并"好不好"编辑评审 + "对不对"一致性校对；`subagents/creative/reviewer/`）

- 身份定位：workspace 只读的评审执行体，编辑角色后端三顶帽子——按 brief `scenario` 选载镜头：发展性·好不好（`developmental-review`，scope chapter/manuscript）/ 文字·文字精修（`line-editing-review`）/ 校对·对不对（`consistency-review`）；可多选=全视角。agent.md 正文承载公共评审协议 + 统一输出契约（身份/scenario 路由/brief 校验/输出契约/红线），评审 how-to 在三套镜头 subSkill 里（四段式，输出不重复）。
- 工具面：文档读取组 + `find_references` + `write_file`（**仅**落盘检查文件到 `/large_tool_results/`）。**权限沿用 SA04 Researcher 同款——不设 blanket write-deny**（否则 temp 检查文件写不了），workspace 只读靠红线 + 审批层（workspace 写→requires-review、不静默；temp 写→自动放行）。
- 输入输出契约：brief 必含 `files`（绝对路径）+ `intent` + `scenario`（一或多：`developmental`[+`scope` chapter/manuscript]/ `line` / `consistency`）+ 参照物（章纲/总纲、`project.md` 绝对路径）；缺失回 `MISSING_FIELDS`。核查颗粒度由 `scope`/任务定；全稿宏观级分批时（03 §2.14）另含章节区间、批次标识与前批"跨批线索"摘要。**统一输出契约**：详细发现写 `/large_tool_results/review-<slug>.md`，回传**简报 + 文件路径**；每条按五类输出（判断/诊断/方向/方案/行动）组织、四级优先级（致命/重要/局部/可选）分级、标注依据对象；多任务各 block 各 verdict 分列不合并。
- 安全红线：**workspace 只读**——只写 `/large_tool_results/`，绝不改稿/改工作区对象；只给意见/方向、采纳由 SA02/作者定；整理问题不替作者裁决（含不裁决外部反馈本身是否正确）。

## 5. 技能文档写作要点

编写 S/SS 技能文档（SKILL.md）时遵守（依据 03 §7 与 issues#2/#4/#7 教训）：

- frontmatter `description` 只写触发条件（"什么时候用我"），不写流程摘要——它是渐进披露的常驻部分，流程在正文按需读取；
- **匹配形式与失败类型**：规则违反类失败用禁止清单；输出形状（shaping）类失败必须用正例/范例，用禁止清单反而会让问题更严重——SS10 明确禁止"每句话必须同时做两件事"式可数清单；
- 新增/保留一个技能前必须能回答：它解决什么具体问题、如何验证效果（无此技能的基线场景 vs 有此技能的对比）——回答不了的应下线或合并（issues#7）；
- 深层素材（范例文本、对照表）放技能目录 `references/`，SKILL.md 正文指引按需读取，不占常驻上下文；
- **引用其它技能一律用技能名，绝不用挂载键路径**：agent 从系统 prompt 自动生成的技能清单里按**名字**定位、用清单给的路径 `read_file`；挂载键（`creative/writer`、`creative/common` 之类）只是磁盘装配配置，**agent 不可见**，写进正文等于给了一个 agent 无法解析的地址。owner 内部的深层素材用相对路径 `references/x.md`（相对该 owner 的 SKILL.md）。（本轮踩坑固化。）
- 技能步骤不得写入"每轮启动读取 status / 全局扫描 / 自动 git diff"（03 §1.4 状态边界）；需要全局态势的步骤写成"必要时读取/提议重建/请求确认"；
- 项目级自定义技能可用自然语言书写，不要求理解内部 ID 体系（NFR-3）。

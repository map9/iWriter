# 全能创作搭子｜AI Writing Buddy：脚手架 详细设计

> 本文档承载**脚手架能力**的详细设计，由《03. 小说创作搭子｜AI  Story Buddy：概要设计》§2.10-§2.13、§5.1 拆出。脚手架 = host 在 deepagents 框架之上实现的、与具体 domain 无关的通用宿主能力，edit 与 creative 两个 domain 共用：框架能力是 deepagents 自带的（纯复用）；脚手架能力是本设计要交付的，一次实现、各域共享，不属于任何单一 domain；domain 层只做实例化（creative 域的实例化内容见《04.3 小说创作搭子｜AI  Story Buddy：Agent+Skills 详细设计》）。
>
> **引用约定**：`§x`（如无特别说明）指《03. 概要设计》的章节；本文内部互引记作"本文 §n"。
>
> **章节安排**：§1 先给出用户级 + 项目级的**完整目录结构**——后面各章的文件落点都在这张图里；§2-§6 分别是**子 Agent / Skills / Memory / 块级读写工具 / 审批底座**的**目标设计**（只讲要做成什么样）；§7 集中承载**与现有代码相关的重构**——现状缺陷、现有资产复用、实施阶段核验。§2-§6 的设计结论是在 §7 的重构判断基础上成立的，两部分分开是为了让"目标"与"改造路径"各自清晰。

## 1. 目录结构：用户级 + 项目级

脚手架的文件资产分**两级根**，职责不同、隔离清晰：

- **用户级 AI 运行时根 `~/.iwriter/ai/`**：系统资产（内置 skills、子 Agent 定义随应用分发同步）+ 用户级协作记忆，**跨项目生效**；它是 AgentEngine 的 `aiRootPath`。
- **项目级工程态根 `{workspace}/.iwriter/`**：单个作品工作区内的 AI 工程态——项目级自定义 skills、派生缓存、写作会话工程态；**不进 git、不存放记忆、不存放子 Agent 定义**。

### 1.1 用户级 `~/.iwriter/ai/`

```
~/.iwriter/ai/                   # 用户级 AI 运行时根（AgentEngine 的 aiRootPath），跨项目生效
  empty-fs/                      # 无工作区会话的兜底文件系统根（现状保留）
  memory/                        # 用户级（作者级）协作记忆，按 domain 隔离，本期只读装配（本文 §4）
    edit/memory.md
    creative/memory.md
  skills/                        # 内置技能同步目标，按 common + domain 组织（本文 §3）
    common/                      #   两域共用技能（web-research、document-block-tools 等）
    edit/                        #   edit 域技能
    creative/                    #   creative 域技能（完整目录树见《04.3》§3）
  subagents/                     # 专用子 Agent 定义同步目标，按 common + domain 组织（本文 §2）
    common/                      #   两域共用的专用子 Agent
      researcher/agent.md        #     查证是两域通用承包商：web 工具面/红线/契约都域无关；
                                 #     挂共享 web-research 技能，交付件落盘会话级 /large_tool_results/
    edit/                        #   edit 域专用子 Agent（机制相同，内容不在本设计展开）
    creative/                    #   目录名 = 子 Agent name（kebab-case，不带 ID 前缀）
      explorer/agent.md
      writer/agent.md
      consistency-checker/agent.md
```

### 1.2 项目级 `{workspace}/.iwriter/`

```
{workspace}/.iwriter/            # 项目级工程态目录：agent/host 管理，不进 git
                                 # 不存放记忆（协作记忆只有用户级）、不存放子 Agent 定义
  skills/
    {slug}/SKILL.md              # 可选、懒创建：项目级作者自定义工作流 skill
                                 # 固定挂在技能源列表末位，覆盖内置同名技能（本文 §3）
  status.md                      # 可选：派生状态摘要缓存，纯派生物（字段见《04.2》）
  <写作会话工程态>               # 写作会话基线快照等运行中工程态（§5.3），不进 git
```

工作区内的正式对象（`project.md`、`worldbuilding/`、`characters/`、`outline/`、`manuscript/` 等）属**对象模型**，见《04.2》与 03 §1.1，不在脚手架范围。

### 1.3 两级的分工与隔离原则

- **系统资产 vs 用户/项目资产**：`skills/` 与 `subagents/` 是**系统资产**，随应用分发并同步到用户级运行时根（两者同步机制相同）；用户级 `memory/` 由作者手工维护；项目级 `.iwriter/skills/` 由作者懒创建（agent 可代写草稿，作者确认）。
- **记忆只有用户级一层**：不设项目级协作记忆（工作区 `.iwriter/` 不放记忆文件），也不使用 deepagents 默认的 `~/.deepagents/{agentName}/agent.md`、`.deepagents/agent.md`（理由见本文 §4）。项目特有的工作流约定由项目级自定义 skills（§2.9）或当前对话指令承载。
- **子 Agent 定义只有用户级一层**：`subagents/` 是系统资产，不开放项目级覆盖（边界见本文 §2）。
- **`agent.md` 与 `memory.md` 双重隔离**：子 Agent 定义文件固定名 `agent.md` 且**只存在于 `subagents/` 根下**；记忆文件固定名 `memory.md` 且**只存在于 `memory/` 根下**——**文件名 + 目录根双重隔离**。装配记忆源时不扫描 `subagents/` 根，两者不会混成同一个事实来源，也不会互相误读。
- **优先级方向**：项目级自定义 skill 覆盖内置默认（本文 §3 的 last-wins 机制）；但系统不变量（03 §2.9 的审批机制与安全红线）不在技能层，覆盖不掉。
- **另有会话级虚拟挂载（非持久目录）**：运行时文件系统除上面两级持久根外，还挂 `/large_tool_results/`、`/conversation_history/` 两个虚拟区，映射到 `os.tmpdir()` 临时目录、会话结束即清，是子 Agent 交付件的免审批暂存区（详见本文 §6 策略层）。它们不是本节的持久目录结构的一部分，此处仅提示其存在。

## 2. 子 Agent 设计（声明式装配）

> 对应 §2.10；落点见本文 §1.1 的 `subagents/`。**现有子 Agent 构造代码如何复用、现存目录如何迁移见本文 §7.2。**

**框架事实（deepagents，设计时已核实）**：subagent 在框架层只有编程式装配——`createDeepAgent({ subagents: SubAgent[] })`，`SubAgent` 是 `{ name, description, systemPrompt, tools?, model?, skills?, permissions?, interruptOn?, ... }` 的配置对象，框架本身**没有**从 markdown 加载 subagent 定义的机制；与之对照，skills 在框架层已经是文件化的（SKILL.md 按 Agent Skills 规范从目录加载）。本设计因此自建一层"markdown 定义 → SubAgent 装配"的脚手架，把增删改一个专用子 Agent 降为文件操作。

**目录即子 Agent**：

- 每个专用子 Agent 一个目录，定义文件固定名 `agent.md`（`subagents/{domain}/{name}/agent.md`），与技能"目录 + SKILL.md"的组织方式对齐，目录内可携带定义所需的辅助素材；
- **共用池 + 域目录**：装配器扫描 `subagents/common/` 与当前 domain 的目录（`subagents/{domain}/*/agent.md`），每个定义装配为一个 SubAgent；同名（frontmatter `name` 相同）时 **domain 目录覆盖 common**（完整替换非合并）——与本文 §3 技能源的 last-wins 语义一致，某个域需要差异化某个共用子 Agent 时放一份同名定义即可，不必改共用池。**该覆盖机制当前无实例**：唯一的共用子 Agent researcher 定为纯承包商（域无关身份/工具/红线，交付去处由委派单决定），各域直接复用不覆盖；机制保留供将来真需要差异化时用；
- **命名约定**（与技能一致）：子 Agent 目录名 = frontmatter `name` = 常规 kebab-case（如 `writer`、`consistency-checker`），**不带 ID 前缀**——SA 编号是设计文档层的索引，不进入目录名与 `name`，编号与子 Agent 的对应关系由 03 §2.2 总表维护；`name` 同时是 `task` 委派时使用的 subagent 标识；
- **general-purpose 不落定义文件**：它由框架自动提供（S09 及 S10 提炼批次（SS17）的通用委派路径依赖它），为它建文件反而制造第二个事实来源。

**定义文件格式**：frontmatter 承载配置、正文即 systemPrompt：

| 定义文件字段 | 对应 SubAgent 字段 | 说明 |
| --- | --- | --- |
| frontmatter `name` / `description` | `name` / `description` | `description` 是 `task` 工具的委派路由信号，质量要求高（写"什么任务该派给它"，不是自我介绍） |
| frontmatter `model` | `model` | 可选，`"provider:model"` 字符串，缺省继承主控 |
| frontmatter `model-params` | `model`（构造参数） | 可选，采样/推理参数对象：`temperature` / `top-p` / `reasoning-effort`（03 §7 任务阶段差异化的机制落点，如 SA02 提高 temperature、SA03 保持精确默认）。装配器把 `model` 字符串 + `model-params` 一并解析为模型实例；参数对具体 provider 的支持差异由装配层校验，不支持的参数忽略并告警，不使装配失败。A00 主控的参数由 domain 配置承载，不经此字段 |
| frontmatter `tools` | `tools` | **工具名白名单**，装配时经"名字→实例"注册表映射；出现未注册的工具名装配立即失败（fail fast），不静默忽略——工具面是安全边界 |
| frontmatter `skills` | `skills` | 技能源目录路径数组，即 §2.1"prompt 通过指针引用主 skill"的机制化落点；各执行体的取值见 §2.11 挂载矩阵 |
| frontmatter `permissions` | `permissions` | 纯 JSON 结构，**工具层强制收窄的实现手段**：SA03 的"只读"就在这里声明（替换而非合并父 Agent 权限） |
| frontmatter `interruptOn` | `interruptOn` | 纯 JSON，写操作的 HITL 确认点 |
| 正文 | `systemPrompt` | 只写 §2.1 允许的四类内容：身份定位、输入输出契约、安全红线（工具范围已由 frontmatter 承载）；流程逻辑一概不写，在 skill 里 |

`responseFormat`（需要 Zod schema，且子 Agent 按既有决策不使用结构化输出约束）与自定义 `middleware`（SA01-SA04 均不需要）不进入定义文件——这两项正是无法声明化的字段，方案因此无损。

**装配流程**：agent 实例创建时扫描 `subagents/common/` 与当前 domain 的定义目录 → 解析各 `{name}/agent.md` 的 frontmatter → 工具名查注册表换成实例 → 组装为 `SubAgent[]` 传入 `createDeepAgent`。装配器本身是脚手架的一部分，各 domain 共用。

**边界与约束**：

- **"动态"指装配期动态，不是运行中热插拔**：subagents 在 agent 实例创建时静态固定，定义文件的改动在下次会话（实例重建）时生效。这已满足设计目标——增删改一个专用子 Agent 是文件操作而非代码变更（裁撤 SA05 那样的决策 = 删一个文件），prompt 调试不需要改代码；
- **与 §2.9 的边界**：`subagents/` 定义文件是系统资产，不开放给作者项目级覆盖；若未来沿 FR-9 方向允许项目级定制子 Agent，只允许覆盖 systemPrompt 正文与 `skills` 指针，**不允许扩大 `tools`/`permissions`**——工具面与权限是系统不变量，同 §2.9 审批机制的地位。

## 3. Skills 设计（目录与挂载机制）

> 对应 §2.11 机制部分；系统资产同步落点见本文 §1.1、项目级挂载点见本文 §1.2。**general-purpose 继承主 Agent 技能这一承重假设的核验见本文 §7.2。**

**框架约束（决定目录怎么切）**：deepagents 技能加载以**目录为挂载单元**——`skills: string[]` 是源目录列表，源目录下每个 `{skill-name}/SKILL.md` 是一个技能（目录名必须等于技能 `name`）；多个源之间**同名后者覆盖前者（last-wins）**；技能按渐进披露加载（frontmatter 列表常驻，正文按需读取，技能目录内可携带更深层的参考文件供执行时按需读取）。子 Agent 不继承主 Agent 的技能，唯一例外是框架自动提供的 general-purpose 子 Agent——这正是 S09 与 S10 提炼批次（SS17）走通用委派仍能拿到技能的机制前提。

机制要点（脚手架层，各域通用）：

- **目录即挂载单元**：执行体定义文件的 `skills` 字段是源目录路径数组，目录分组的物理意义就是挂载集合，按执行途径切分是诚实的；
- **同名 last-wins**：多个源之间同名技能后者覆盖前者；项目级 skills 目录 `{workspace}/.iwriter/skills`（本文 §1.2）固定挂在每个源列表末位，last-wins 即 FR-9.3"项目级自定义 > 内置默认"优先级裁决的机制实现，不需要另写裁决逻辑（但 03 §2.9 的系统不变量——审批机制与安全红线——不在技能层，覆盖不掉）；
- **渐进披露三层**：frontmatter 列表常驻 → SKILL.md 正文按需读取 → 技能目录内 `references/` 深层素材由正文指引按需读取，不占常驻上下文；
- **命名约定**：技能目录名 = 技能 `name` = 常规 kebab-case（如 `scene-to-prose`），**不带 ID 前缀**——S/SS 编号是设计文档层的索引，不进入目录名与技能 `name`，编号与技能的对应关系由 03 §2.2 总表维护；系统技能与作者项目级自定义技能遵循同一命名规则（NFR-3，作者不需要理解内部编号——编号本就不出现在文件系统中）；
- **系统资产同步**：`skills/` 与 `subagents/` 同为系统资产，随应用分发并同步到用户级运行时根目录 `~/.iwriter/ai/`（目录全貌见本文 §1.1），不属于工程空间对象模型。

creative 域的完整目录树、挂载矩阵与现有技能处置见《04.3 小说创作搭子｜AI  Story Buddy：Agent+Skills 详细设计》§3。

## 4. Memory 设计（本期只读装配）

> 对应 §2.13、FR-13.4/13.5/13.6；这是 edit 与 creative 共用的脚手架能力，creative 只是其中一个 domain 实例。目录落点见本文 §1.1 的 `memory/`。

**目录约定**：协作记忆**只有用户级（作者级）一层**，按 domain 隔离，位于用户级运行时根 `~/.iwriter/ai/memory/`，文件名固定 `memory.md`（`edit/memory.md` 与 `creative/memory.md`，见本文 §1.1）。

**不设项目级协作记忆**：工作区 `.iwriter/` 只承载项目级自定义 skills、状态缓存与会话工程态（本文 §1.2），不存放记忆文件；项目特有的工作流约定由项目级自定义 skills（03 §2.9）或当前对话指令承载。也不使用 deepagents 默认的 `~/.deepagents/{agentName}/agent.md`、`.deepagents/agent.md` 等路径：不共享单一记忆文件（避免 edit 与 creative 协作规则互相污染），也不把 iWriter 脚手架管理的记忆资产放进 deepagents 默认记忆目录（模糊 host 与框架的责任边界）。

**装配逻辑**：脚手架在创建 agent 实例时由当前 domain 决定记忆源，而不是让各 domain 自己拼接路径。

1. `DomainStrategy` 或等价配置声明当前 `domain` 与记忆路径；
2. `AgentEngine` 创建 deepagents 实例时，按 domain 装配 memory sources：`~/.iwriter/ai/memory/{domain}/memory.md`（不存在时跳过，或由 host 以默认模板初始化后供作者手工编辑）；
3. 注入 prompt 时明确说明：该文件是协作规则（跨项目生效），不是剧情事实源；**本期记忆只读，agent 不得写入或更新它**；用户当前明确指令优先于记忆；正式对象优先于记忆；
4. 子 Agent 继承同一 domain 的协作记忆边界；执行体定义文件虽也名为 `agent.md`，但只存在于 `subagents/` 根下（本文 §1.3 双重隔离），装配记忆源时不扫描该根，两者不会互相误读。

**本期只读，更新机制延后**（FR-13.5/13.6）：

- 不提供 `memory_update` 或任何 Agent 写入记忆的路径；记忆内容由作者手工维护；
- deepagents 默认 memory prompt 会鼓励 agent 在学到偏好时自动更新记忆（经 `write_file`/`edit_file`），装配时**必须覆盖该提示为"记忆只读"**——记忆文件位于工作区之外，写入本身会被审批策略层"工作区外自动拒绝"封死（本文 §6 第 3 层），但不覆盖提示会让 agent 反复尝试写入、浪费轮次；
- prompt/skills 只描述"读取并遵循记忆中的协作规则"，不得包含任何写入、沉淀或更新记忆的步骤；
- 记忆的自动沉淀与更新（候选捕获、作用域分类、边界过滤、合并去重、受限写入、domain 覆盖策略）属于整体记忆系统设计，后期统一考虑，本设计不展开。

## 5. 块级读写工具设计

> 对通用读写工具（文档读取组 + 块级编辑组，§2.7）行为层的重设计，属脚手架能力——edit 与 creative 两域共用同一套读写协议与参考技能。**本节给出目标设计；现状四缺陷及根因、以及"设计如何回应缺陷"的映射见本文 §7.1。**

1. **两级块模型**：块分容器块（列表/引用/代码块/表格）与叶块（段落/标题/列表项）两级；读输出中叶块标注容器归属，**容器永不跨页**。
2. **自适应分页**：分页从"按段数"改为"按内容预算"（字符预算，默认约一页 4000 字符），以块为最小单位聚集、绝不切开块；超出预算的单个大块（长代码块/表格）独占一页。`limit` 语义相应从段数改为预算上限。
3. **列表编辑规则**：单项的纯文字修改 → 叶级 `edit_block`（保留现路径）；涉及结构的修改（增删项、调整嵌套、跨项改写）→ **容器级 `edit_block`**：`new_content` 传完整容器的 markdown，落地实现为整容器替换。整容器替换在编辑器路径与磁盘路径上都是"同一段 markdown 的整体替换"，两条路径行为天然一致——结构同构问题从"逐项局部修补"降维成"整段重排"，这是把列表做对的关键。何时用哪级由工具参考技能给出决策树（见下）。
4. **批量提交协议**：同一快照上的多个编辑提案**一次性批量提交**；审批呈现为一张按**文档正序**排列的聚合 diff 卡，一次决策通过/拒绝、可逐条覆写（§5.2）；引擎负责按稳定节点 ID 解析并**按文档位置逆序应用**——顺序正确性是引擎职责，永远不是作者交互的职责。写作会话内（§5.3）自动累积的块编辑同样逆序落地。
5. **ID 生命周期契约**：块 ID 的有效期 = 一个快照版本；同一快照内可连续发出多个编辑提案，**无需中途重读**；批量落地后，工具响应直接返回受影响区域的新块映射（旧 ID→新 ID + 邻域新视图），只有结构大变时才要求全量重读 outline——取代现在"每次编辑后全量重读"的粗粒度契约。**作者手工编辑同样推进快照版本**（03 §5.3 并发语义）：agent 每次块级写入做新鲜度校验，持有陈旧快照 ID 的写入失败并返回新块映射，调用方重读适应后继续——作者修改是新事实，不是需要合并解决的冲突。
6. **工具参考技能**：启用 §2.7"工具专属参考技能"特例的**首个实例**——`common/document-block-tools`（跨域，随 `skills/common/` 挂载给全部执行体，本文 §3），承载：两级块模型、分页语义、列表编辑决策树、批量提交模式、ID 生命周期与失效恢复。edit 域与 creative 域的 system prompt 由此不再各自重复说明这套用法——这正是该特例条款设立时预期的场景：说明依附于工具本身，而非驱动任何创作场景。
7. **单一内容路由**：文件在编辑器打开时，编辑器缓冲是当前有效内容，块级读写经 host 统一路由——打开的文件操作编辑器文档、未打开的文件操作磁盘文件，两侧不得静默分叉（NFR-4，issues#8 的正面回答）。§5.3 的基线快照与整章 diff 必须取自同一路由：会话（懒）激活取基线时若目标文件有未保存修改，先同步落盘一次再取基线。**写作会话期间作者可随时手工编辑同一文件**（03 §5.3 code agent 式并发语义）：不挂起、不弹窗、不加锁，编辑器仅显示安静的"AI 写作会话进行中"标识；作者编辑经设计 5 的快照版本推进对 agent 现形。**与外部修改/自动保存的并发处理沿用现有保存管线的约束，实施阶段核验见本文 §7.2。**

## 6. 审批底座设计（五段裁决级联）

> 对应 §5.1；edit 与 creative 共用的脚手架能力——所有写动作（文件写、块级编辑、creative 专项、写作会话累积、子 Agent 交付件）都收敛到同一条裁决管线。**本节是目标设计（管线长什么样）；哪些段复用现有实现、哪一段是新增、核验点见本文 §7.2。**

一次中断携带本轮全部 `actionRequests[]`（命中 interruptOn 的全部工具调用）。每个动作按**固定顺序的级联**被裁为 approve/edit/reject——某段裁定即止，未裁定者落到人工。

**Stage 0 — 框架捕获**（deepagents `interruptOn`）：interruptOn 两源合流收集 actionRequests——文件系统脚手架的文件写工具（write/edit/rename/delete/move_file）+ 域配置（块级编辑 + creative 专项：`confirm_writing_plan`、`git_commit`/`git_tag`/`git_restore` 等；§2.7 工具重审后随退役工具清理旧条目）。恢复时以按**原始索引对齐**的决策数组一次性回传（`Command({ resume: { decisions } })`）。决策态：`approved` / `edited`（"改完即契约"）/ `rejected`（带理由回模型）/ `responded`。

**Stage 1 — 路径策略**（host 纯代码 `FilesystemApprovalPolicy`，**仅文件写工具**）：按路径裁决——空/不安全段（`..`/`~`）/相对路径 → 自动拒绝；内部虚拟路径（`/large_tool_results/`、`/conversation_history/`）→ **自动放行**；工作区之外的绝对路径 → **自动拒绝**；工作区之内 → 交后续（人工）。

- **内部虚拟路径 = 子 Agent 交付件握手**：运行时文件系统是 CompositeBackend——工作区（或 `empty-fs` 兜底）挂根、真实读写；`/large_tool_results/`、`/conversation_history/` 映射到 `os.tmpdir()` 临时目录、`virtualMode`、会话销毁即清。生产者写 `/large_tool_results/{name}.json`、回传 `{path, summary}`，消费者按 path 读——研究/风格交付件走此路，免审批、会话级可丢弃、不污染工作区对象（`exploration/` 等候选区）。
- **本文 §4 记忆只读**即靠"工作区之外自动拒绝"兜底（记忆在工作区外）。
- **边界**：路径策略只管 deepagents 内建**文件**工具；域的块级/提案工具（edit_block…create_document）不走这里，进 Stage 2/3。

**Stage 2 — 会话授权**（host 纯代码，**唯一新增裁决源**，落地 §5.3 的"授权登记 + 懒激活"）：针对**块级编辑工具**——

- **授权登记**：`confirm_writing_plan` 在 Stage 5 被 approve 时，host 登记一份写作授权 {计划文本, 章节清单}（普通 S05 清单长度 1，S07 重构为多章）。host **只依赖这个必然可见的审批事件，不感知 task 委派**——S07 逐章委派引用已批准方案这件事对 host 透明，机制上不需要它可见；
- **懒激活**：块级编辑首次命中授权清单中某章节文件 → 激活该章写作会话，**此刻**按本文 §5 设计 7 的单一路由取基线快照（消除批准到动笔之间的基线陈旧）→ 自动放行并计入累积；后续命中已激活会话的编辑照常放行累积。**一个正文文件至多一个活动会话**；跨文件会话可并存；
- 否则（含域外）→ 交后续（人工）。**授权域只含计划声明的正文文件**；章纲及其它对象永不自动放行——SA02 越界即现形、照常人工评审（越权面最小化）；前提缺口切回构思（FR-2.4）时会话保持开启、不引入挂起态——域外写入照常人工审批，无泄漏面；
- **会话内新建文件**（create_document 造新章）不进本段自动放行，一律人工——新建面风险高于就地编辑；
- **配置位置**：host 段，读 host 持有的**会话登记**（threadId → {授权清单, 活动会话集合}，每个活动会话含 {目标文件, 基线快照, 累积记录}），与 Stage 1 同格、在域级 Stage 3 之前；domain 无关（edit/creative 都可能有写作会话）。

**Stage 3 — 混类守卫**（域级 `preDecideMixed`）：剩余 review 批次混入不同类别（块级编辑 vs creative 计划/审校 vs 文件写）时，非主导类自动拒绝并提示"分到不同轮次再提交"（当前主导序 edit > creative）。目的：每张审批卡单一类别，防混类批次一起蒙混过审。

**Stage 4 — 批次毒化**（安全级）：**Stage 1 路径策略产生过自动拒绝**时，整批其余未决动作全部拒绝——"半批落地"会造成不一致状态。**关键分界**：毒化只由 **Stage 1 安全拒绝**触发（机械安全 = 全灭）；**人工在聚合 diff 上逐条拒绝不触发毒化**（人工评审 = 逐项独立，§5.2 逐条覆写）；Stage 2 域外只是转人工、不是拒绝，也不触发毒化。

**Stage 5 — 人工评审 + 合并回传**：剩余动作 → DomainReviewItem（edit/creative/filesystem），以卡片队列呈现——

- 块级编辑：同一 file 的多个编辑聚合成一张按**文档正序**的 diff 卡，一次决策、可逐条覆写；引擎按稳定节点 ID **逆序应用**（顺序正确性是引擎职责，本文 §5 设计 4）；
- 文件写 / creative 计划 / git：各自独立卡；
- 渲染端决策态（跳过/打回/暂停批次）折算回四态；合并按"**既定 rejected → Stage 1-4 自动决定 → 人工决定**"三重叠加、原始索引对齐回传（`_mergeResumeDecisions`）。每线程至多一个飞行中断，重开时从孤儿 tool_call **再水化**未决中断。

**会话状态机**（贯穿 Stage 2/5）：`confirm_writing_plan` 在 Stage 5 被 approve → host 登记写作授权 → 块级编辑首次命中授权章节时懒激活该章会话（基线快照存 `.iwriter/`）→ Stage 2 自动累积域内块级编辑 → 会话闭合触发**整章终审**（基线 vs 现状聚合 diff 一张卡：approve+commit / rework / reject-restore）。补充状态转移（03 §5.3）：

- **rework 不闭合会话、不重置基线**：该章授权未完成、会话保持激活，rework 意见转 S05 修订链路任务后其块级编辑仍经 Stage 2 自动累积（按目标文件裁决，不区分链路），收束于再次整章终审；
- **终审卡归因**：host 以累积记录比对整章 diff，检测到非 agent 来源修改时标注"本章含手工修改，reject 将一并回退到基线"，此时 reject 需二次确认——保留手工部分的出口是 approve/rework；
- **授权结束**：章节清单全部终审完成，或作者显式取消授权；进程中断沿用未闭合会话恢复条款（03 §5.3）。

**子 Agent（如 SA02）的中断经 checkpointer 冒泡到 host，与主控走同一管线**（03 §5.4）。

**引擎级失败兜底与手动接管**（03 §5.7，脚手架层职责）：host 在工具分发层捕获**非法工具调用参数**（JSON 解析/schema 校验失败），转为说明错误原因的错误 tool result 回传模型供其修正重试，不静默终止会话；同一工具连续失败超限（默认 2 次）时停止重试、把失败原文呈现给作者。作者**中断接管**时 host 中止当前 run（含飞行中子 Agent 委派，checkpointer 停在最后完成步骤）：未落地的工具调用作废，已累积写入保留在工作树不自动回滚，未决审批卡保留，未闭合会话走恢复条款，并在对话中明示中断结果。

## 7. 重构设计（利用与改造现有代码）

> 前六章是**目标设计**；本章集中说明这些设计如何落到现有代码——哪些是对现状缺陷的**改造**、哪些是对现有实现的**复用**、哪些留待**实施阶段核验**。§2-§6 的设计结论都是在本章的重构判断基础上成立的。本章对应 03 §0"利用/重构现有代码"阶段的核验结论。

### 7.1 块级读写：现状四缺陷及根因（对应本文 §5）

本文 §5 的重设计针对现有通用读写工具的四个缺陷，根因如下：

1. **读得太碎、分页不自适应**：三个根因叠加——①分页单位实现为"空行分隔的文本段"而非块（实现把块内容用空行拼接后再按空行切分，含空行的块如代码块/多段引用被切碎，页内 `{b:n}` 与内容的对应断裂）；②默认每页 20 段按**段数**计数，与内容体量无关（20 个一行的列表项和 20 个长段落相差一个数量级）；③块模型对列表取**项级**粒度（每个列表项一个块），长列表一页装不下、每块只有几个字。
2. **列表写入很难做对**：块模型给列表的是项级 ID，而落地是"markdown 片段 → 局部 ProseMirror 结构替换"——单项编辑要经过 去前缀→补前缀→markdown→HTML→节点→剥掉容器取内层项 的多步往返，嵌套列表的缩进层级在往返中**没有稳定同构**；跨项修改（增删项、调整嵌套）用扁平位置区间删除会撕裂列表容器，编辑器的结构自修复产生意外结果。编辑器内路径与磁盘路径最终共用同一套局部结构替换，脆弱点相同（issues#8 同源）。
3. **批量修改逐条确认、顺序负担泄漏给交互**：一批多个编辑提案逐条审批，应用按提交顺序正序执行，先前的编辑使后续引用漂移——于是出现"审批时逆序确认"这种把**引擎的顺序正确性责任转嫁给作者交互**的用法。
4. **ID 生命周期不清**：块 ID 是快照期的顺序号，任何一次编辑后全量失效，而工具返回只说"全部重读 outline"——模型每改一块就全量重读一次；事实上提案在引擎内部按稳定节点 ID 解析，**同一快照内的多个编辑本可一次提交**，这条关键事实没有进入工具契约。

**设计对缺陷的回应**：

| 现状缺陷 | 本文 §5 的回应 |
| --- | --- |
| ① 读得太碎/分页不自适应 | 设计 1 两级块模型（容器永不跨页）+ 设计 2 自适应分页（按内容预算） |
| ② 列表写入难做对 | 设计 3 列表编辑规则（结构级改动走容器级整段替换，两路径同构） |
| ③ 批量逐条确认/顺序泄漏 | 设计 4 批量提交协议（引擎逆序应用，顺序不再是交互职责） |
| ④ ID 生命周期不清 | 设计 5 ID 生命周期契约（有效期 = 一个快照，落地返回新块映射） |
| 说明重复 / 双路径分叉 | 设计 6 工具参考技能 `document-block-tools` + 设计 7 单一内容路由 |

### 7.2 现有资产复用与实施阶段核验清单

以下各项确定复用/沿用现有实现，具体接入位置与兼容性在实施阶段核验，不属目标设计：

- **审批管线（本文 §6）**：五段中**四段直接复用现有实现**，一段是新增——
  - **复用**（已在 `AgentEngine._prepareActionRequestsForReview`/`_handleInterrupt`/`resumeRun` 落地）：Stage 0 interruptOn 两源合流；Stage 1 `FilesystemApprovalPolicy` 路径策略（含 `/large_tool_results/` 自动放行、工作区外自动拒绝）；Stage 3 `preDecideMixed` 混类守卫；Stage 4 批次毒化（`hasAutoReject` 全灭）；Stage 5 `_mergeResumeDecisions` 三重叠加 + 孤儿 tool_call 再水化（`_maybeRehydrateInterrupt`）。域配置层随 §2.7 工具重审调整 interruptOn 条目。
  - **新增**：Stage 2 会话授权——须在 host 增加**会话登记**（threadId → {授权清单, 活动会话集合}，活动会话含 {目标文件, 基线快照, 累积记录}）与一个与 Stage 1 同格的纯代码预裁决（读该登记，对块级编辑做授权域内自动放行 + 首次命中懒激活）；以及 `confirm_writing_plan` approve→登记授权、首次命中→激活会话、会话闭合→整章终审（含 rework 保持激活、手工修改归因）的状态流转。这是本管线唯一需要新写的机制，其余是编排/条目调整。另有小项：工具分发层的非法调用参数兜底（错误 tool result 回传 + 重试上限，本文 §6 末段）——实施时核验现有工具分发路径上解析失败的行为，确认无静默终止。
- **子 Agent 装配（本文 §2）**：装配代码的接入位置、现有子 Agent 构造逻辑能否复用、运行时现存的子 Agent 目录如何沿用/迁移。
- **general-purpose 技能继承（本文 §3）**：子 Agent 不继承主 Agent 技能、唯 general-purpose 例外——这是 S09 与 S10 提炼批次（SS17）通用委派路径的承重假设，实施前**优先核验**框架此行为仍成立。
- **子 Agent 中断冒泡（本文 §6 Stage 0 / 会话状态机）**：子 Agent 的中断经框架 checkpointer 冒泡到 host、与主控走同一评审管线（03 §5.4），实施前**优先核验**。
- **单一内容路由的并发（本文 §5 设计 7）**：基线快照与整章 diff 取自同一路由；与外部修改、自动保存的并发处理沿用现有保存管线的约束（并发导致长度为 0 文件等问题已在现有保存管线处理），实施阶段核验对接点。

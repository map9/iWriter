# AI小说创作伙伴：重构设计

> 本文档是对现有 `design/creativeagent/` 实现的重构设计，起点是《正式需求与设计前置约束》（同目录下），而不是现有实现本身——现有代码只在每个设计点上被单独核验是否真的复用得上。本文档记录的是多轮讨论后的最终结论；讨论过程与历次修订请查 git 历史（`git log -- "design/creativeagent phase 2/AI小说创作伙伴：重构设计.md"`），文档正文不再用 v1/v2/v3 这类内部版本标签自我指代。

---

## 0. 从新需求倒推：这次要解决的是什么

《正式需求与设计前置约束》把系统重新定义为"面向小说创作工程的通用 Agent 框架"，核心是三层设计（通用内核 / 适配层 / 任务层）+ 三层架构（主控 Agent / 通用能力层 / 可组装子 Agent）+ 三层控制面（Prompt / Skills / Workflow）。这三组"三层"是同一个系统的三个切面：

- **通用内核**回答"工作对象是什么、怎么装配上下文、怎么定责任边界"——落地为第 1 节的对象模型；
- **三层架构**回答"谁来执行"——落地为第 3 节的 Agent 重新设计；
- **三层控制面**回答"复杂度放在哪"——落地为第 5 节的工具最小化设计。

下面各节按"先从需求推导应该是什么样 → 再核验现有代码哪部分能直接用、哪部分要改、哪部分要砍"的顺序展开。两个先于设计的事实纠正（影响多处判断）：

1. **Skills 不是空目录，是已有 29 个真实 `SKILL.md` 文件**（`electron/ai/builtin-skills/creative/{common,main,consistency,planner,writer}/*/SKILL.md`）。内容质量整体不差，真正的问题是：①从未做过埋点验证（issues#7）；②个别条目内容本身有害——`creative/writer/information-density/SKILL.md` 明文要求"每个句子至少同时做两件事"，与 issues#4"每一个字都很设计、肤浅、形式化"是直接因果关系。
2. **`writer.ts` 当前系统提示词仍然写着**"Execute the approvedPlan ... precisely. Do not improvise plot changes, character decisions, or structural deviations."——这是 issues#2/#3/#4 的直接代码证据，不是已经修复的历史遗留（第 6 节）。

## 1. 对象模型与工程空间（通用内核）

### 1.1 目录与对象映射

```
{workspace}/
  project.md                  # 作品对象：身份信息 + 当前版本字段（第 4 节）
  status.md                   # 过程对象：agent 维护的动态状态快照（原 storybible.md，见 1.6）
  setting/
    world.md                  # 设定对象（默认单文件，规模增长后按主题拆分）
  characters/
    {slug}.md                 # 重要角色个人档案
    _minor-cast.md            # 次要角色合集
  outline/
    masterplan.md             # 结构对象：总纲（含"章节顺序"字段，见 1.4/5.4）
    vol{N}.md                 # 结构对象：卷纲（可选层，见 1.3）
    ch{NN}-outline.md         # 结构对象：章纲（场景列表，见 1.3/1.4）
  draft/
    ch{NN}.md                 # 正文对象，内含 beat 哨兵（见 1.3）
    fragments.md               # 素材对象（见 1.4）
  process/
    open-questions.md         # 过程对象：待解决问题
    changelog/
      v{version}.md            # 过程对象：版本说明归档
  exploration/                 # 候选方案区（纯目录约定，见 5.5，不需要专用工具）
  .iwriter/
    session.json               # 仅一份状态：{ lastSessionEndedAt, knownPaths }，host 侧用，不是数据库（见 5.6）
  .git/
```

### 1.2 为什么大纲不能只有"一句话核心情节"

小说/剧本写作方法论里，**场景（scene）是相对题材中立、已被广泛验证的最小叙事单元**，结构是三段式：

- **目标（Goal）**：场景内 POV 角色这一刻具体想要什么——必须具体到"能判断是否达成"，不能是"想变强"这种抽象欲望。
- **冲突/阻碍（Conflict）**：谁、什么、何种处境阻止了这个目标。没有冲突，场景就是流水账。
- **结果（Outcome）**：经典三种出口——目标达成但代价更大／目标未达成／目标达成但揭示了新问题。**结果不能是"顺利达成"**，顺利达成意味着这个场景对故事没有推进力，应该被精简或删除。

这套结构现有代码里已有雏形（`electron/ai/builtin-skills/creative/common/scene-structure/SKILL.md`"目标→冲突→转折"），只是此前的设计没有把它真正落到大纲对象的字段里——大纲字段是按直觉拍的，不是按已经存在于代码里的方法论设计的。本版纠正这个错位：**章纲的核心字段就是场景列表，每个场景按上述三段式填**，不是一句话。

新需求 §1 的流程表本身写了"大纲分层：根据创作需求搭建粗纲/分卷大纲/章节细纲"——"分卷大纲"是此前设计完全遗漏的一层，本版补上（1.3 节）。

### 1.3 结构层完整层级关系

```
outline/masterplan.md          总纲：结构节点 + 主题落点 + 人物弧光交汇 + 伏笔总表 + 章节顺序
  └─ outline/vol{N}.md         卷纲（可选）：本卷大事件序列
       └─ outline/ch{NN}-outline.md   章纲：场景列表（每场景 目标-冲突-结果）
            └─ draft/ch{NN}.md 内的 beat 哨兵   场景内节拍
                 └─ beat 统辖的正文区间          正文本身
```

beat 哨兵格式：`> [场景2-节拍3] 一句话提纲`，紧跟其统辖的正文段，回指章纲的场景序号。一个场景在正文里通常展开为 2~5 个 beat。

"调整情节"= 编辑某一层、向上/向下冒泡：改一个 beat → Writer 只重写该 beat 统辖区间；某场景的目标/冲突/结果改变 → 提示是否需要重写该场景对应的全部 beat；章纲改动影响主线 → 提示是否需要调整卷纲/总纲。冒泡是**提示**，不是自动连锁修改（新需求 §4.10：变更传播是需要被显式分析、说明和确认的工程行为，不是刚性状态机）。

反向生成（从已有正文提炼章纲/总纲）有了明确写入目标：从 `draft/ch03.md` 提炼 → 写入 `outline/ch03-outline.md`；多章模式归纳 → 写入/校正 `outline/masterplan.md`。

是否启用卷纲层：篇幅规划预估达到一定规模（如 ≥ 20 章，或作者明确说明是分卷连载题材）时启用；中短篇作品章纲直接挂在总纲下，不强制要求卷纲文件存在。

章节文件之间的**故事顺序**由 `masterplan.md` 的"章节顺序"字段权威记录，**不由文件名编号维护**（5.4 节说明原因）。

### 1.4 各对象文档详细字段定义

字段是"必须有"的下限，agent 可以视项目情况增补，但缺这些字段视为对象未建立完整。

#### `project.md`（作品对象，单文件，全程仅一份）

| 字段 | 怎么填 |
|---|---|
| 书名 | |
| 题材/标签 | 自由文本标签，不限定枚举（题材是适配层维度，通用内核不预设题材分类） |
| 故事核心句 | **不是随意一句话**，必须包含四要素：主角是谁、目标是什么、核心阻碍是什么、赌注（失败的代价）是什么。例：「退伍老兵阿坤想找回失踪的女儿，但唯一线索指向他曾经背叛过的黑帮，一旦重新接触就可能连累现在的家庭。」 |
| 主题 | 一句话哲学命题（如"复仇是否值得付出和解的代价"），不要求文学化措辞，要求清楚 |
| 读者承诺 | 这本书向读者承诺的核心体验（爽感/悬疑解谜/情感共鸣等），全书不应违背 |
| 目标读者 | |
| 篇幅规划 | 预估总字数/章节数量级，决定是否启用卷纲层（1.3 节） |
| 当前版本 | 形如 `1.2（初稿补写中）`，语义见第 4 节 |

#### `status.md`（过程对象，动态状态快照，原 storybible.md，见 1.6）

| 字段 | 怎么填 |
|---|---|
| 当前进度 | 写到第几章、最近一次写作动作 |
| 角色状态摘要 | 每个重要角色当前所处弧光阶段的一句话摘要，详情指向 `characters/{slug}.md` |
| 开放伏笔摘要 | 指向 `outline/masterplan.md` 伏笔总表里尚未回收的条目 |
| 写作约束摘要 | 视角/时态/基调，从 `setting/world.md` 与已确认章纲提炼，不重复定义 |
| 待解决摘要 | 指向 `process/open-questions.md` 中状态为"待决策"的条目 |

`status.md` 不是数据源，是**全部由 agent 生成的派生摘要**，目标 2000-4000 token，每次重建都是"重新读取其余对象文件、重新生成"。不存在"作者直接编辑 `status.md` 来改设定"这种用法——作者要改设定，改 `setting/world.md` 本身。

#### `setting/world.md`（设定对象）

| 字段 | 怎么填 |
|---|---|
| 时代背景 | |
| 规则体系 | 题材相关：magic system / 科技水平 / 社会运作规则，要求写到"这条规则在什么情况下会被测试/违反会怎样"，不是纯背景介绍 |
| 阵营与势力 | 每个阵营的诉求、与主角的关系 |
| 地理信息 | |
| 历史沿革 | |
| 名词体系 | 专有名词统一表：人名/地名/机构名的标准写法一栏，供精修期检查统一性时直接比对 |
| 禁区 | 绝对不能出现的设定矛盾，**必须写明原因**（不是只列"不能做 X"，要写"因为 X 会破坏 Y 设定的根基"） |

规模增长后可拆分为 `setting/world.md`（规则/时代/历史）+ `setting/factions.md`（阵营/地理），拆分时机由 agent 判断（参照"够用就不拆"原则），不强制预先拆分。

#### `characters/{slug}.md`（重要角色个人档案）

| 字段 | 怎么填 |
|---|---|
| 姓名/别名 | |
| 外显特征 | 年龄、身体状态、阶层、职业、语域——这些字段是 issues#3 常识问题的直接解法：角色的移动速度、情绪外露程度、说话方式都应能从这组字段机械推导，不是事后核查清单。例：「62 岁，膝关节有旧伤，退休码头工人，习惯用身体经验而非数据说话」直接限定了这个角色不会健步如飞、不会用书面语吵架 |
| 核心欲望/核心恐惧/虚假信念 | 心理三角，首次建档强制要求三项齐全。虚假信念要求是"可被推翻的错误认知"而不是性格标签——例：「他相信展现脆弱等于失去尊重」是虚假信念，"他很骄傲"不是 |
| 成长弧光 | 初始状态 → 目标状态 → 当前阶段，要求三段都填，不能只填"当前阶段" |
| 关系网络 | 与其他角色的关系，双向标注（A 对 B 的认知 ≠ B 对 A 的认知，这种不对称往往是冲突来源） |
| 声音特征 | 词汇选择/语速节奏/惯常沉默点，直接供 `character-voice` skill 引用 |
| 当前状态 | 随故事推进更新 |
| 出场章节索引 | 列出出场章节文件名 |

#### `characters/_minor-cast.md`（次要角色合集，单文件多条目）

| 字段 | 怎么填 |
|---|---|
| 姓名 | |
| 功能定位 | 信使/路人/反派打手/导师，一词 |
| 与主角关系 | 一句话 |
| 显著特征 | 1-2 句，够 Writer 区分声音即可 |
| 升级标记 | 是否已触发"建议升级为独立档案"（规则见 1.5 节） |

#### `outline/masterplan.md`（总纲，单文件，全程仅一份）

| 字段 | 怎么填 |
|---|---|
| 故事核心句 | 与 `project.md` 一致，此处可展开为 2-3 句 |
| 主题落点 | 主题如何具体化为情节事件——不是抽象命题，是"通过哪几个具体情节让读者感受到主题"，每个落点指向大致结构节点 |
| 结构节点 | **默认 8 个题材中立的占位节点**（可按题材/篇幅调整数量与命名，但"该有节点"不能省）：开篇钩子 / 激励事件 / 早期试炼 / 中点转折 / 危机加深 / 至暗时刻 / 高潮 / 结局余波。每节点填：发生什么（具体事件，不是阶段描述）、大致章节区间、关键到哪条人物弧光 |
| 人物弧光交汇点 | 列出主要角色的弧光在哪些结构节点彼此交汇/冲突，把"角色对象"与"结构对象"显式关联 |
| 卷纲索引 | 若启用卷纲层，列出各卷目标并指向 `vol{N}.md`；否则留空 |
| 伏笔总表 | 表格：伏笔内容 / 埋设章节 / 回收章节 / 所属结构节点 / 状态（待埋设/已埋设/已回收） |
| 候选方向记录 | 若主线仍有未收敛的方向，标注"候选"并指向 `exploration/` 中对应文件 |
| 章节顺序 | 按故事顺序排列的章节文件名列表，如 `["ch01.md","ch02.md","ch03b.md","ch03.md","ch04.md"]`。这是章节故事顺序的**唯一权威记录**，文件名本身不再需要保持连续无缺口（5.4 节） |

**示例片段：**

```markdown
## 结构节点

### 激励事件
阿坤收到一张匿名照片，照片里的女孩侧脸与失踪的女儿有六成相似。
章节区间：ch02-ch03
关键人物弧光：阿坤（从"已放下"到"重新被钩住"）
```

#### `outline/vol{N}.md`（卷纲，可选层）

| 字段 | 怎么填 |
|---|---|
| 本卷结构功能 | 对应 `masterplan.md` 哪些结构节点落在本卷 |
| 本卷核心冲突来源 | 本卷阶段性的主要阻碍/反派/危机 |
| 大事件序列 | 表格：大事件 / 大致章节区间，粒度介于结构节点和章纲场景之间 |
| 本卷高潮与收尾 | |
| 卷末角色状态变化 | |
| 衔接 | 与上一卷承接点、给下一卷的铺垫 |

#### `outline/ch{NN}-outline.md`（章纲，提纲价值的关键载体）

| 字段 | 怎么填 |
|---|---|
| 本章结构功能 | 对应 `masterplan.md`/`vol{N}.md` 的哪个结构节点或大事件 |
| **场景列表**（核心字段） | 见下表，一章通常 1-3 个场景 |
| 本章伏笔操作 | 逐条对应总纲伏笔总表条目，标注本章是"埋设/强化/回收"哪一条 |
| 开篇钩子/结尾悬念 | 章节首尾的吸引力设计 |
| 字数预估 | |
| 衔接 | 与上一章衔接点、给下一章的过渡铺垫 |
| 状态 | 草稿中 / 已确认——对应新需求 §4.5"候选 vs 已确认前提" |

**场景列表字段（每个场景一段）：**

| 子字段 | 怎么填 |
|---|---|
| 场景序号 | 用于 beat 哨兵回指，如"场景 1" |
| 地点/时间 | |
| 出场人物（含 POV） | 若全书用多视角叙事，必须标明本场景的 POV 角色 |
| 目标（Goal） | POV 角色这一刻具体想要什么，要求可验证是否达成，不能是抽象欲望 |
| 冲突/阻碍（Conflict） | 谁/什么阻止了目标 |
| 结果（Outcome） | 必须是"达成但代价更大／未达成／达成但揭示新问题"三选一，**不能是顺利达成**——若确实顺利达成，说明这个场景该被精简或合并 |
| 情绪基调/节奏 | 快/慢、紧张/舒缓，供 `pacing-control` skill 参考 |
| 信息释放 | 本场景向读者揭示什么新信息、对谁仍隐藏什么 |

**示例片段：**

```markdown
## 场景列表

### 场景 1
地点/时间：码头仓库，深夜
出场人物：阿坤（POV）、老周
目标：阿坤想让老周说出照片的来源
冲突：老周欠阿坤的人情已经还清，不愿意再卷入
结果：老周说出来源，但代价是要阿坤帮他做一件违法的事——交换条件让阿坤的处境更复杂
情绪基调：压抑，对话为主，节奏慢但张力累积
信息释放：揭示照片来源指向阿坤曾背叛过的黑帮；对读者隐藏老周自己也欠那个黑帮的债
```

这样的章纲才有"提纲的价值"——Writer 拿到这份提纲可以直接知道该写什么对话、什么转折，而不是面对一句"阿坤去找老周问线索"自己现编冲突和结果。

#### `draft/ch{NN}.md`（正文，每章一份）

beat 哨兵 `> [场景N-节拍M] 一句话提纲`，紧跟其统辖的正文段，回指章纲的场景序号（1.3 节）。

| 影响范围 | 涉及哪些对象文件/章节 |

#### `fragments.md`（素材对象，单文件，多条目）

新需求 §9.1 把碎片明确为"一句对话、一个场景念头、一个人物细节、一个伏笔想法"——这几类东西的归宿完全不同（人物细节该并入角色档案，伏笔想法该并入总纲伏笔总表，场景念头该并入某章场景列表），fragments 不应该是这些东西的终点，而是**捕获区 + 路由前的暂存区**。

| 字段 | 怎么填 |
|---|---|
| 原始内容 | 一句话/几个词/情绪/问题，**不强制作者分类**——零摩擦记录是核心价值，分类是 agent 事后做的事 |
| 类型 | agent 识别后标注：场景念头 / 对话片段 / 人物细节 / 伏笔想法 / 情绪意象 / 调研笔记 / 未分类 |
| 记录时间 | |
| 关联线索 | 可能关联的角色/章节/结构节点，agent 识别后填，不要求作者主动说明 |
| 采用状态 | 未采用 / 已采用 |
| 采用去向 | 已采用时记录被并入了哪个对象文件（如"并入 `characters/老周.md` 的外显特征"），与 open-question 的"解决后归档去向"是同一个设计模式：任何"暂存态"对象都要能追溯最终去了哪 |

agent 不要求作者在记录时分类，但在合适时机（如下次涉及相关对象的任务）主动提议"这条碎片要不要并入 XX"，由作者决定是否采纳。

### 1.5 角色文件粒度规则

- **触发独立建档**（满足任一条件即可）：① 该角色在第 2 个不同章节中出现实质性动作/对话（不只是被提及）；② 作者明确指定该角色重要；③ 该角色承担一条独立副线。
- **人数豁免阈值**：当前"重要角色"总量（已独立建档 + 已满足升级条件待处理）**≤ 5** 时，允许继续维持合并状态；超过 5 后，新触发升级条件的角色强制走一次升格审批（作者可拒绝，拒绝后留在合集里但保留升级标记，下次再问）。5 是初始可调阈值，写入 `project.md` 或设置项，允许作者调整。
- **合集内容溢出信号**：`_minor-cast.md` 中某条目内容超过 3-4 句时，agent 应主动提议升级。
- **不做自动降级**：独立档案降级回合集是低频操作，不提供专门工具，按作者指示走普通文件操作（删除/合并）即可。

### 1.6 `storybible.md` → `status.md`：不只是改名，是重新定位

`storybible.md` 这个名字暗示"权威圣经/数据源"，与它实际定位（动态状态快照，不是数据源）矛盾，容易让未来开发者误判其权威性。本版把它正名为 `status.md`，与 `project.md` 明确分工：

- `project.md` = **身份信息**，几乎不变（书名/主题/读者承诺/篇幅规划），改动频率低；
- `status.md` = **状态快照**，随写作推进频繁重建，是 agent 派生产物，作者可读但不应该把它当成编辑设定的入口。

迁移：现有项目的 `storybible.md` 直接重命名为 `status.md`，内容结构基本不变（已经是摘要性质）。

### 1.7 对象间引用索引——不做 wiki 化，做隐形的 agent 侧引用索引

讨论起点：构思模式下的对象（`setting/`/`characters/`/`outline/`）是否该采用 wiki 式组织（`[[链接]]`、反向链接、graph view）。结论：**不做**：

- 角色/设定规模本来就小（1.5 节的 5 人豁免阈值已经把"重要对象"控制在个位数），文件树直接点开即可定位，wiki 式关联浏览/graph view 在这个规模上收益有限；
- 强迫作者书写 `[[...]]` 本身就是一种"系统内部技术概念暴露"，与 `01_需求定义.md` §6"不向作者暴露系统内部的技术概念"直接冲突。

但 wiki 机制里真正有价值的部分——**精确的反向引用**——值得单独留下，做成一个对作者完全隐形的 agent 侧能力：agent 已经知道全部对象名称（`characters/`/`setting/` 下的标题），扫描任意 markdown 文档的纯文本、匹配这些已知名称出现的位置，就能得到"谁提到了谁"的精确对照表——**不需要作者写任何特殊语法，纯 prose 即可被索引**。

用途：① 高风险操作的影响面分析（第 7 节）；② "我在哪些章节提到过这个角色/这条设定"的检索需求。落地为工具 `find_references(name)`（5.2 节），基于现有 `DocumentSearch` 能力做精确名称匹配，不需要维护持久化索引表。

## 2. 模式判定机制（构思 / 写稿）

判定信号：

| 信号类别 | 来源 | 示例 |
|---|---|---|
| 工程状态信号 | 版本语义（第 4 节）+ 当前操作对象类别 | 0.x → 倾向构思；目标是 `outline/*.md` → 倾向构思；目标是 `draft/ch*.md` → 倾向写稿 |
| 任务意图信号 | 用户动词 | "发散/设定/大纲/方案比较" → 构思；"写/改写/续写/润色" → 写稿 |
| 风险信号 | 改动是否直接落盘为正式对象 | 候选生成 → 构思（落 `exploration/`）；正式改稿 → 写稿（落正式对象） |

**对象类别判定不需要工具**：路径前缀本身就说明类别（`setting/`→设定、`characters/`→角色、`outline/`→结构、`draft/`→正文），这是一行字符串判断，模型自己读路径就知道，没有必要包装成一次工具调用。信号不足时按新需求 §3.3 做最小化澄清。

候选方案处理：构思模式产出统一写入 `exploration/`（覆盖范围从"仅正文方向探索"扩大到设定/大纲候选），作者明确选定后才晋升为正式对象（5.5 节，纯目录约定，不需要专用工具）——这是新需求 §4.5"候选不能被默认当作正式结论"的直接落地。

## 3. Agent 架构：固定子 Agent 花名册

主控 Agent 唯一对话入口，负责任务/模式判定、上下文装配、结果收束。通用能力层（第 5 节）不是 agent，是共享函数/工具。固定子 Agent 按新需求 §7.7 判据（跨项目高频、工具链稳定、I/O 边界清楚、值得独立监控复用）裁决为 **5 组（6 实体）**：

| 角色 | 裁决 | 理由 |
|---|---|---|
| Researcher | 保留 | 通用研究，边界清楚，直接服务 issues#3 常识问题（时代/职业/阶层细节查证） |
| Explorer（吸纳原 Advisor） | 保留，扩大职责 | Advisor 的核心能力（生成多方向、不评判优劣、交还选择权）与 Explorer 结构相同，区别只是触发时机（被动求助 vs plan 前主动渗透检查）。合并后覆盖：方向对比 + plan 前主动渗透 + 前期筹备阶段的多版开篇试写 |
| ConsistencyChecker | 保留，扩展为单章 + 全稿宏观两种模式 | 检查类，独立上下文避免确认偏差，触发改为可控（issues#6），不再写完自动强制 |
| Writer | 保留，约束重写 | 正文执行高频、工具链稳定。当前"精确执行计划、禁止即兴"的约束必须删除（第 6 节） |
| WritingStyleExtractor + WritingStyleSkillCreator | 保留（配对） | 风格提取 → 固化为 skill 的流水线，边界清楚 |
| Planner | **取消** | 见下方专项论证 |

#### 为什么取消 Planner

1. **新需求把"规划"拆成了两类性质不同的工作**：构思模式下的总纲/章纲生成属于"结构对象产出"（应该直接落 `outline/*.md`，走章纲层的确认机制，不是审批后即弃的临时 plan）；写稿模式下的"写前意图确认"是轻量的（不需要独立长上下文 agent）。用一个统一的重型 Planner sub-agent 处理这两类工作，是用同一个工具解决两个不同问题。
2. **"plan → execute → audit" 是工程师 Agent 范式**，把"结构化纪律"强加给了本该交给 Writer 自主处理的"生成与声音"层。取消 Planner 后，逻辑/常识校验下沉为 ConsistencyChecker 的检查维度之一，从"写前强制审"变成"写后查 + 可选写前查"，与 issues#6 方向一致。
3. **逐句深层 schema 本身就是 issues#1"非常细致的 json 结构输出"问题的来源之一**。取消 Planner 后，`confirm_writing_plan` 的 schema 可以简化为 `{plan, rationale, alternatives?}`，不再有深层嵌套的逻辑审计结构。

**统一调用机制**：以上全部固定子 Agent，一律经 deepagents 原生 `task(subagent_type, description)` 调用——**不为任何一个 sub-agent 单独包一层工具**。`task` 本身是通用能力层的一部分，不是 creative 专属。

是否需要新角色（如"题材专项审校 Agent"/"设定冲突排查 Agent"）：不需要，这类能力按新需求 §7.7 属于"动态组装"候选，落地为 skill（如 `genre-conventions`），按需被现有固定子 Agent 装配，不新增角色。

## 4. 版本语义

`project.md` 的"当前版本"字段（形如 `1.2（初稿补写中）`）是版本语义的唯一载体，用普通的 `edit_block` 编辑即可——不需要专用工具，也不需要数据库表来缓存（这是过早优化：`git_log`/`git_tag` 本身就是廉价操作，不值得为此另建一份缓存状态）。

版本号语义沿用新需求 §4.4 的约定：0.x = 仍处于构思打底、设定收敛和大纲成形阶段；1.0 = 第一次形成可通读全稿；1.x = 完整初稿基础上的补写/局部改写/问题修补；2.x = 完成一轮大修后的稳定版本；3.x = 精修后的稳定版本。真正的版本固化交给 git tag（已有工具），二者不强制同步，不一致时提示不覆盖。

## 5. 工具清单：彻底的最小化审查

### 5.1 审查方法

对每个候选工具问：**"这是不是只是'对一个已知 markdown 文档做读/写'，或者只是'调用一个已经存在的 sub-agent'？"** 如果是，已有机制——`DocumentTools`（读）、`EditProposalTools`（写：`edit_block`/`insert_block`/`delete_block`/`replace_range`/`create_document`）、`FilesystemMutationTools`（`delete_file`/`rename_file`/`move_file`）、deepagents 原生 `task`——已经覆盖，不需要专用工具。只有满足以下任一条件才保留专用工具：

- (a) 需要跨多个对象做精确匹配/聚合，且这件事不需要 LLM 推理，专用工具比让模型自己拼搜索逻辑更可靠；
- (b) 必须保证模型真的会停下来等待结构化决策，纯对话文本做不到这一点。

旧版本里"creative 特有工作流状态""文件系统级操作"这两类曾被当作独立的保留理由，重新核查后发现都能用"目录在哪"或"调用哪个工具/sub-agent"表达，不需要单列。

历史教训：`storybible.md` 单文件、非结构化大文本黑盒的旧模型，逼出了大量专用解析/patch 工具（比如曾经存在过的、专门从一段大文本里解析多个角色心理三角的工具，因为标题层级和装饰符号漂移而出过 bug）。对象拆分之后，这类专用解析逻辑的存在理由本身就消失了——角色已经是独立文件，要读心理三角直接用 `get_section` 即可。

### 5.2 最终保留的 creative 专用工具：2 个

| 工具 | 保留理由 |
|---|---|
| `find_references(name)` | 1.7 节：精确名称匹配是纯字符串操作，不需要也不该交给 LLM 推理，专用工具更快更可靠 |
| `confirm_writing_plan(plan, rationale, alternatives?)` | 见下方说明 |

**为什么 `confirm_writing_plan` 仍然需要是一个工具，而不是"agent 把计划说出来，作者回复继续"**：纯对话式的"输出计划文本，等用户说继续"无法保证模型真的会停下来等待——模型可能在同一轮或紧接着的下一轮就直接开始调用写入工具，UI 上也没有办法把"这是一个需要决策的审批点"和"这是一句普通的聊天"区分开。`confirm_writing_plan` 利用 deepagents 的 `interruptOn` 机制是目前能够**保证暂停**的唯一方式。

但它的使用应该是**有条件的**，不是任何写作任务都强制先过一遍：新场景/新章节、超过一段的改写、涉及已确认设定的修改、结构性调整，才需要先过 `confirm_writing_plan`；局部润色、小范围直接修订应该跳过这一步，直接进入块级编辑 + 章节级审批（第 7 节）。理由是 plan-first 的真实价值是"避免在错误理解下浪费一整段写作精力"，这个价值只在"写错了代价高"的任务上成立，小修改本身重写代价就很低，不需要这道额外的关卡。

### 5.3 被取消的工具及替代方式

| 候选工具 | 替代方式 |
|---|---|
| 章节槎位管理（列出/创建/删除/重命名/重排章节文件） | 见 5.4：通用文件工具 + `masterplan.md` 的"章节顺序"字段 |
| 会话间 diff 感知 | host 侧（主进程/orchestrator）每次会话启动自动计算并注入上下文，不是 agent 可调用工具——这件事每次都该自动做，不需要模型决定"要不要查一下" |
| StoryBible/status 过期提示 | host 侧自动比较各对象文件 mtime 与 `status.md` 自身 mtime，过期则在上下文里提一句，不是工具 |
| 对象类别分类 | 折叠进 prompt：路径前缀本身说明对象类别，模型自己判断即可 |
| 版本声明 | 就是编辑 `project.md`"当前版本"字段的一次普通 `edit_block`，不需要专用工具 |
| 对象文件懒创建（带默认模板） | 就是 `create_document`（已有），模板内容放在 prompt/skill 里 |
| 候选区全套工作流工具（开始探索/写候选稿/完成探索/晋升/列出/读取/删除候选） | 见 5.5：全部折叠进"目录约定 + 已有通用工具" |
| 一致性检查触发 | `task(subagent_type='consistency_checker', description=<brief>)`，与调用其余固定子 Agent 完全一样，不单独包工具 |
| 顾问方向建议 / 全稿架构分析 | 前者并入 Explorer 的 `task` brief 参数；后者归入 ConsistencyChecker 的全稿宏观模式 brief |

### 5.4 章节管理：通用工具 + 一个排序字段，取代级联重命名

不再维护"文件名必须是连续无缺口的 ch01/ch02/ch03"这个不变量——维护它需要多文件原子重命名（脆弱），现在每章还配了一份 `outline/ch{NN}-outline.md`，级联重命名必须同时维护两个文件同步改名，复杂度只会更高：

- **章节创建** = `create_document`，文件名由 agent/作者随意决定（不要求紧跟序号，允许 `ch03b.md` 这种中间插入命名）；
- **章节删除** = `delete_file`（已有）；
- **章节改名** = `rename_file`（已有）；
- **章节顺序的权威记录** = `outline/masterplan.md` 的"章节顺序"字段（1.4 节），重新排序 = 编辑这一个列表里几行文字的顺序（一次 `edit_block`/`replace_range`），不需要重命名任何文件。

代价：文件名的字母序可能不再总是精确反映故事顺序（中途插入的 `ch03b.md` 在文件树里看起来不如严格连续编号直观）。这是一个**有意识接受的小代价**，换来的是不需要维护脆弱的多文件级联重命名机制，以及不需要让重命名逻辑感知配对的大纲文件。作者想整理文件名时，随时可以单独 `rename_file`，不需要系统自动级联。

### 5.5 候选区：纯目录约定，零专用工具

`exploration/` 与正式对象目录之间的全部区别，靠 prompt 表达：

- 构思模式下生成的候选内容，写入 `exploration/{方向名}.md`，用已有的 `create_document`；
- 比较多个候选方向，agent 直接在对话里描述差异（候选内容本身就是可以打开查看的普通文件，不需要专门的"比较报告"工具）；
- 作者选定方向后，"晋升"分两种情况：① 整篇替换正式对象 → `move_file`（已有）；② 合并进已有对象的一部分 → agent 读取候选文件内容（`get_blocks`），再用 `insert_block`/`edit_block` 把选中部分写入目标对象，与日常编辑没有区别；
- 放弃候选 → `delete_file`（已有）；
- 列出/查看现有候选 → 普通目录浏览 + `get_blocks`。

唯一可能需要的不是"工具"，而是**审批 UI 层的呈现优化**（比如把"晋升"动作渲染成 before/after 对比卡片）——这是展示层的事，不影响 agent 看到的工具协议。

### 5.6 `.iwriter/creative.db`（SQLite）整体取消

此前设想用 SQLite 承载会话日志、变更日志、版本状态三类数据，本节取消的工具一并带走了它们的写入方。剩下唯一真正需要持久化的是"上次会话结束的时间点 + 当时已知的文件列表"，用于 host 侧计算 diff。这点状态用 SQLite 已经是过度配置——改为一个极简 JSON 文件 `.iwriter/session.json`（`{ lastSessionEndedAt, knownPaths }`），host 侧用 `fs.stat` 逐个比较 mtime 即可判断新增/修改，已知路径列表消失即判断删除。不再需要数据库依赖，不再需要任何"表"的概念。

## 7. 审批与高风险操作分级

- **构思模式高风险**（错误决策风险）：`exploration/` 候选 → 正式对象的"晋升"动作必须显式审批，不能批量静默转正。
- **写稿模式高风险**（变更扩散风险）：跨章节重写、改动 `outline/masterplan.md`、改动已确认角色心理三角——审批卡片需要展示"影响面"，用 `find_references` 做精确名称匹配（不是关键字命中），接受同名歧义这类边界情况，不建完整依赖图谱。
- **一致性检查触发改为可控**（回应 issues#6）：默认不再"写完章节自动强制触发"，而是三种途径之一：①作者主动要求；②skill 驱动的自动化流程（章节级审批节点触发一次）；③字数变化超过阈值时，提示"建议做一次检查"，由作者决定是否执行。
- **章节级审批**（沿用已验证机制）：写作进行中的逐块编辑自动通过累积，章节完成时触发一次整章 diff 审批。

## 8. 数据与项目迁移

### 8.1 已有 iWriter 项目的迁移（懒迁移）

不提供一次性迁移工具。agent 下次操作某类对象且独立文件不存在时，从 `status.md`（先重命名）当前内容提炼初始版本创建独立文件。`outline/masterplan.md`/`vol{N}.md`/`ch{NN}-outline.md` 没有历史数据，可选择从已有正文反向提炼场景结构生成初始章纲。

### 8.2 已有小说的反向导入（独立场景，不是迁移的边角情况）

适用场景：作者带着一部已经写了一部分甚至已完结的小说进入系统——`draft/` 下有章节文件，但 `setting/`/`characters/`/`outline/` 全部空白或严重不完整，甚至连 `status.md` 都不存在。这是一个独立的首次导入场景，应该被显式支持。

**核心原则**：反向提炼出的全部内容（设定规则、角色心理三角、章纲场景列表、总纲结构节点）都是**agent 对既有正文的解读，不是作者确认过的事实**，必须先进 `exploration/` 候选区或在对象文件内标注"推断，待确认"状态，不能直接写成正式对象。这是第 2 节"构思/写稿模式"与"候选 vs 已确认"机制的一次反向应用：通常流程是"设定 → 情节 → 正文"，这里反过来"正文 → 提炼设定/情节 → 作者确认 → 再继续正向迭代"，机制不需要新发明，只是入口方向反了。

**触发条件**：agent 检测到 `draft/` 非空但 `setting/world.md`/`characters/`/`outline/masterplan.md` 缺失或明显单薄时，主动提议"要不要先帮你把现有设定理出来"，**不自动执行**。

**提炼范围**：

- **结构层**（置信度最高，建议优先做）：逐章读取正文 → 反推每章场景列表（目标-冲突-结果，既有正文本身已经体现了场景结构，这一步是"还原"不是"猜测"）→ 归纳总纲结构节点与伏笔总表。
- **角色层**：识别反复出场的人名 → 草拟角色档案，心理三角字段从行为证据推断，**标注"推断，待确认"**，作者审阅时直接采纳或修改。
- **设定层**：从正文里反复出现的规则/背景描述归纳 `setting/world.md` 草案。
- 不强求一次提炼完整：可以先只做结构层，角色/设定层视作者意愿再做。

**交付形式**：以一批可审批的候选提案呈现，作者逐项确认/修改/拒绝，不是一次性静默写入。确认后的内容才进入正式对象目录，后续按本文档其余章节定义的机制继续迭代。

## 10. 风险与未决问题

- **对象拆分粒度**：角色文件粒度规则已在 1.5 节给出具体阈值（5 人豁免、溢出信号），阈值是可调初始值，R2 落地时按实际项目反馈调整。
- **文件名字母序与故事顺序不一致**（5.4 节）：接受这个代价，权威顺序在 `masterplan.md`，不在文件名；若实测作者对文件树顺序的直觉依赖度很高，可再考虑加一个"按需整理文件名"的辅助操作，但不做成自动级联。
- **去数据库化是否会在后续阶段反悔**：若 R8 之后确实需要持久化更多结构化操作记录（如跨会话的 review 历史），到时候再引入数据库，不提前为"可能需要"预留。
- **`find_references` 的同名歧义**：不同对象重名时精确匹配会混淆，目前不做消歧，接受这个边界情况。
- **反向导入的提炼准确率**：心理三角从行为证据推断的可靠性未经验证，需要用真实外部小说样本验证，而不是只用自产的测试数据。
- **`fragments.md` 的类型识别准确率**：依赖 agent 自主判断，初期可能误判类型或漏掉"可并入"的提议时机，不建强规则，靠后续观察调整。
- **`process/changelog/` 与 `status.md` 归档摘要的关系**：二者都承担"版本/阶段性总结"语义，是否需要合并或明确分工，R7 实施时需要进一步明确，避免信息重复维护两份。

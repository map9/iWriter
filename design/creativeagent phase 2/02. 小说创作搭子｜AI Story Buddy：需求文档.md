# 小说创作搭子｜AI  Story Buddy：需求文档

> 本文档是小说创作搭子（`AI Story Buddy`）的正式需求文档：定义系统必须具备的能力与约束，回答"要做到什么"，不展开"怎么做"。实现方案见《03. 小说创作搭子｜AI  Story Buddy：概要设计》，该文档每一节都应能回溯到本文档的一条或多条需求编号（见 §8）。已知问题的原始记录见《A. 小说创作搭子｜AI  Story Buddy：问题清单》，本文档 §9 给出问题到需求的映射。

* * *

## 0. 文档迭代原则

- 需求与设计文档会持续修订；任何单一版本都不是终态。后续讨论可以整体推翻本文档任意具体条款，不视为"破坏已定稿内容"。
- 需求与设计不是单向推导关系：设计阶段发现需求表述不清、有遗漏或过度约束时，应回过头修改本需求文档，而不是把需求当作设计期间不可变更的输入——两者之间允许来回拉扯。
- `AI Story Buddy` 的定位（§1）本身不变，但定位之下的具体需求与设计条款都必须用业务场景校验（§10 场景清单），以避免遗漏正常场景，或设计出无法覆盖真实场景任务的方案。任何新增/调整的需求或设计条款，都应能说出它对应哪个场景、解决场景中的什么问题。
- **现存代码不作为需求与设计的依据。** 只有设计的主体逻辑（对象模型、模式判定、Agent 与工具边界等）已经从需求推导确定之后，才进入"如何利用/重构现有代码"这个单独的、后置的阶段。纯设计阶段（包括梳理需要哪些 skills、需要哪些固定执行体）不参考现有实现的具体代码、现有 skills 文件、现有 prompt 或现有工具命名作为设计输入——这些只在"重构落地"阶段被核验能否复用，不能反过来用它们的现状去定义或限定设计结论。

## 1. 背景与定位

小说创作搭子是 `AI Writing Buddy`（对应代码 Creative Domain）下的一个独立领域 Agent，陪伴作者完成从构思到定稿的小说创作。

它服务的对象不是一次性 prompt，而是一个由作品设定、人物、结构（大纲）、正文、过程记录与素材共同组成的**小说创作工程**。系统的定位是**作者主导下的协作型创作搭子**：Agent 可以广泛参与构思、整理、试写、续写、重构、审校、归档等环节，但不替代作者做方向、取舍与最终审批的决定。

演进方向上，系统可以从"高参与度协作"逐步发展出更高自主度的执行能力，但方向确认、关键取舍、版本批准与最终责任，应始终保留在创作者一侧。

## 2. 范围

### 2.1 覆盖的创作阶段

| 阶段 | 核心目标 | 关键产出类型 |
| --- | --- | --- |
| 一 前期筹备 | 选题、世界观、人物体系、分层大纲、开篇试写 | 设定集、人物卡、大纲、试写稿（定义类对象） |
| 二 初稿写作 | 按大纲落地为完整正文，不中断记录问题 | 分章初稿、问题批注（正文类对象） |
| 三 一轮大修 | 结构与剧情修改：节奏、逻辑、冲突、人物弧线 | 修订全文、结构调整说明 |
| 四 二轮精修 | 文字与细节打磨：语言、视角、统一性 | 精修全文、统一性规范表 |
| 五 三审定稿 | 冷处理、试读反馈、终审通读 | 终审定稿、配套归档资料 |

创作不是流水线：前两个阶段之间会反复拉扯调整，系统必须支持这种来回而不强迫线性推进（见 §4 FR-2）。

### 2.2 明确不覆盖

- 第六阶段（投稿/出版/发布收尾）不在本期范围内。
- 全自动无人值守创作、复杂多人协作与细颗粒度权限体系、可视化流程编排器、跨项目通用长期学习记忆系统、大规模自治多 Agent 协商网络（详见 §7.3）。

## 3. 核心概念

| 概念 | 定义 |
| --- | --- |
| 工程空间 | 承载一个小说项目全部对象的持久化工作区，人类可读可编辑可版本化 |
| 工作对象 | 工程空间中的一类结构化实体：作品、设定、角色、结构、正文、过程记录、素材 |
| 构思模式 | 面向创意、设定、人物、大纲等定义类对象的执行方式，重点是发散、比较、收敛 |
| 写稿模式 | 面向章节、场景、正文、修订稿等正文类对象的执行方式，重点是落地、续写、改写、审查 |
| 候选方案 / 已确认前提 | 候选是尚未被作者采纳的构思产出；已确认前提是作者认可、可作为后续写作依据的正式对象 |
| 高风险操作 | 影响面广、连锁反应强、验证成本高、可能破坏当前稳定版本或难以回滚的操作 |
| 版本/阶段语义 | 工程当前所处的成熟度（筹备中／已有可读全稿／大修后稳定／精修后稳定等） |
| 用户级协作记忆 | 某一 Agent/domain 与该作者协作时应遵守的协作规则、作者成熟度、干预强度、风险偏好与上下文恢复策略；跨项目生效；edit/creative 独立维护；不承载剧情事实或实时进度 |

## 4. 功能需求

每条需求给出编号与描述；关键需求附验收标准，验收标准描述"如何判断这条需求被满足"，不规定实现方式。

### FR-1 工作对象与工程空间

- **FR-1.1** 系统必须以一个持久化、人类可读可编辑的工程空间承载全部创作产物，而非零散文件或单次 prompt 上下文。
- **FR-1.2** 系统必须支持至少以下一级工作对象：作品、设定、角色、结构（大纲）、正文、过程记录（任务/审批意见/问题清单/版本记录）、素材。
- **FR-1.3** 对象之间必须具有可判定的依赖/引用关系（如角色约束正文、设定约束结构与正文），以支持后续的一致性检查与影响面分析。
- **FR-1.4** 系统必须能区分每类对象的维护责任（作者主导／agent 派生／两者皆可）与生效条件（是否需要作者确认）。

  验收：给定任意一个工作对象，能明确回答"谁能改它"与"改了它会影响谁"。

- **FR-1.5** 系统必须支持零摩擦的灵感碎片捕获：作者随手记录一句对话、一个念头时不强制分类；系统在后续处理相关任务时主动提议将碎片归入对应对象，采用与否由作者决定。
- **FR-1.6** 系统必须支持从零初始化一个新的小说工程：引导作者建立作品身份信息（故事核心句四要素——主角/目标/阻碍/赌注——必须成立）、必需对象骨架与版本基线；初始化必须经作者确认，不得静默执行。

### FR-2 执行模式判定（构思 / 写稿）

- **FR-2.1** 系统必须依据工程状态与用户意图自动判定进入构思模式还是写稿模式，不强制用户手动选择模式概念。
- **FR-2.2** 判定依据不足或信号冲突时，系统必须发起最小化澄清，不得默认选择风险更高的模式。
- **FR-2.3** 构思模式产出的内容，在作者明确确认前不得被当作已生效的正式结论使用；不同候选方案可并行存在，必须被显式区分。
- **FR-2.4** 写稿模式执行过程中若暴露出前提缺口（设定不稳、大纲无法支撑正文），系统必须能短暂切回构思模式补齐前提后再继续写稿。
- **FR-2.5** 作者显式指定模式或流程（如"进构思模式""直接写，别猜"）时，显式指定优先于自动判定，系统必须尊重并跳过相应判定环节；审批机制与安全红线不因显式指定而放宽。

  验收：给定一段用户输入和当前工程状态，能给出模式判定结果及依据；依据不足时能给出具体澄清问题而非静默假设。

### FR-3 上下文装配

- **FR-3.1** 系统必须依据当前任务与模式自动选取相关性最高的对象子集作为上下文，不得注入全部历史信息。
- **FR-3.2** 优先级规则：用户当前明确指令 > 已确认的正式对象 > 候选方案/历史版本；与当前任务局部相关的对象优先于全局弱相关信息。（放弃的候选不单列为"废弃草案"优先级层——放弃即删除，内容仅保留在 git 历史，需要时随历史版本一并恢复，工作区不常设保留废弃态。）
- **FR-3.3** 历史版本、废案与旧草稿默认不注入写稿模式上下文，仅在用户明确要求比较、回顾或恢复时引入。
- **FR-3.4** 已废弃对象若仍可被检索到，必须显式标注失效状态，防止被误引用为当前有效依据。
- **FR-3.5** 系统不得依赖会话启动时的全局扫描、全局 diff 或状态摘要重建来获得"当前状态"；必须优先依据当前任务按需读取相关对象，只有在比较、回退、断点恢复、高风险影响面分析或用户明确要求时，才扩大读取范围或引入版本信息。

### FR-4 内容生成与修改

- **FR-4.1** 系统必须支持围绕设定、人物、大纲、章节等对象的构思、扩写、续写、改写与润色能力。
- **FR-4.2** 任何正式变更都必须以可见的提案或差异形式交付，不得静默直接落地到正式对象。
- **FR-4.3** 创作者必须能够批准或拒绝任一正式变更提案；一批多个提案时可逐条决策（各自批准/拒绝）。不要求对单个聚合提案（如整章 diff）做逐块"局部采纳"——对散文，聚合改动内部往往叙事互依，部分挑选易破坏连贯性且无机制保证；"保留方向、定向修正"的诉求由整体保留 + 迭代修订（rework）满足，而非局部回退。
- **FR-4.4** 系统必须支持从作者提供的范文中提炼可复用的风格配置（声音、措辞、句法等），并在作者确认后于其指定范围内应用于写作与审校；提炼结果在作者确认前视为候选。

### FR-5 一致性检查与编辑评审

区分两类：**一致性（"对不对"）**——忠实度 + 硬一致（角色/世界规则/时间线/称谓/伏笔/关系），可客观勾检；**编辑评审（"好不好"）**——戏剧性、人物与声音、视角、行文、结构与节奏、主题、读者体验等craft 视角，是方向建议、需盲评。两者机制可共用，但产出与触发分开。

- **FR-5.1** 系统必须支持角色设定、世界规则、时间线、称谓、伏笔与关系推进的一致性检查能力（"对不对"）。
- **FR-5.2** 检查触发方式必须可控：由作者主动要求、由项目已启用的 skill/workflow 规则触发、或在满足显式提示条件（如字数变化超过阈值）时向作者建议触发。**不得对每次写作动作都强制自动触发一次全量检查**。
- **FR-5.3** 检查结果必须区分问题等级，并给出判断依据的对象与可执行的处理建议。
- **FR-5.4** 系统必须支持将作者提供的外部反馈（如试读意见）整理为分级问题清单，映射到具体对象/章节，供后续修订使用；系统不代作者裁决反馈本身是否正确。
- **FR-5.5** 系统必须提供**编辑"好不好"评审**能力（craft 视角，只给意见/方向、由 writer/作者自主取舍），有两种模式：**（模式A）随写随评**——写完一章后自动只做"好不好"评审并驱动一轮修订，意见临时、不入库、不做一致性；**（模式B）用户触发评审**——作者显式要求时做（可含一致性），结果落 `review-findings.md`。评审技能应完整覆盖视角但不堆砌细则（先给方向、信任模型能力）。
- **FR-5.6** 系统必须在**提交入库（commit）**时，若本次提交涉及"回头修改已定稿章节 / 结构重构 / 多章变更"之一，向作者**提醒**先做一致性检查（提醒非硬锁，作者可跳），建议范围为改动章及其影响面而非全书。

  验收：给定一次写作动作，能说明检查是否触发及由哪条途径触发；不存在对每次写作动作强制全量一致性检查的执行路径；模式A 的编辑意见不落 `review-findings.md`，仅模式B 落盘。

### FR-6 高风险操作与审批

- **FR-6.1** 系统必须能判定一个操作是否为高风险操作，判据至少包括：影响面广度、连锁反应强度、验证成本、是否破坏当前稳定版本、是否难以回滚。
- **FR-6.2** 高风险操作执行前，系统必须能展示受影响的对象/章节/版本范围，并说明修改理由。
- **FR-6.3** 高风险操作必须获得作者显式确认后才能落地；系统不得先写入再补救。
- **FR-6.4** 任何正式变更必须保留原版本，可生成前后差异说明，并支持回退到上一稳定版本。

  验收：给定一个操作，能依据 FR-6.1 判据说明其是否属于高风险；高风险操作在未获作者显式确认时不存在落地路径。

### FR-7 版本与阶段推进

- **FR-7.1** 系统必须能表达工程当前所处的成熟度，并据此影响模式判定与上下文装配策略，但不得实现为僵化的状态机式流程开关。
- **FR-7.2** 版本/阶段推进必须依据成果物是否已"闭合"判断（如主题明确、核心设定基本稳定、主要人物可支撑主线、存在至少一版可写大纲），而非按固定步骤强制切换。

### FR-8 失败与恢复

- **FR-8.1** 系统在判断、生成、修改或上下文装配出现问题时，问题必须能被发现、保留现场，并向作者暴露差异。
- **FR-8.2** 创作者必须能在任意执行环节中断当前自动流程，改为手动接管。

### FR-9 Skills 与 Workflow 可扩展性

- **FR-9.1** 系统必须提供覆盖多数项目的默认工作流。
- **FR-9.2** 系统必须允许作者通过 skills 覆盖或补充默认工作流的局部步骤，不需要修改核心逻辑。
- **FR-9.3** 多个 skills/workflow 规则同时生效发生冲突时，系统必须有可预期的优先级裁决顺序。

### FR-10 策略适配（作品上下文 / 交互协作偏好）

- **FR-10.1** 系统必须区分两类适配维度：题材、作品风格、设定约束、读者承诺等属于作品上下文，影响创作内容；作者成熟度、干预强度、风险偏好等属于交互协作偏好，影响解释深度、澄清频率、提案颗粒度与风险提示方式。
- **FR-10.2** 作品上下文维度写入作品对象、风格配置对象与其他正式对象，作为内容生成和审校依据；交互协作维度必须写入用户级（作者级）协作记忆或当前任务上下文，**不得**作为作品事实写入作品对象。
- **FR-10.3** 这些差异必须表达为可配置、可从上下文推断的维度，**不得**写死为固定的产品分支或题材专属代码路径。

### FR-11 协作角色与权限

- **FR-11.1** 协作角色收敛为创作者与 Agent 两方；Agent 可参与任意环节，但任何正式变更的最终决定权在创作者。
- **FR-11.2** 出现方案/设定/版本/方向冲突时，Agent 必须整理冲突点、给出可比较方案与影响说明，不得替创作者裁决。

### FR-12 可观测性与解释义务

- **FR-12.1** 解释深度必须与操作的影响范围/风险等级匹配：局部低风险操作给出简要说明；跨对象或高风险操作必须说明依据对象、修改理由、影响面与待确认风险。

### FR-13 个性化记忆作用域

- **FR-13.1** 系统必须区分并独立管理三种作用域的记忆/配置：项目级（作品上下文配置，如题材、设定约束、文风配置，存在于工程空间的正式对象与项目级自定义 skills 中）、用户级/作者级（协作记忆：长期协作习惯与协作偏好，跨项目生效）、任务级（仅存在于当前上下文，不沉淀为长期记忆）。**不设项目级协作记忆**——协作规则不随单个工程存放。
- **FR-13.2** 用户级协作记忆只记录如何协作与如何恢复上下文，例如作者成熟度、干预强度、风险偏好、默认工作方式、上下文恢复策略；不得记录可从工程对象读取的剧情事实、当前进度、文件变更流水或未经确认的推断。
- **FR-13.3** 任务执行中探索到的剧情事实、设定推断、进度判断默认属于任务级上下文；只有在作者确认后，才能写入对应正式对象、候选区、素材或过程记录，**不得写入协作记忆**（本期协作记忆只读，见 FR-13.5）。
- **FR-13.4** 用户级协作记忆必须按 Agent/domain 隔离命名空间，不得共享单一记忆文件，也不得落入 agent 框架的默认记忆路径；具体路径约定由设计文档规定。
- **FR-13.5** 本期协作记忆为**只读装配**：系统在创建 agent 实例时按 domain 装配用户级协作记忆并注入上下文；不提供自动更新或任何 Agent 写入路径，记忆内容由作者手工维护。
- **FR-13.6** 记忆的自动沉淀与更新（何时写入、如何合并去重、边界过滤、是否需要审批）属于整体记忆系统设计，本期不实现，延后统一考虑。

  验收：给定任意一条记忆/配置信息，能明确回答其作用域归属（项目级作品上下文／用户级协作记忆／任务级）与存放位置；运行期间协作记忆文件内容不被 Agent 修改。

### FR-14 已有作品导入（物理导入 + 反向提炼）

- **FR-14.1** 系统必须支持导入一部已存在（部分或全部完成）的小说，在设定/人物/大纲对象缺失或不完整时，从既有正文反向提炼候选设定、人物、大纲。
- **FR-14.2** 反向提炼的内容在作者确认前必须被视为候选/推断内容，不得直接写为**已确认**正式对象。落点按对象类型分流：**有 status 字段的对象（大纲）**可直接写入 `outline/` 并标 `status: 草稿中`（该字段即"候选/待确认"的就地标记，下游须核对确认状态方可当作正式前提）；**无 status 字段的对象（设定/角色）**必须进 `exploration/` 候选区，作者确认后才晋升为正式对象。
- **FR-14.3** 系统必须支持整本单文件（txt/docx/md）的**物理导入**：格式归一为 markdown、识别章节边界（边界划分必须经作者确认后才执行拆分）、按章节命名约定拆分落盘到 `manuscript/`、剥离原格式噪声（页眉页脚、软换行等）；导入后的正文必须与原文逐字一致，导入过程不得改写内容。

### FR-15 资料查证

- **FR-15.1** 系统必须支持对现实细节与专业背景进行查证，结论必须区分"观察到的证据"与"解读"，并标注来源与置信度、暴露信息缺口。
- **FR-15.2** 查证产出属于**参考性中间产物**（落于会话级暂存区，非工作区候选对象），未经作者确认不得直接写入正式对象；要保留的结论由作者/主控提炼后另行写入。

## 5. 非功能需求

- **NFR-1 人类可读可编辑**：正式成果物应以可读、可编辑、可版本化的格式存在，创作者可随时手工修改任意对象。
- **NFR-2 可追溯**：每一次正式变更均可追踪、可解释、可比较、可回退。正式变更的可追溯粒度为**章级**——写作会话内自动累积的块级草稿不单独留痕，一章一次终审 + commit（见设计 §5.3 的"工作树草稿 vs 正式变更"边界）。
- **NFR-3 低打扰**：默认交互不应强迫作者学习或感知系统内部技术概念（如显式的模式名称、内部对象术语）。
- **NFR-4 内容一致性**：同一对象在编辑器打开与未打开两种状态下，读取与写入的行为与结果必须一致；编辑器缓冲与磁盘内容不得静默分叉。
- **NFR-5 规模边界**：设计基准为 25-35 万字 / 60-120 章的长篇（机械上限受章节命名约定 999 章约束）；核心交互（模式判定、单章写稿、局部审校）的响应与上下文成本不得随全稿规模增长（按需读取，不整稿装载）；全稿级任务（全稿审校、整本导入提炼）允许分批完成，不要求在单次会话内完成。

## 6. 验收标准与质量判断维度

不采用单一打分体系，按任务类型给出判断维度：

| 任务类型 | 关注维度 |
| --- | --- |
| 构思类 | 方向是否清晰、候选方案之间是否有区分度、是否已形成可写前提 |
| 设定类 | 规则是否闭合、人物动机是否成立、结构对象是否可支撑主线 |
| 写稿类 | 是否完成任务目标、是否符合当前设定与章纲、是否存在明显断裂 |
| 审校类 | 问题识别完整性、严重性分类是否合理、建议是否可执行 |

公共维度（适用于所有任务类型）：完整性、自洽性、一致性、可执行性、风险暴露程度、是否满足当前阶段目标。

执行方式：上述维度不做自动打分，以**固定样本工程上的对比评审**落实——对每类任务比较"未启用相关 skill 的基线"与"启用后"的产出，客观维度按清单勾检（schema 完整性、约定遵守、红线违反），主观维度（如行文自然度、"像不像人话"）由作者对两版本盲评；验证方案的完整设计由设计文档承载。

## 7. MVP 范围

### 7.1 目标

首版目标不是全自动创作，而是把"作者主导、Agent 协作、可见、可审、可回退"的核心协作闭环做扎实。

### 7.2 MVP 必须覆盖

- 读取并引用工程中的核心对象（FR-1）
- 构思模式与写稿模式的基本判定与切换（FR-2）
- 围绕设定、大纲、章节的协作：局部写作、改写、润色、review（FR-4、FR-5）
- 以提案/差异/候选结果形式交付正式修改（FR-4.2、FR-6）
- 基础版本比较、回退与变更说明（FR-6.4、FR-7）
- 默认工作流与基础 skills 的挂接（FR-9）
- 主控 Agent、少量固定子 Agent 与按条件动态组装能力的基本协同（设计见《03. 概要设计》）

### 7.3 MVP 明确不包含

- 从选题采集到完稿的全自动闭环
- 复杂多人协作与细颗粒度角色权限体系
- 高度复杂的可视化流程编排器
- 跨项目通用的长期记忆学习系统
- 大量高度自治、彼此长期协商的复杂多 Agent 网络
- 记忆系统的整体设计与自动沉淀/更新（本期用户级协作记忆仅只读装配，见 FR-13.5/13.6）

### 7.4 完成标志

- 作者可在一个工程中稳定完成从构思到正文修改的基础协作
- Agent 的工作依据来自工程上下文，而不只是单次 prompt
- 高风险修改不会无痕直接落地
- 正式结果可见、可批、可拒绝、可回退
- 系统具备向更复杂 skills、workflow 与多 Agent 协作扩展的稳定骨架

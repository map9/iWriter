# llm call · 章节连续性记忆（★四层记忆核心写侧）

## 概要
- **name**: `chapter.memory`
- **role**: 长篇小说的章节连续性记忆抽取器
- **工作内容**: 正文写完后**一次调用**同时抽取「摘要 + 下一章承接 handoff + 计划-正文对账」。每条带**逐字引文证据**（`evidenceQuotes`），offset 由系统回查、不信任模型位置。产物经 CAS + hash 溯源写回 `chapters.summary / continuityHandoff / planReconciliation`，构成正文生成期连续性保护块的读侧来源。

## prompt

````text
[system]
你是长篇小说的章节连续性记忆抽取器。只根据给定正文提取，不补写、不推测未来、不混入其他章节信息。

输出必须是一个 JSON 对象，不要 Markdown 围栏或解释：
{
  "summary": "100-200字客观摘要",
  "handoff": {
    "finalScene": { "location","storyTime","activeCharacters":[],"lastAction" },
    "stateChanges": [], "knowledgeChanges": [], "commitments": [],
    "openLoops": [], "immediateNextIntent": "",
    "evidenceQuotes": [ { "quote":"逐字复制的短引文","prefix":"消歧前锚点","suffix":"消歧后锚点" } ]
  },
  "planReconciliation": {
    "completedGoals":[{"text":"","evidenceQuotes":[…]}],
    "unfinishedGoals":[…], "deviations":[…], "newConstraints":[…], "nextChapterImpacts":[…],
    "proposedOutlineSummary": "基于实际正文的章纲候选；无需更新则空字符串"
  }
}

规则：
1. summary 与 handoff 必须来自同一次阅读；
2. finalScene/lastAction/openLoops/immediateNextIntent 以正文结尾为准；
3. stateChanges/knowledgeChanges/commitments 覆盖整章；
4. evidenceQuotes 必须逐字复制正文，禁止编造；不要输出 offset；
5. planReconciliation 必须比较原计划与实际正文；每条至少带一条正文逐字证据，没有证据就不输出；
6. 实际已发生内容优先于过时计划；不自动替作者决定更新，只给候选；
7. 没有依据的字段用空字符串或空数组，不要猜测。

[user]
【章节标题】{{chapterTitle}}
【原章纲与细纲】{{chapterPlan}}
【下一章当前计划】{{nextChapterPlan}}
【标准化后的完整章节正文】{{chapterText}}
请输出 JSON：
````

## context
本章标题 + 原章纲/细纲 + 下一章当前计划 + 标准化后的完整正文。

### 各个部分内容详细说明
- `chapterText`：经 `normalizeChapterText` 标准化的整章正文（引文回查以此为准）。
- `chapterPlan` / `nextChapterPlan`：本章原计划 + 下一章计划，用于 `planReconciliation` 对账（已完成/未完成/偏移/新增约束/对下一章影响）。
- 写回受 `adopt` 的 `compareAndSet`（chapter-source-text-hash）保护：正文 hash 变了就丢弃旧派生记忆（stale）。

# llm call · 事实抽取（双层事实账本）

## 概要
- **name**: `fact.extract`（fact-extract-adapter）
- **role**: 小说事实抽取器
- **工作内容**: 从章节正文抽取角色的**可验证客观事实**（受控谓词），每条带逐字引文，作为候选进 `temporalFacts`，作者确认后升为 canon，供 `currentFacts` 投影。

## prompt

````text
[system]
你是小说事实抽取器。从给定章节正文中，抽取关于角色的【可验证客观事实】，用于长篇一致性事实账本。

只允许使用下列受控谓词（不得自创）：${predicateList}

输出严格 JSON：
{"facts":[{"subject":"角色名","predicate":"受控谓词key","value":"事实值",
          "object":"关系/持有的对象名(可选)","quote":"逐字正文引文"}]}

规则：
1. predicate 必须是上面列出的 key（或其常见说法），否则不要输出该条；
2. quote 必须逐字摘自正文（用于回查证据），不得改写、不得编造；
3. 只抽客观、可验证的事实（地点/存亡/伤势/修为/目标/持有/认知/关系），不抽主观评价或推测；
4. 拿不准、正文没有明确依据的，不要输出；宁缺毋滥；
5. 没有可抽取的事实就返回 {"facts":[]}。

[user]
【章节】{{chapterTitle}}
【正文】{{chapterContent}}
请输出 JSON：
````

## context
本章标题 + 正文 + **受控谓词清单**（`fact-predicate-registry.ts`）。

### 各个部分内容详细说明
- `predicateList`：从谓词注册表注入的受控谓词 key，硬约束 AI 不得自创谓词（软抽取 + 硬校验的地基）。
- `quote`：解析后系统会逐字回查正文；证据不存在则丢弃该条。

# llm call · 状态变化提取（状态卡）

## 概要
- **name**: `state.extract`（state-extract-adapter）
- **role**: 小说角色状态追踪器
- **工作内容**: 对比当前状态表，只提取**已登记角色**本章明确发生的状态变化（位置/身体/境界/目标/势力/持有物/关系），写回 `stateCards`。

## prompt

````text
[system]
你是一个小说角色状态追踪器。你的任务是阅读章节内容，对比当前状态表，只提取已登记角色发生的状态变化。

规则：
1. 只提取本章中**明确发生变化**的状态，不要重复已有状态
2. entityName 必须严格取自"已登记角色名单"；地点、物品、组织、事件都不能作为角色
3. category 必须固定为 character
4. field 用简短中文词汇：位置、身体状态、境界、目标、所属势力、持有物、关系
5. oldValue 填变化前的值（从状态表读取），新实体填 null
6. 本章无状态变化返回空数组 []

输出：严格 JSON 数组，不要 markdown、不要解释。
示例：[{"entityName":"李明远","category":"character","field":"位置","oldValue":"长安","newValue":"洛阳"}]

[user]
【已登记角色名单】{{characterNames}}
{{stateContext}}                     # 当前角色状态记录，可空
【章节标题】{{chapterTitle}}
【章节内容】{{trimmedText}}
请只提取名单内角色的状态变更：
````

## context
已登记角色名单 + 当前状态表 + 本章正文。

### 各个部分内容详细说明
- `characterNames`：白名单，硬约束 `entityName` 只能取自它。
- `stateContext`：`buildSelectiveStateContext` 装配的现有状态卡（提供 oldValue 基线，避免重复）。

# llm call · 物品栏提取（物品流水）

## 概要
- **name**: `inventory.extract`
- **role**: 小说物品流水追踪器
- **工作内容**: 提取主角/核心视角本章的物品**获得/消耗**事件（gain/consume + 数量 + 来源），写回 `itemLedger`。是 `held-items` 确定性一致性校验的数据源。

## prompt

````text
[system]
你是一个小说物品流水追踪器。阅读章节正文，提取主角（或核心视角人物）**获得**或**消耗/失去**物品的事件。

规则：
1. 只提取本章明确发生的物品获得或消耗，不要提取仅被提及但未变动的物品
2. action 只能是：gain（获得/捡到/购买/奖励）或 consume（消耗/用掉/损坏/失去/赠予他人）
3. quantity 为正整数（不明填 1）
4. itemName 用简洁规范名称（"疗伤丹"而非"一颗疗伤的丹药"），多章保持一致
5. note 简述来源或用途
6. 只追踪主角/核心视角实际持有的可携带物品；地点、门、建筑、抽象能力、情绪、任务均不是物品
7. 结合"已有规范物品名"统一同义名称
8. 本章无物品变动返回 []

输出：严格 JSON 数组。
示例：[{"itemName":"疗伤丹","action":"gain","quantity":3,"note":"洞府石室中拾得"}]

[user]
【已有规范物品名】{{knownItemNames}}
【章节标题】{{chapterTitle}}
【章节内容】{{chapterText}}
请提取本章主角的物品获得/消耗事件：
````

## context
已有规范物品名 + 本章正文（长章由调用方分块，禁止静默截断）。

### 各个部分内容详细说明
- `knownItemNames`：统一同义名称，避免同一物品拆成多个近义名。

# llm call · 故事年表提取

## 概要
- **name**: `story-timeline.extract`
- **role**: 小说剧情梳理器
- **工作内容**: 提取本章**实际发生**的剧情大事（转折/冲突/相遇/突破），带故事内时间与重要度，写回 `storyTimelineEvents`（区别于世界背景历史）。

## prompt

````text
[system]
你是一个小说剧情梳理器。阅读章节正文，提取本章发生的**剧情大事**（推动故事的关键事件、转折、冲突、相遇、突破等）。

规则：
1. 只提取本章实际发生的剧情事件，不要提取背景设定或回忆
2. title 用简洁短语概括（"主角突破筑基期"）
3. storyTime 填故事内时间（"开元三年春"/"穿越后第7天"），无法判断留空
4. importance：1=次要、2=重要、3=关键转折
5. description 一句话补充经过/影响
6. 本章无重要剧情返回 []

输出：严格 JSON 数组。
示例：[{"title":"主角突破筑基期","storyTime":"入门第三年","importance":3,"description":"服下筑基丹闭关七日突破"}]

[user]
【章节标题】{{chapterTitle}}
【章节内容】{{chapterText}}
请提取本章的剧情大事：
````

## context
本章标题 + 正文（无上游设定，纯从正文抽）。

# llm call · 词条提取（设定库整理）

## 概要
- **name**: `codex.extract`
- **role**: 小说设定库整理器
- **工作内容**: 把整段世界观/设定文本拆成**当前分类**下的结构化独立词条（name/summary/description/fields/tags/importance），写回 `codexEntries`。可对正文或设定长文运行。

## prompt

````text
[system]
你是小说设定库整理器。把用户提供的整段设定拆成"当前分类"下的独立词条。

规则：
1. 只提取属于当前分类的实体或概念；不要把段落标题、泛称、空洞概念当成词条
2. 已有同名词条不要重复生成；同一实体只输出一次
3. name 简洁稳定，summary 一句话，description 保留关键设定与限制
4. fields 只能使用给定字段 schema 的 key；没有依据的字段不要编造
5. importance 为 0-5；越影响主线越高
6. supplementTags 为"是"时生成 2-5 个检索标签，否则 tags 为 []

输出严格 JSON 数组：
[{"name":"","icon":"","summary":"","description":"","fields":{},"tags":[],"importance":0}]

[user]
【当前分类】{{categoryName}}
【分类字段 schema】{{fieldSchema}}
【已有词条名称】{{existingEntries}}
【是否补充检索标签】{{supplementTags}}
【待拆分内容】{{sourceText}}
请拆分为可确认写入的词条。
````

## context
当前分类名 + 该分类字段 schema + 已有词条 + 待拆分文本。

### 各个部分内容详细说明
- `fieldSchema`：该 codex 分类允许的字段 key，硬约束 `fields` 不得越界。

# llm call · 润色 / 扩写 / 去 AI 味

## 概要
- **name**: `chapter.polish` / `chapter.expand` / `chapter.de-ai`
- **role**: 文字润色专家 / 小说扩写专家 / 文字风格化专家
- **工作内容**: 对选区或整段正文做**保持情节不变的局部改写**——润色（优化表达）、扩写（加细节/心理/环境，情节不变）、去 AI 味（改得更像真人写，90%~110% 篇幅铁律）。产物预览后替换。

## prompt

````text
[chapter.polish · system]
你是一位文字润色专家。根据用户的指令修改文本，保持原意不变，只优化表达。直接输出修改后的文本，不要解释。{{#if usesStyle}}本次润色风格倾向：{{style}}{{/if}}
[user] 指令：{{instruction}}  原文：{{text}}

[chapter.expand · system]
你是一位小说扩写专家。将用户提供的文本扩展丰富，增加细节描写、心理活动、环境氛围，但保持情节走向不变。直接输出扩写后的文本。{{#if usesAddType}}本次扩写主要增加：{{addType}}{{/if}}{{#if usesExpandRatio}}扩写倍数：约 {{expandRatio}}{{/if}}
[user] {{#if userHint}}要求：{{userHint}}{{/if}} 请扩写以下内容：{{text}}

[chapter.de-ai · system]
你是一位文字风格化专家。你的任务是将 AI 味道重的文本改写得更像真人写的{{#if usesAggressiveness}}（改写力度：{{aggressiveness}}）{{/if}}。
去 AI 味技巧：1.去掉"的确/毫无疑问/不禁"等 AI 常用词 2.把个别过长句子拆短 3.更口语化 4.增加不完美感 5.减少排比对仗 6.保持原意不变
⚠ 篇幅铁律：成稿字数控制在原文 90%~110%；绝不删减情节/跳段/合并场景/省略描写；也不注水扩写；逐段对应改写。
直接输出修改后的全文。
[user] {{text}}
````
可调参数：polish `style`；expand `expandRatio`/`addType`；de-ai `aggressiveness`。

## context
仅目标文本 + 指令/参数，**不装配项目上下文**（纯文本加工，不需要世界观）。

### 各个部分内容详细说明
- `text`：选区文字或整章正文（去 AI 味整章时对全文，修 G4 字数缩水）。
- 注：批量正文 `chapter.content.batch` 复用 `detail.scene` + `chapter.content`，由 `batch-detail-runner` 串多章跑，支持断点续跑/暂停。

# llm call · 质量审校（五维）

## 概要
- **name**: `review.quality`（review-adapter `buildReviewPrompt`）
- **role**: 专业小说编辑（多维审校）
- **工作内容**: 从逻辑一致性/人物行为/世界观/伏笔衔接/情节节奏五维审查正文，输出带评分 + 逐条 `issues{severity,quote,suggestion}` 的 JSON 报告（ReviewPanel）。软建议，不落库。

## prompt

````text
[system]
你是一位专业的小说编辑，负责对章节进行多维度审校。请从以下五个维度审查正文：
1. 逻辑一致性（logic）：位置移动是否合理、时间线是否连贯、因果是否成立
2. 人物行为一致性（character）：性格是否前后矛盾、对话是否符合人设
3. 世界观一致性（worldview）：是否违反已设定的世界规则
4. 伏笔衔接（foreshadow）：本章涉及伏笔是否处理得当、是否遗漏
5. 情节节奏（pacing）：是否拖沓或跳跃、叙述节奏是否合理

输出严格 JSON（不要 markdown 代码块）：
{ "overallScore":85,
  "issues":[{ "dimension":"logic|character|worldview|foreshadow|pacing",
              "severity":"info|warning|critical","description":"","quote":"原文≤30字(可选)","suggestion":"" }],
  "suggestions":[""] }
评分：90-100 优秀 / 70-89 良好 / 50-69 一般 / 0-49 需大改。

[user]
【章节标题】{{chapterTitle}}
【正文】{{chapterContent}}                 # slice 4000
【上一章摘要】/【世界观】/【角色设定】/【伏笔状态】/【状态表】（各截断）
请开始审校：
````

## context
本章正文 + 上一章摘要 + 世界观 + 角色 + 伏笔状态 + 状态表（均截断注入）。

### 各个部分内容详细说明
- 上下文覆盖五个维度各自的判据来源；`quote` 用于把 finding 锚回原文（引证纪律的雏形）。

# llm call · AI 味检测

## 概要
- **name**: `review.anti-ai`（anti-ai-adapter）
- **role**: 检测/消除 AI 生成痕迹的文学编辑

```
上游生成（D1）──→ chapter.content ──→ 已写正文 chapters
                                          │
        ┌─────────────────────────────────┼───────────────────────────────┐
        │ 组A 反写四层记忆/提取（软抽取+硬回查）                              │
        │  chapter.memory / fact / state / inventory / story-timeline /     │
        │  codex / location.extract  ── 作者确认 → canon → 回流下一轮上下文  │
        └──────────────────────────────────────────────────────────────────┘
        ┌──────────────────────────────┐   ┌───────────────────────────────┐
        │ 组B 编辑加工（纯文本）         │   │ 组C 审校（软建议，不落库）     │
        │  polish / expand / de-ai      │   │  quality / anti-ai /           │
        └──────────────────────────────┘   │  readability / revise /        │
                                           │  scene.verify                  │
        ┌──────────────────────────────┐   └───────────────────────────────┘
        │ 组D 文风/参考/历史             │   ┌───────────────────────────────┐
        │  style.learn（→反哺正文文风） │   │ 组E 结构化/导入/地图           │
        │  reference.* / history.*      │   │  restructure / *.structure /   │
        └──────────────────────────────┘   │  import.* / geography.*        │
                                           └───────────────────────────────┘
```

**共性**：所有下游调用同样是「UI 触发 → 固定 adapter → 单发 chat」；软抽取一律加**硬回查/硬校验**（受控谓词、引文逐字回查、白名单实体、`adopt` 字段/枚举/FK/去重、CAS/hash 溯源）；产物一律**候选 → 作者确认**才成权威。没有任何一步由 agent 自主决定"下一步调哪个 LLM"——编排全在 UI 与固化流程里。

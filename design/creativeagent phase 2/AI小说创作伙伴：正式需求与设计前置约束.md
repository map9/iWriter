## 1\. 小说完整创作全流程

分为**前期筹备、初稿写作、中期修改、定稿打磨、出版/发布收尾**五大核心阶段，每个阶段有明确工作目标，业余写手常跳过大量环节，成熟作家会完整走完。这五大阶段，都会形成阶段性的成果物，也会存在反复，特别是前三个阶段。

|   阶段序号   |   创作阶段名称   |   核心工作内容   |   对应成果物及呈现形式   |
| --- | --- | --- | --- |
|   一   |   前期筹备阶段（动笔前，占总工作量30%）   |   1.灵感收集与选题筛选：积累日常素材、验证选题市场适配度与核心冲突，确立故事核心主题与一句话梗概；【由main Agent→Planer Agent】 2.世界观搭建：根据题材设定时代背景、规则体系、势力/地理等核心设定，规避后期设定崩坏； 3.人物体系设计：打造主角成长弧光、配角独立动机，梳理完整人物关系网； 4.大纲分层：根据创作需求搭建粗纲/分卷大纲/章节细纲，明确故事起承转合； 5.开篇打磨：多版开篇试写，确定最佳故事切入点。   |   灵感素材文档 选题定位说明文档 全书设定集 人物总表/单人人物卡/人物关系图谱 全层级大纲文档 多版开篇试写稿   |
|   二   |   初稿写作阶段（落地文字，占总工作量30%）   |   1.固定写作节奏，设定稳定的日更字数，保证持续输出与语感连贯； 2.遵循「先完成，再完美」原则，不纠结细节措辞，按大纲完成完整故事； 3.实时记录写作中发现的设定漏洞、剧情缺口，不中断写作节奏； 4.完成全稿后通读整体脉络，标记核心问题。   |   分章节初稿文档 卡文标注草稿 全书完整初稿（第一版全文） 初稿问题批注文档   |
|   三   |   一轮大修（结构与剧情修改，核心环节，占总工作量25%）   |   1.节奏优化：砍掉无关支线、冗余内容，合并重复情节； 2.逻辑修复：修正人物行为矛盾、设定冲突、生硬巧合等问题； 3.冲突强化：拉高主角阻碍，补齐反派动机，修正降智剧情； 4.人物弧光调整：补充过渡事件，修正主角成长突兀的问题； 5.剧情比重重分配：解决前松后紧、高潮篇幅不足等结构问题。   |   带修订批注的初稿全文 支线删减清单 剧情重排对照表 逻辑漏洞修复表 二改结构稿（调整完故事框架的完整文稿）   |
|   四   |   二轮精修（文字与细节打磨，占总工作量10%）   |   1.语言优化：删减冗余修饰，统一文风，区分不同人物的对话语气； 2.细节填充：完善环境、动作、心理描写，增强画面感与代入感； 3.情绪校准：调整段落节奏与氛围，匹配对应故事情绪； 4.查漏补缺：统一人名、地名、时间线，修正笔误； 5.视角统一：固定叙事视角，避免频繁切换造成混乱。   |   带文字修订标记的全文 人名/地名/时间线统一规范表 人物说话风格对照表 三改精修稿（文字细节全部理顺的完整文稿）   |
|   五   |   三审定稿阶段（收尾优化）   |   1.冷处理搁置：精修稿放置3-7天，脱离创作情绪后重新通读自查； 2.外部试读：将样稿交给编辑、目标读者试读，收集客观反馈； 3.针对性微调：根据反馈优化内容，同时守住核心创作表达； 4.全文通读定稿：连续完整通读，修正最后残留的病句、标点、分段问题； 5.整理配套文件，归档全流程资料。   |   自查问题清单 试读样稿 读者反馈收集表 反馈整改方案 终审定稿全文 完整设定集/人物卡/大纲等配套附属打包文件   |
|   六   |   投稿/出版/发布收尾阶段（先不用考虑）   |   1.网文连载路线：分章切割定稿，制作封面、撰写简介与标签，连载期间根据读者反馈小幅调整剧情，完本后整体大修； 2.传统出版路线：撰写投稿资料包，投递出版社/编辑，过稿后配合编辑深度修改，完成三审三校、排版校对、印刷上市全流程； 3.独立出版/自印路线：自行对接排版、校对、印刷，完成宣传文案与封面设计。   |   网文连载：分章定稿、作品简介、标签、番外文稿、作者专栏简介； 传统出版：投稿资料包、编辑修改稿、三审校样、清样校对稿、封面/封底/腰封文案； 独立出版：排版定稿、印刷源文件、全套宣传物料   |

## 2\. AI小说创作伙伴的定位

AI 小说创作伙伴不应被定位为一个只负责续写或单次生成内容的工具，而应被定位为一个面向“小说创作工程”的协作型 Agent 系统。它服务的不是一次性 prompt，而是从前期筹备、初稿写作、中期修改到定稿打磨的完整创作链条，并围绕这一链条参与对象识别、上下文装配、任务执行、review、版本推进与协作交付。

从工作对象看，它所面对的不是零散文本，而是一个由作品设定、人物资料、关系结构、章纲、章节、场景、版本、问题清单与 review 结果共同组成的工程空间。因此，它的价值不只在于“帮作者写一点内容”，而在于作为一个可参与整个小说创作过程的系统化协作伙伴，帮助作者在复杂工程中持续完成构思、写作、修改、校验与回溯。

在当前阶段，这个系统的核心定位应是“作者主导下的协作型创作伙伴”。它的重点不是替代作者做最终判断，而是在作者掌握方向权、取舍权与审批权的前提下，承担资料整理、创意辅助、设定补全、大纲展开、正文协助、局部改写、问题扫描、一致性检查、review 与版本说明等工作。换言之，现阶段首先要把“高参与度、可见、可控、可回退的协作能力”做扎实，而不是一开始就追求完全自主创作。

从演进方向看，AI 小说创作伙伴可以逐步从协作执行者，发展为能够承担局部主创任务的执行型 Agent，再进一步发展为具备选题整理、创意孵化、方案比较、阶段编排与高自主度写作能力的创作系统。但无论自主程度如何提高，正式创作中的方向确认、关键取舍、版本批准与最终责任，仍应始终保留在写作者一侧。这意味着，它未来可以越来越能写、越来越能组织流程，但其根本定位依旧不是替代作者，而是持续放大作者的创作能力。

## 3\. AI小说创作伙伴的设计分层

AI小说创作伙伴不应该先被定义为服务某一类作者、某一种小说类型、或某一个固定工作流的工具，而应该先被定义为一个面向小说创作工程的通用 Agent 框架。它更接近 Code Agent 的设计方式：先抽象出稳定的工作对象、核心能力、约束机制与任务体系，再通过配置、上下文和策略去适配不同作者、不同类型、不同创作阶段。

这一设计可以拆成三个层次：通用内核、适配层、任务层。

### 3.1 通用内核

通用内核回答的是“这个 Agent 在任何小说项目中，始终如何工作”的问题。它不随着作者类型、题材类型、创作习惯而改变，是整个系统的底层不变量。

核心内容包括：

*   小说工程的对象模型：作品、设定、人物、关系、时间线、大纲、章节、场景、草稿、修订稿、版本等；
    
*   上下文装配与记忆机制：在不同任务下，如何自动读取当前需要的设定、人物资料、章节内容、历史版本与约束条件；
    
*   编辑与生成约束：哪些内容可以直接生成或修改，哪些高风险改动必须先确认；
    
*   一致性检查机制：角色设定、世界规则、时间线、称谓、伏笔、关系推进等是否前后一致；
    
*   版本、审批与回溯机制：每轮修改都可追踪、可解释、可比较、可回退。
    

### 3.2 适配层

适配层回答的是“面对不同类型的作者与项目，这个 Agent 应该以什么策略工作”的问题。

这里的差异不应该被写死为产品边界，而应该被设计成可切换、可配置、可从上下文中推断的工作模式。例如：

*   作者成熟度差异：新手需要更多解释与引导，成熟作者更需要高效率与低打扰；
    
*   类型差异：玄幻、悬疑、言情、科幻等题材在节奏、信息释放、结构习惯上存在差异；
    
*   风格差异：偏网文节奏、偏出版表达、偏类型爽感、偏文学化表达等；
    
*   干预强度差异：建议型、协作型、执行型、自主推进型；
    
*   风险控制差异：保守、平衡、激进。
    

因此，作者画像和小说类型不应该先成为限制条件，而应该成为 Agent 的配置维度、策略维度和上下文维度。

### 3.3 任务层

任务层回答的是“在小说完整创作流程中，Agent 具体承担哪些工作，以及在不同工程状态下应如何执行”的问题。

它不应只被理解为对五个创作阶段的静态罗列，也不应只是一个功能清单。更准确地说，任务层同时包含两条组织线索：一条是按小说完整创作流程覆盖阶段任务，另一条是按当前工程状态与用户问题决定 Agent 的执行操作思路。

第一条线索是阶段覆盖。除第六阶段“投稿/出版/发布收尾阶段”暂不纳入外，Agent 需要覆盖前五个创作阶段中的核心任务，并与各阶段的成果物、审批点、上下文需求相对应。

第二条线索是执行模式判断。Agent 在执行操作层面，不应始终以同一种方式工作，也不应把“模式选择”交给用户手动决定。更合理的方式是：依据当前工程状态与用户当前问题，自动判断采用更偏构思的执行模式，还是更偏写稿的执行模式；如果判断依据不足，再通过最小化澄清获取信息。

构思模式主要面向创意、设定、人物、大纲、候选方案等定义类对象，重点是发散、比较、推演、收敛与形成可写前提；写稿模式主要面向章节、场景、正文、修订稿、版本差异等正文类对象，重点是落地、续写、改写、重构、审查与收束。两种模式与创作阶段高度相关，但不完全等同于阶段标签，Agent 需要根据工程状态与当前问题动态判断。

#### 3.3.1 前期筹备阶段

这一阶段通常以构思模式为主。Agent 主要承担创意发散、信息整理、方案比较和结构规划工作，包括但不限于：创意发散与主题收敛、世界观与背景设定构建、人物设计、角色关系推演、总纲/卷纲/章纲生成、关键剧情节点拆分、多版开篇试写与切入点比较等。此时 Agent 的重点不是直接生产稳定正文，而是帮助形成可写前提，并显式区分“候选方案”和“已确认前提”。如果用户在这一阶段要求试写开篇、试写场景或验证某种文风，也可以局部进入写稿模式，但其目的仍然服务于构思判断，而不是正式进入大规模正文生产。

#### 3.3.2 初稿写作阶段

这一阶段通常以写稿模式为主。Agent 主要承担将规划内容落地为正文的工作，包括但不限于：从章纲展开正文、从场景卡展开场景、续写与桥接、对话与描写强化、写作过程中的即时一致性提醒、阶段性通读与问题标注等。此时 Agent 的重点是基于当前有效设定和大纲稳定生产正文，而不是重新发散整体方向。但如果写作过程中暴露出基础设定不稳、章纲无法支撑正文等问题，Agent 也应能短暂退回构思模式，对局部前提重新梳理后再继续写稿。

#### 3.3.3 一轮大修阶段

这一阶段整体上仍以写稿模式为主，但工作重点从“生成正文”转向“结构重构”。Agent 主要承担全稿结构诊断、剧情节奏分析、高潮与冲突分布检查、剧情重组建议、人物弧线与关系线校准、伏笔与回收体系审查、大修执行辅助与结构调整后的版本说明生成等。这里更像对既有正文工程做系统性重构，而不是重新定义全部创作前提；但若重构过程中发现主线、设定或人物逻辑本身存在根本性缺口，Agent 也应切换到构思模式，先补齐前提，再回到写稿模式执行修改。

#### 3.3.4 二轮精修阶段

这一阶段主要处于写稿模式中的精修环节。Agent 主要承担语言质量与阅读体验优化工作，包括但不限于：语言润色、句式节奏优化、文风统一、视角控制、细节逻辑修正、称谓与名词统一、重点片段精修等。此时 Agent 的重点是局部优化与一致性收束，通常不会再大范围打开新的方案分支。

#### 3.3.5 三审定稿阶段

这一阶段主要处于写稿模式中的终审与收束环节。Agent 主要承担全稿终审检查、遗留问题清单汇总、版本差异总结、正文与设定集一致性核查、项目成果物整理、定稿前风险提示等工作。此时 Agent 的重点是基于当前版本做核查、校验、归档与风险暴露，而不是再打开新的大方向分支。

## 4\. 正式需求与设计前的关键约束

### 4.1 工作对象定义

在进入具体设计前，首先需要明确 AI 小说创作伙伴所操作的不是零散文件，也不是单次 prompt，而是一个完整的“小说创作工程”。因此，应先定义清楚系统的核心工作对象，以及这些对象之间的关系。只有工作对象被定义清楚，后续的文件结构、上下文装配、任务拆分、一致性检查、审批流转和 UI 呈现才有稳定基础。

工作对象至少应包括以下几类：

*   作品对象：书名、题材、标签、主题、目标读者、篇幅规划、创作目标等；
    
*   设定对象：世界观、时代背景、规则系统、阵营、地理信息、历史沿革、名词体系等；
    
*   角色对象：角色档案、外显特征、核心欲望、动机、秘密、成长弧线、关系网络等；
    
*   结构对象：总纲、卷纲、章纲、场景卡、关键冲突、高潮点、伏笔与回收点等；
    
*   正文对象：章节草稿、修订稿、重点片段、被删片段、批注内容等；
    
*   过程对象：任务、审批意见、修改说明、问题清单、版本记录、阶段状态等；
    
*   素材对象：灵感碎片、参考资料、图片、废案、备选桥段、风格样例等。
    

这些对象不是彼此孤立的，而是构成一个有依赖关系的创作网络。例如，角色对象会约束正文对象，设定对象会约束结构对象与正文对象，过程对象会记录正文对象和结构对象的变更历史，素材对象则为前期筹备与局部改写提供支持。

因此，在需求层应进一步回答几个问题：哪些对象是一级对象，哪些是附属对象；哪些对象是长期稳定的，哪些对象会频繁变动；哪些对象可以直接被 Agent 修改，哪些对象只能由作者确认后生效；对象之间的引用关系、优先级关系和版本继承关系如何定义。

这一层一旦定义清楚，AI 小说创作伙伴才能真正像 Code Agent 一样，不是围绕“文本输入输出”工作，而是围绕“工程对象的读取、理解、修改、校验与协作”工作。

### 4.2 能力边界定义

在工作对象被定义清楚之后，下一步需要明确的是：AI 小说创作伙伴在小说创作工程中到底承担什么职责，以及哪些事情不应由它默认决定。这里的能力边界不应被理解成一套静态权限表，而应与 Agent 的执行模式一起理解。

整体上，Agent 至少存在两种不同的执行操作思路：构思模式，以及写稿模式。前者更像 Code Agent 的计划模式，主要面向创意、设定、人物、大纲、候选方案等定义类对象；后者更像 Code Agent 的实施模式，主要面向章节、场景、稿件、修订结果等正文类对象。

在构思模式下，Agent 可以大量进行方案生成、方案比较、结构补全、设定推演、问题整理与待确认项组织；但不应默认把候选内容升级为正式设定，不应擅自淘汰备选路线，也不应在结论尚未稳定时锁定整体方向。

在写稿模式下，Agent 可以基于当前有效设定和大纲进行续写、改写、局部重写、问题扫描、版本比对和一致性修正；但不应擅自改动主线走向、引入未授权核心设定、跨多个对象进行高影响面修改，或在未确认的情况下覆盖稳定版本。

因此，能力边界定义本质上要回答的不只是“哪些事情能做、哪些事情不能做”，还包括：面对当前工程状态与用户问题，Agent 应判断自己进入哪一种执行模式；在该模式下，哪些操作属于直接执行，哪些属于建议生成，哪些属于必须等待作者确认的创作决策。若判断依据不足，Agent 应优先向用户做最小化澄清，而不是把模式选择负担转交给用户。这里的两种模式，可以直接用写作者更容易理解的说法来表达：构思模式与写稿模式。

### 4.3 高风险操作定义

高风险操作并不是一个跨阶段完全相同的清单。对 AI 小说创作伙伴而言，构思模式与写稿模式面对的是不同类型的对象，因此高风险的来源也不同。

在构思模式下，高风险更多来自“错误决策风险”，而不是“正文破坏风险”。典型情况包括：把候选设定误升级为正式设定、过早冻结尚不成熟的大纲或世界规则、删除本应保留的备选方案、让局部灵感错误地主导整体创作路线等。这类风险一旦发生，后续写作虽然看似顺利，底层前提却可能已经被错误锁定。

在写稿模式下，高风险更多来自“变更扩散风险”。典型情况包括：修改世界观底层规则、改变核心人物设定或关系走向、重排主线结构、整章或跨章节重写、用新版本覆盖稳定正文、以旧版本回滚当前有效版本等。这类风险会牵动多个对象、多个章节和后续大量正文。

因此，高风险操作的定义不应只是一张静态清单，还应明确其判断维度，例如：影响面是否广、连锁反应是否强、验证成本是否高、是否会破坏当前稳定版本、是否难以回滚。

同时，还需要定义配套处理原则：是否必须在执行前提示影响范围；是否必须给出修改理由与替代方案；是否要求展示会受影响的对象、章节或版本；是否必须保留原版本并生成差异说明；是否需要作者显式确认后才能继续。

只有把高风险操作定义成“与执行模式相关的高影响面改动”，后续审批机制、回滚机制、提示机制和自动驾驶边界才会真正稳定。

### 4.4 阶段成果物与版本推进条件

AI 小说创作伙伴既然要服务完整创作流程，就需要理解不同阶段会沉淀出不同类型的成果物。但这里不必把小说工程设计成僵硬的阶段状态机，更合适的方式是围绕成果物类型与版本推进条件来组织工作。

尤其需要区分两类差异明显的阶段：前期筹备阶段，主要沉淀设定、大纲、人物、创意方案等定义类对象；写作阶段（包括初稿、一稿、二稿及其后的修订），主要沉淀章节正文、修订稿、问题清单、版本差异等正文类与修订类对象。

因此，这部分需求至少要回答两类问题：

*   当前阶段的核心成果物是什么；
    
*   在什么条件下，当前版本可以继续推进到下一类稳定成果。
    

在筹备阶段，典型成果物包括创意卡、立项卡、设定集、角色卡、总纲/卷纲/章纲、多版开篇方案等。这里的推进条件，不是简单地“切换到下一状态”，而是创作前提是否已经足够闭合，例如主题是否明确、核心设定是否基本稳定、主要角色是否能够支撑主线、是否至少存在一版可写的大纲。为了方便后续写入 Agent 的 prompt，可以把 0.x 的语义直接约定为：仍处于构思打底、设定收敛和大纲成形阶段；只有满足这些条件后，工程才适合从 0.x 类的筹备版本推进到 1.0 级的正文落地。

在写稿阶段，典型成果物包括章节初稿、完整初稿、一轮大修稿、二轮精修稿、终审问题单、版本差异说明等。这里的推进条件，更接近版本迭代是否形成了阶段性稳定快照。为了方便后续写入 Agent 的 prompt，可以把语义进一步说清楚：1.0 表示第一次形成可通读全稿；1.x 表示在完整初稿基础上的补写、局部改写和问题修补；2.x 表示完成一轮大修后的稳定版本；3.x 可以表示精修后的稳定版本；而诸如 draft-complete、rewrite-pass、final-candidate 之类的 tag，则可用于标记阶段性稳定成果。

这样定义之后，Agent 就不会把“阶段”理解成僵硬的流程开关，而是能把它理解为：当前工程正在沉淀哪一类成果物、当前版本处于怎样的成熟度、是否已经具备继续推进的条件。后续在 Agent 的 prompt 中，也可以直接用这套版本语义来判断当前更适合进入构思模式还是写稿模式。

### 4.5 上下文优先级与装配规则

由于小说创作工程中会同时存在正式设定、候选方案、当前正文、历史版本、批注意见、废弃草案等多种信息来源，因此在设计前不仅要定义“谁优先”，还要定义“在什么任务下装配哪些上下文”。否则，Agent 很容易把不同阶段、不同版本、不同性质的信息混在一起使用。

这部分规则需要同时覆盖两种执行模式：构思模式与写稿模式。

在构思模式下，Agent 面对的主要是定义类对象和候选方案。此时，上下文装配应优先围绕“当前正在讨论的方案分支”展开，并遵循以下原则：已确认的创作前提优先于未确认的灵感与草案；不同候选方案可以并行存在，但必须被显式区分，不能被混合引用；历史方案可以用于比较，但不应默认被当作当前有效结论。

在写稿模式下，Agent 面对的主要是正文类对象和修订类对象。此时，上下文装配应优先围绕“当前有效正文链路”展开，通常优先读取当前章节或场景、对应章纲、已确认设定、相关人物资料、相邻章节与当前有效版本；历史版本、废案与旧草稿默认不注入，除非用户明确要求比较、回顾或恢复。

在两种模式之上，还应存在一组共同的优先级原则：

*   用户当前明确指令，优先级最高；
    
*   当前有效版本中的正式对象，优先于历史版本与候选草案；
    
*   已确认前提，优先于未确认候选；
    
*   与当前任务局部最相关的对象，优先于全局但弱相关的信息；
    
*   已废弃对象若仍可检索，必须被显式标注为不可直接引用。
    

此外，还需要补充若干细化规则：同一对象存在多个版本时，哪个版本被视为当前有效版本；用户当前指令若与已确认前提冲突，系统是直接服从，还是先提示冲突；在自动装配上下文时，哪些来源默认注入，哪些来源只能在显式请求下引入。

上下文优先级与装配规则一旦建立，后续的记忆系统、检索系统、审校系统和自动写作系统才有稳定依据。否则，Agent 最危险的一类错误并不是“写得不好”，而是“逻辑上自洽，但依据了错误的上下文”。

### 4.6 输入输出契约定义

在进入具体设计前，还需要明确 AI 小说创作伙伴的输入输出契约。这里的重点不是把所有交互写死，而是先约定：在不同任务类型下，系统接收的输入至少应包含哪些必要信息，输出结果至少应以什么结构交付，哪些内容属于正文结果，哪些内容属于说明性结果。

输入契约至少要覆盖几类常见任务：构思类任务、设定类任务、大纲类任务、写稿类任务、审校类任务、重构类任务。不同任务的输入重点不同，例如构思类任务更依赖主题、题材、目标情绪与候选方向，写稿类任务更依赖当前有效设定、章纲、相关章节与篇幅要求，审校类任务则更依赖被检查对象、检查范围与判断标准。

输出契约也应被结构化约定。例如：生成类任务的输出，至少要区分“正式可用结果”和“候选建议”；修改类任务的输出，至少要区分“修改后的正文”“修改说明”“影响范围”“待确认事项”；审校类任务的输出，至少要区分“发现的问题”“问题等级”“依据对象”“建议处理方式”。

这部分约定的意义在于：后续无论是单 Agent 执行，还是多 Agent 协同，或是通过 skills 装配出不同 workflow，系统都能围绕同一套输入输出契约工作，而不会退化成纯聊天式的不可控交互。

### 4.7 验收标准与质量判断规则

AI 小说创作伙伴不仅要能生成、修改和审查内容，还需要有一套可约定的验收标准与质量判断规则。否则，Agent 虽然可以持续产出内容，却无法判断某一轮结果是否已经达到“可接受”“可进入下一轮”“必须返工”的程度。

这里的验收标准不必做成单一打分体系，而应根据任务类型进行约定。例如：构思类任务更关注方向是否清晰、候选方案之间是否有区分度、是否已形成可写前提；设定类任务更关注规则是否闭合、人物动机是否成立、结构对象之间是否可支撑主线；写稿类任务更关注正文是否完成任务目标、是否符合当前设定与章纲、是否存在明显断裂；审校类任务则更关注问题识别的完整性、严重性分类与建议的可执行性。

在需求层，可以先约定几类基础判断维度：完整性、自洽性、一致性、可执行性、风险暴露程度、是否满足当前阶段目标。后续 Agent 的 review、问题扫描、版本比较与阶段推进，都可以围绕这些维度给出判断，而不是只给出模糊的“写得好/不好”。

### 4.8 协作角色与权限边界定义

在当前阶段，系统中的协作角色可以先收敛为两个：写作者与 Agent。这里不需要先扩展为复杂的多人协作体系，因为当前最关键的是把“写作者如何与 Agent 协作”定义清楚。

在这一前提下，可以约定：Agent 在能力上可以参与任何环节，包括构思、整理、试写、续写、重构、审校、归档、review、版本比较等；但 Agent 的任何正式变更都需要获得写作者的同意。也就是说，Agent 可以广泛介入，但不能绕过写作者做最终决定。

当冲突出现时，无论是方案冲突、设定冲突、版本冲突，还是修改方向冲突，Agent 都不应直接替写作者裁决，而应整理冲突点、给出可比较方案、解释各自影响范围，再由写作者做最终决定。这一约定可以保证系统在保持高参与度的同时，不会越过作者主导权。

### 4.9 失败模式与恢复机制

失败模式与恢复机制，应尽量按照 Code Agent 的方式来处理，而不是额外设计一套重型流程系统。这里的关键不是定义所有错误状态，而是约定：当 Agent 的判断、生成、修改或装配出现问题时，系统如何发现、保留现场、暴露差异、允许回退，并让写作者重新接管。

典型失败模式至少包括：引用了错误版本的上下文；把候选方案误当正式设定；局部改动引发了未预期的连锁影响；生成结果偏离当前章纲或设定；重构过程中破坏了已有结构稳定性；review 结论与正文依据不一致等。

恢复机制则应围绕几个原则展开：保留原版本、显式展示差异、说明依据对象、暴露影响范围、允许回退到上一稳定版本、允许写作者中断当前执行并改为手动决策。也就是说，失败不是通过隐藏来处理，而是通过版本、差异、说明与回退来处理。

### 4.10 冻结规则与变更传播处理原则

冻结规则与变更传播，不必先做成一套刚性的状态机规则，更适合按照 Code Agent 的方式来处理。也就是说，当前阶段不必预设大量“冻结对象”与“自动传播链”，而是优先通过版本语义、影响分析、变更说明与写作者确认来控制风险。

换句话说，系统不需要先规定复杂的“某对象一旦冻结就绝不能改”，而应在每次高影响面修改发生时，能回答几个更实际的问题：改动影响了哪些对象、哪些章节、哪些设定、哪些版本；这些影响是局部的还是全局的；是否需要回扫相关正文；是否需要额外做一次 review。

因此，这部分可以先作为处理原则存在：不单列重状态冻结系统，而是把变更传播视为一种需要被显式分析、说明和确认的工程行为。

### 4.11 默认工作流与可覆盖工作流

AI 小说创作伙伴需要有一套默认工作流，用来支撑大多数项目的稳定推进；同时，也必须允许工作流被覆盖或扩展，而不是把流程写死。

默认工作流可以直接对齐当前文档中已经定义的完整创作流程，并在每类关键任务后约定基础动作，例如：写完一轮内容后可自动触发一次 review，做完一次大修后可自动生成版本差异说明，进入定稿前可自动触发一致性检查等。

但另一方面，用户也应能通过 skills 来定义自己的流程或操作方式。例如，有的作者希望每次调整后自动做 review，有的作者希望每一章写完后都自动做设定一致性检查，有的作者希望在构思阶段固定先做三版方案比较。也就是说，系统需要有“默认流程”，也需要有“可由 skills 覆盖或补充的流程”。

### 4.12 单 Agent 与多 Agent 分工定义

从长期设计看，这一系统更适合建立在多 Agent 基础上，而不是把所有能力写死在单一 Agent 中。但这里的多 Agent，也不应一开始就被规定得过于僵硬。

一类 Agent 可以是预先定义好的标准能力 Agent，例如 web search agent、explorer agent 等，这些能力边界相对清晰、复用性强，适合被固定下来。另一类 Agent 则可以是围绕当前项目、当前流程、当前 skills 动态生成或装配出来的 Agent，例如针对某部小说当前 workflow 临时形成的构思 Agent、写稿 Agent、审校 Agent、版本比较 Agent 等。

因此，需求层更应强调“灵活组装”而不是“预设死板角色”。Agent 如何拆分，应服从前面已经定义的设计分层：通用内核负责提供基础能力，适配层负责提供策略差异，任务层负责确定当前要完成的工作，多 Agent 的具体分工则由 prompt、skills 与当前工程状态共同决定。

### 4.13 配置体系与个性化记忆定义

在配置与记忆层面，可以先明确三种作用域：项目级别、作者级别、任务即时上下文。

项目级别的记忆，主要服务于当前小说工程本身，例如题材、设定约束、文风偏好、角色关系、版本语义、默认工作流等；作者级别的记忆，主要服务于长期协作习惯，例如是否偏好多方案先行、是否喜欢先 review 再改稿、是否接受激进改写、是否需要更多解释等；任务级别的信息，则不必单列为长期记忆，而主要放在当前上下文中处理。

这样区分的好处是：长期偏好不会和临时任务混在一起，项目规则不会误扩散到其他作品，而一次性要求也不会被错误记成永久习惯。

### 4.14 可观测性与解释义务

最后，还需要明确系统的可观测性与解释义务。这里不必要求 Agent 对所有动作都做同等强度的解释，而应根据当前工作任务与实际动作来决定解释深度。

例如：普通的局部润色，可以只给出简要修改说明；跨章节重写、大纲调整、设定改动、版本回退、高风险操作等，则应给出更完整的解释，包括依据了哪些对象、为什么这样改、可能影响哪些部分、是否仍有待确认风险。

也就是说，解释义务应与任务类型、影响范围和风险等级相匹配。这样既不会让系统陷入过度说明，也能在真正关键的地方保持足够可观测、可检查、可追责。

## 5\. 设计落地前置要求

第 4 节解决的是“设计前需要先定义清楚什么”的问题；第 5 节则进一步回答：为了把这些需求真正落成一个可运行、可协作、可回溯的 AI 小说创作伙伴，在工程与实现层面需要先具备哪些前置条件。

整体上，所有成果物都应按照“目录 + 文档 + 版本”的方式进行管理，像软件开发中的工程空间一样组织。写作者可以看见所有内容、手工修改所有对象、审查所有差异；Agent 则在这个工程空间中读取、分析、提案、修改、review 与回溯。

### 5.1 工程空间与目录约定

小说项目应被组织成一个明确的工程空间，而不是零散文档的集合。至少需要约定根目录下的核心结构，例如：设定目录、角色目录、大纲目录、章节目录、素材目录、review 与问题清单目录、版本说明目录、skills 与 workflow 配置目录等。

目录划分的目的，不只是为了整理文件，更是为了让 Agent 能稳定识别不同对象所在的位置，并据此完成上下文装配、对象引用、版本比较与任务分发。哪些目录属于正式对象区，哪些目录属于临时工作区，哪些目录用于归档或废案保存，也应提前约定清楚。

### 5.2 文档格式与对象映射约定

所有正式成果物（不含外部收集来的原始资料）应尽量采用可读、可编辑、可版本化的格式。文本类对象以 Markdown 为主，必要时可附加结构约定；图片类对象用于地图、人物肖像、关系示意等；其他外部素材则作为参考资料保留。

更关键的是，要约定“对象如何映射到文档”。例如：角色对象是否一人一文档，章纲与章节是否一章一文档，设定集是总文档还是分主题拆分，review 结果、问题单、版本说明分别以什么格式存放。只有对象与文档的映射关系清楚，后续的读写、引用、review、diff 与自动化处理才会稳定。

### 5.3 版本、tag 与变更记录约定

整个小说工程需要按照类似 git 的方式管理版本与分支，并让版本语义与第 4 节的版本推进条件保持一致。也就是说，0.x、1.0、1.x、2.x、3.x 等版本号，不只是命名方式，还应在工程中有明确含义。

除了版本号之外，还需要约定 tag 与变更记录机制。例如：draft-complete、rewrite-pass、final-candidate 等 tag 如何命名、何时打标；每次大修、精修、回退、重要设定修改后，是否自动生成一份变更说明；review 结果与问题清单如何挂接到对应版本。这样，Agent 后续在 prompt 中引用版本语义时，才能直接落到工程对象上，而不是停留在抽象描述层。

### 5.4 Agent 基础能力要求

在技术实现上，AI 小说创作伙伴至少需要具备一组稳定的基础能力。这些能力不依赖某一个具体 workflow，而是作为通用内核长期存在。

至少包括：读取工程空间内对象的能力；按对象和任务装配上下文的能力；对 Markdown 等文档进行局部修改、范围替换与差异展示的能力；对不同版本做比较、回溯和变更摘要的能力；执行 review、问题扫描与一致性检查的能力；依据工程状态与用户问题，在构思模式和写稿模式之间切换的能力。

### 5.5 Skills 与 Workflow 挂接要求

系统需要有默认工作流，但也必须允许通过 skills 覆盖或补充默认行为。因此，在实现前，需要明确 skills 与 workflow 是如何挂接到项目工程中的。

至少要回答几个问题：skills 放在什么位置、如何声明自己的适用范围、可以覆盖哪些默认步骤、是项目级生效还是任务级生效；当多个 skills 同时生效时，冲突如何处理；标准流程 Agent 与动态组装 Agent，分别如何读取这些配置。只有这部分先约定清楚，后续“让用户通过 skills 定义自己的流程或操作方式”才不会变成无边界的 prompt 堆叠。

### 5.6 审批、可见性与人工接管要求

由于 Agent 可以参与任何环节，但任何正式变更都需要获得写作者同意，因此实现前必须明确审批与可见性要求。

至少应保证：Agent 的正式修改以提案、差异或候选结果的形式可见；写作者可以批准、拒绝或局部采纳；高风险操作能够显示依据对象、影响范围与修改理由；在 Agent 判断错误、上下文异常或作者想中断自动流程时，写作者可以随时接管并改为手动决策。

这部分要求，本质上是把“作者主导、Agent 协作”落实到工程交互层，确保系统始终像一个高参与度的创作伙伴，而不是一个不可见、不可控的黑箱。

## 6\. Agent架构与运行机制

在第 4 节与第 5 节给出需求约束与工程前置条件后，第 6 节进一步规定：AI 小说创作伙伴的 Agent 架构应如何分层，任务发生时应按什么机制运行，以及哪些判断必须先于实际执行发生。

本节采用规范性写法。凡未被明确授权为可变项的内容，均应视为默认机制；凡需要按项目、任务或作者偏好调整的内容，均应通过 prompt、skills、workflow 或工程状态信号装配，而不应写死在单体 Agent 中。

### 6.1 总体架构：主控 Agent + 通用能力层 + 可组装子 Agent

系统应采用“主控 Agent + 通用能力层 + 可组装子 Agent”的架构，不应预设一个覆盖全部场景的单体 Agent。

其中：

*   主控 Agent 负责任务理解、状态判断、模式选择、上下文装配决策、能力调用决策、结果收束与对外交付；
    
*   通用能力层负责提供跨任务复用的基础能力，包括工程空间读写、对象识别、上下文装配、版本比较、差异摘要、review、问题扫描、一致性检查与审批提案输出；
    
*   子 Agent 负责承接被明确分发的局部任务，其形态可以是固定能力 Agent，也可以是按当前条件动态组装的临时 Agent。
    

架构设计应遵守两条原则：高复用、低分歧的能力进入通用能力层；高场景性、强任务性的能力留给可组装子 Agent。

### 6.2 主控 Agent 的职责边界

主控 Agent 的核心职责是判断、调度与收束，而不是默认亲自完成全部内容生产。主控 Agent 至少应承担以下职责：

*   识别当前任务类型，包括构思、写稿、审校、重构、版本处理等；
    
*   判断当前工程处于 0.x、1.0、1.x、2.x、3.x 中的哪一类版本语义；
    
*   结合任务意图、工程状态、相关对象与默认 workflow，确定执行模式；
    
*   在信息不足时发起最小化澄清；
    
*   决定当前任务由主控 Agent 直做、调用固定子 Agent，还是动态组装临时子 Agent；
    
*   汇总结果，并按要求输出正文、方案、差异、说明、review 结论或待确认事项。
    

主控 Agent 不应无条件下沉到所有细节执行；但凡存在模式切换、上下文取舍、风险评估、步骤编排或结果归并问题，均应先由主控 Agent 做判断。

### 6.3 执行模式判定机制

系统在执行前，应先完成模式判定。默认至少区分两种顶层模式：构思模式与写稿模式；必要时可在其下细分审校、重构、版本处理等子模式。

模式判定至少应综合以下信号：

*   工程状态信号：当前版本区间、当前工作对象类别、是否已有正式正文；
    
*   任务意图信号：用户是在要求发散、补设定、调大纲，还是要求续写、改写、重构、精修、review；
    
*   风险信号：当前操作是候选方案生成、局部试写，还是高影响面的正式改稿；
    
*   workflow 信号：当前流程是否要求在执行前后插入 review、版本比对或一致性检查。
    

若信号明确，系统应直接进入对应模式；若信号冲突、不足或会影响后续高风险操作，系统应先发起最小化澄清。澄清的目标应是补齐判定信息，而不是把内部模式概念转嫁给用户学习。

### 6.4 上下文装配与任务编排

模式判定完成后，系统应先装配上下文，再组织任务，不应在未完成对象定位前直接生成内容。

构思模式下，任务编排应优先支持“发散—比较—收敛”链路，默认读取主题、题材、设定草案、角色草案、大纲草案、候选方案与相关素材，并允许并行生成多个候选方向后再统一收束。

写稿模式下，任务编排应优先支持“定位—引用—执行—校验”链路，默认读取当前章节、对应章纲、相关人物资料、已确认设定、相邻章节与当前有效版本，并在执行后补做一致性检查、差异说明或 review。

因此，任务编排规则不应抽象成单一流水线；它必须随模式、对象与风险级别切换，但切换依据应可解释、可回溯。

### 6.5 Skills 与 Workflow 的加载顺序

系统必须支持默认 workflow 与 skills 叠加运行，但二者的生效顺序应固定，不应在运行时临时猜测。

默认加载顺序应为：先识别任务类型与工程状态；再读取项目级默认 workflow；再读取项目级 skills、作者级偏好与任务级即时要求；最后确定固定子 Agent 调用或临时 Agent 组装方案。

skills 不应仅被视为“附加 prompt”。每个 skill 至少应能声明以下信息：适用任务范围、插入步骤位置、可覆盖的默认行为、附加检查要求、输出结构要求。

workflow 则应负责声明步骤顺序、门禁条件、审批节点、回退路径与阶段完成条件。二者关系应表现为“workflow 提供骨架，skills 提供可插拔能力”，而不是无序堆叠。

### 6.6 执行、Review 与审批闭环

系统运行必须形成“执行—检查—提案—审批—落地—回溯”的最小闭环，不应停留在一次性生成结果。

标准闭环至少包括以下步骤：主控 Agent 完成模式判定与任务编排；子 Agent 或主控 Agent 完成局部执行；系统生成正文、方案或修改提案；系统补做必要的 review、差异说明与风险提示；写作者对结果进行批准、拒绝或局部采纳；批准后正式写入工程空间，并挂接版本与变更说明。

若在闭环中发现上下文异常、影响范围过大、设定冲突、版本依据不稳或用户意图不明确，系统应在审批前暴露问题并暂停落地，不应先写入再补救。

### 6.7 面向未来的可扩展原则

系统扩展应遵守“骨架稳定、能力组装、角色可增减”的原则。

应被固定的，是少量高复用、边界清楚、跨项目稳定存在的基础 Agent 与通用能力，例如检索、探索、review、版本比较、上下文装配等。

不应过早写死的，是明显依赖题材、阶段、作者习惯、项目流程或风险级别的任务型 Agent，例如构思辅助 Agent、大修 Agent、题材专项审校 Agent、设定冲突排查 Agent。

因此，新增能力的首选路径不应是继续膨胀主控 Agent，而应优先判断：该能力是否可以通过新增 skill、扩展 workflow、增加固定工具 Agent、或按条件动态组装临时 Agent 来实现。只有当某项能力跨项目高频复用且职责边界稳定时，才应上收为通用能力或固定 Agent。

## 7\. Prompt / Skills / Workflow 设计原则

第 6 节回答的是“架构怎么跑”；第 7 节进一步回答“架构靠什么被装配”。如果不把 prompt、skills 与 workflow 的职责边界说清楚，所谓“灵活组装 Agent”最终只会退化成大量 prompt 堆叠。因此，这三者必须被视为三种不同层级的控制面，而不是同义替换词。

### 7.1 三者的职责分层

Prompt 负责定义当前这一次任务要做什么、面向谁、输出什么、语气如何、当前禁止什么；它解决的是即时任务约束问题。

Skills 负责封装可复用的能力片段与局部规则，例如某类审校方法、某类题材检查器、某类 research 流程、某种输出模板；它解决的是能力复用问题。

Workflow 负责规定步骤顺序、进入条件、退出条件、审批节点、异常分支与阶段成果物；它解决的是流程编排问题。

三者不得互相越位：prompt 不应承担完整流程定义，skill 不应私自改写全局阶段推进规则，workflow 不应承载大量只适用于单次任务的措辞细节。

### 7.2 Prompt 的设计原则

Prompt 应尽量短而准，只承载当前任务不可缺少的即时约束。一个合格的任务 prompt 至少应回答六个问题：当前任务对象是什么、目标动作是什么、可使用哪些上下文、输出形式是什么、风险边界是什么、完成后需要交付给谁。

Prompt 不应重复写入已经由工程状态、对象文档、skill 声明或 workflow 规则稳定提供的信息。凡是跨任务稳定存在的规则，都不应长期滞留在 prompt 中，而应上移到 skill、workflow 或工程配置层。

Prompt 的主要作用不是“尽量多写”，而是为主控 Agent 提供一次性决策入口，并为动态 Agent 组装提供当前任务的最小充分约束。

### 7.3 Skills 的设计原则

Skill 应被视为可插拔的能力包，而不是一段更长的 prompt。每个 skill 至少应声明：名称、适用任务范围、前置条件、需要读取的对象类型、会增加或替换的步骤、输出约束、与其他 skill 的冲突关系。

Skill 的理想粒度应是“能独立复用，但不过度膨胀”。过小会导致运行时装配碎片化，过大则会把多个本应独立组合的能力绑死在一起。

Skill 适合承载以下内容：专项审校规则、题材知识使用规则、固定分析框架、结构化输出模板、额外检查器、特定工具调用策略。Skill 不适合承载整个项目的总流程，也不适合携带大量与具体工程对象强绑定的临时说明。

### 7.4 Workflow 的设计原则

Workflow 应被视为任务执行骨架。它至少应声明：步骤列表、每一步的输入输出、步骤间依赖关系、进入条件、跳过条件、审批点、失败回退路径，以及何时允许写入正式对象。

Workflow 应优先表达“什么时候必须停、什么时候必须问、什么时候必须 review、什么时候可以直接落地”这类流程性约束，而不是沉积大量文案风格说明。

一个项目可以有默认 workflow，也可以按阶段、对象类型或任务类型派生出子 workflow；但派生关系应可追踪，覆盖范围应明确，不能让多个 workflow 在同一层级无序争用控制权。

### 7.5 Agent 组装的输入信号

所谓“灵活组装 Agent”，不是先定义一长串角色再去硬匹配，而是根据输入信号决定这次需要什么能力组合。至少应纳入以下组装信号：

*   当前任务 prompt：决定即时目标、输出格式与禁区；
    
*   当前工程状态：决定阶段语义、可用对象与风险级别；
    
*   当前 workflow：决定步骤骨架、审批位置与是否允许并行；
    
*   当前 skills：决定是否插入专项能力、附加检查或替代默认行为；
    
*   当前对象集合：决定需要读取哪些设定、章纲、章节、版本或问题单；
    
*   当前作者偏好：决定风格、可见性、澄清策略与默认交付形式。
    

主控 Agent 应先读信号，再决定组装结果；不应反过来先挑一个预设角色，再逼迫任务去适配角色。

### 7.6 Agent 组装决策顺序

一个可执行的组装顺序应为：先判定任务模式，再判定流程骨架，再加载可用 skills，再装配当前上下文，最后决定是由主控 Agent 直做、调用固定 Agent，还是生成临时 Agent。

当任务边界清楚、上下文短、风险低且不需要专项能力时，主控 Agent 可以直接执行，不必为了“看起来是多 Agent”而强行拆分。

当任务需要稳定工具能力且职责长期不变时，应调用固定 Agent，例如检索 Agent、探索 Agent、review Agent、diff Agent。

当任务依赖特定 prompt、特定 skill 组合、特定对象范围或特定阶段规则时，应优先动态组装临时 Agent。临时 Agent 的身份不是预先命名的重点，关键是其输入约束、能力边界与交付责任是否被明确定义。

### 7.7 固定 Agent 与动态 Agent 的划分原则

是否将某类能力固化为固定 Agent，可用四条标准判断：是否跨项目高频出现、是否工具链稳定、是否输入输出边界清楚、是否值得被独立监控与复用。

满足以上条件的能力，适合沉淀为固定 Agent；不满足的，则更适合在运行时按条件临时组装。换言之，固定 Agent 是“稳定能力单元”，动态 Agent 是“稳定装配机制下的临时执行体”。

这意味着系统真正需要稳定下来的，不是几十个角色名，而是“什么情况下固化、什么情况下临时装配”的判定规则。

### 7.8 组合冲突、退化与回退原则

当多个 skills、多个 workflow 覆盖项或多个约束源发生冲突时，系统必须有显式优先级。一个默认优先级应为：安全与审批约束 > 当前正式 workflow > 当前任务 prompt 中的明确限制 > 已启用 skills > 作者偏好 > 通用默认值。

当动态组装失败、上下文不足、技能冲突无法解消或子 Agent 成本明显高于收益时，系统应允许退化执行：回退为主控 Agent 直做、缩减为单 skill 模式、或先做最小澄清后再重新装配。

灵活组装的目标不是每次都组得更复杂，而是在不破坏可控性和可解释性的前提下，只组装当前任务真正需要的那部分能力。

## 8\. MVP 范围定义

本节只定义首版边界，不展开实现细节。

### 8.1 MVP 的目标

第一版 AI 小说创作伙伴的目标，不是实现从选题到完稿的全自动自主创作，而是形成一个作者主导、Agent 协作、可见、可审、可回退的小说创作工程助手。

首版重点只有两项：一是让 Agent 基于工程上下文参与构思、写稿、修改与 review；二是让这种参与始终处于可解释、可控制、可审批的协作框架内。

### 8.2 MVP 必须支持的能力范围

MVP 至少应支持以下能力：读取并引用小说工程中的核心对象；在构思模式与写稿模式之间做基本切换；围绕设定、大纲、章节等对象提供协作；支持局部写作、改写、润色与 review；支持以提案、差异或候选结果的形式交付正式修改；支持基础版本比较、回退与变更说明；支持默认 workflow 与基础 skills 的挂接；支持主控 Agent、少量固定能力 Agent 与按条件动态组装能力的基本协同。

### 8.3 MVP 明确不包含的内容

MVP 不包含以下目标：从热点采集、选题判断到整部小说完稿的全自动闭环；复杂多人协作与细颗粒度角色权限体系；高度复杂的可视化流程编排器；跨项目通用的长期记忆学习系统；大量高度自治、彼此长期协商的复杂多 Agent 网络。

因此，首版边界应明确落在“把作者与 Agent 的核心协作闭环做扎实”上，而不追求最大化自动化、自治化或系统复杂度。

### 8.4 MVP 的完成标志

MVP 完成至少应满足以下标志：作者可以在一个小说工程中稳定完成从构思到正文修改的基础协作；Agent 的工作依据来自工程上下文而不只是单次 prompt；高风险修改不会无痕直接落地；正式结果可见、可批、可拒绝、可回退；系统具备向更复杂 skills、workflow 与多 Agent 协作扩展的稳定骨架。

## 9\. 核心用户场景与用例清单

本节只定义首版必须覆盖的关键场景，不展开实现级用例细化。

### 9.1 构思类场景

MVP 至少应覆盖以下构思类场景：围绕一个主题生成多个创意方向；在已有方向上继续展开世界观、角色与主线设定；基于已有设定识别缺口、冲突与待确认项；对多个方案做比较与收敛；在构思阶段保留候选方案而不误当正式结论。

### 9.2 写稿类场景

MVP 至少应覆盖以下写稿类场景：基于当前章纲与已确认设定续写章节；对既有正文做局部改写、补写或重写；在不改变核心剧情前提下进行润色与表达优化；根据问题单或 review 结果修正正文；对本次写作或修改所依据的上下文对象给出说明。

### 9.3 审校与修订类场景

MVP 至少应覆盖以下审校与修订类场景：对章节执行设定一致性检查；对人物动机、关系、时间线与情节衔接进行问题扫描；对一轮改稿结果生成 review 结论；对修改前后结果生成差异说明；在发现高风险问题时暂停直接落地并要求作者确认。

### 9.4 工程与协作类场景

MVP 至少应覆盖以下工程与协作类场景：基于当前任务自动装配必要上下文；在默认 workflow 下完成一次标准任务闭环；在启用特定 skill 时调整任务执行方式；将正式修改以提案方式交由作者审批；在需要时回退到上一稳定版本或保留原结果供比较。

### 9.5 本文档与后续正式需求的边界

本节场景与用例清单的作用，是为后续正式需求与设计提供覆盖边界，而不是在当前文档中展开字段级、接口级、状态机级的实现定义。

因此，本文档只回答三类问题：首版必须覆盖哪些场景、必须坚持哪些原则、哪些能力属于首版边界；更细的对象结构、交互流程、异常处理与实现细节，应留待正式需求文档与系统设计文档展开。

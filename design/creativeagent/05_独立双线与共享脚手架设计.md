# CreativeAgent / EditAgent：独立双线与共享脚手架设计

## 1. 设计结论

从当前阶段开始，`CreativeAgent` 与 `EditAgent` 不再尝试做能力耦合，而是按 **两条独立演进线** 处理：

- `CreativeAgent`：面向小说创作资产、创作任务编排、审查与演进
- `EditAgent`：面向现有文档的受控读取、局部修改与 proposal apply

两者 **共用 Agent 脚手架**，但 **不共用领域语义**。

一句话概括：

> 共享运行时，不共享职责。

---

## 2. 为什么现在要拆开

当前工程里的 `EditAgent` 本质上是一个 **文档修改代理**，不是未来 `CreativeAgent` 体系中的 `writeAgent`。

它的优势在于：

- 围绕当前文档做 block-aware 读取与修改
- 通过 proposal / approval / apply 控制高风险改动
- 对局部文稿修订有较强的精确执行能力

它的天然边界也很明确：

- 不以内建方式理解 StoryBible / Outline / SceneCard / CharacterArc
- 不天然以作品级一致性为主目标
- 更适合作为“文档落地执行器”，而不是“创作域写作器”

因此，未来 `CreativeAgent` 中即使存在 `writeAgent`，也不应直接等同于当前 `EditAgent`。

---

## 3. 核心原则

### 3.1 共用的是脚手架，不是能力定义

可以共用：

- `AgentEngine`
- thread / checkpointer / streaming / resume
- provider / model / think mode
- tools / skills 的注册与装配方式
- agent event / task plan / tool call 的基础 UI
- 中断恢复的基础协议
- HITL 的 approve / edit / reject 决策数组协议

不能共用：

- system prompt
- workflow / orchestrator
- state model
- asset model
- tool protocol
- approval model
- version model
- context builder
- EditProposal / BlockEditProposal 等 block-level 审批数据结构

### 3.2 Creative 与 Edit 是两个 domain，不是主从子集

`CreativeAgent` 和 `EditAgent` 都运行在同一套 runtime 之上，但它们是两个不同 domain：

- `Edit` domain 以文档为中心
- `Creative` domain 以创作资产与任务状态为中心

当前阶段不处理两者的相互调用关系，不设计 handoff 主链路，不要求能力打通。

### 3.3 先拆干净，再考虑协作

先保证：

1. 两个 domain 的边界清晰
2. Creative 新能力不继续挤进 Edit 类型和流程
3. Creative 可以独立引入自己的 orchestrator / workflow / assets / proposal

之后再考虑 cross-domain handoff。

---

## 4. 领域职责

### 4.1 EditAgent

定位：

> 文档受控修改代理

职责：

- 读取当前文档或指定文件
- 基于 block / range 形成修改 proposal
- 在用户审批后执行局部文稿修改
- 保持修改过程可追溯、可恢复、可回滚

不负责：

- 世界观设定
- 人设与人物弧线设计
- 作品级提纲规划
- 创作资产管理
- 自动演进

### 4.2 CreativeAgent

定位：

> 创作资产与创作任务代理

职责：

- 灵感孵化
- 世界观、人物、故事线、scene card 等资产构建
- 创作任务编排与多阶段推进
- 创作审查、方案比较、演进记录
- 后续扩展出的 creative write / review / version / branch 能力

不负责：

- 直接承担现有 block edit proposal 执行逻辑
- 直接复用 Edit 的文档修改工具语义

---

## 5. 工程拆分原则

建议把 AI 代码逻辑拆为两层：

```text
Shared Agent Runtime
  - AgentEngine
  - IPC / Stream / Checkpoint / Resume
  - Thread runtime
  - Tool / Skill bootstrap
  - Common UI shell

Edit Domain
  - Edit workflows
  - Document tools
  - Block proposal model
  - Editor snapshot / context
  - Edit prompt

Creative Domain
  - Creative workflows
  - Creative asset tools
  - Creative task state
  - Story asset / context model
  - Creative prompt
```

当前阶段的工程目标不是“大迁移”，而是：

1. 先把 shared/domain 的边界显式化
2. 为 Creative 新能力预留自然目录与装配入口
3. 不破坏现有 Edit 功能链路

---

## 6. 当前实施策略

### 6.1 第一阶段目标

先完成“骨架拆分”：

- 抽出 shared 的 capability 类型
- 抽出 edit domain capability builder
- 抽出 creative domain capability builder
- `AgentEngine` 只负责按 domain 选择 builder，不再内联领域装配细节

这一步必须保持 **行为不变**。

**当前状态：已完成**。参见：

- `electron/ai/domain/types.ts`（DomainAgentCapabilities 接口）
- `electron/ai/domain/edit/buildEditCapabilities.ts`
- `electron/ai/domain/creative/buildCreativeCapabilities.ts`
- `electron/ai/AgentEngine._buildAgentCapabilities`（按 domain 分发）
- `src/ai/thread/system-prompts/{edit,creative,minimal}.ts`
- `src/components/ai/agent-panel/domains/{DomainMessageSession,edit/*,creative/*}`

### 6.2 第二阶段目标（即 v3 文档中的 Phase 1，详见 `Phase 1.md`）

在 creative domain 内独立演进：

- **存储升级**：用 SQLite 替换当前的 flat markdown file 存储（现有 `electron/ai/tools/CreativeArtifactTools.ts` 的 3 个工具会被新设计的 tools 替换）。Phase 1 仅建 `session_log` 表；`proposal` / `review_finding` 推迟，理由见 `03_概要设计 §7`。
- **移除 LocalShellBackend**：换成 `FilesystemBackend({ rootDir: workspacePath, virtualMode: true })`，与 Edit domain 完全一致——不给 agent 自由 shell 访问。
- **资产对象**：按 v3 重构后采用 `storybible.md` + `draft/` 两个文件级别的资产，不引入 Project / CreativeBrief / StoryBible / OutlineTree 这种结构化对象（v1/v2 的设计已废弃，参见 01-04 文档）。
- **Tools**：creative 专属 read / mutation / search tools，通过 `interruptOn` 实现 HITL，无独立 proposal tools。
- **Pilot Mode 开关**：Phase 1 不实施；正常模式下 L2/L3 tools 一律走 HITL。
- **Project = Workspace 绑定**：无 workspace 时禁用 creative。**两层防御**：
  1. UI 层 `ProfilePicker.vue` 在 `appStore.currentFolder` 为空时禁用 creative 选项 + tooltip
  2. Tool 层每个 creative tool 在 runtime configurable 中校验 `workspace_path`，无值则返回明确错误

后续阶段（Draft / Review / Proposal 闭环 / 版本系统 / 自动演进）按 Phase 2-6 推进。

### 6.3 Edit Domain 的复用边界（落实 §3.1 的细化）

复用关系经代码勘察后确认如下：

**直接复用（API 层 + 实现层）：**
- `interruptOn` HITL 协议（`DomainAgentCapabilities.interruptOn` 接口完全共用）
- `AgentEngine` 的 streaming / interrupt / resume 整套链路
- `RendererEventBridge` / `StreamEventAdapter` / IPC protocol
- `BlockEditReviewSurface` / `EditReviewSurface` 的设计模式（CreativeReviewSurface 参考交互，不复用 EditProposal 数据结构）
- `FilesystemBackend`（替换 `LocalShellBackend`）
- `inferToolKind` 中的 read/edit/search 分类（添加新工具名映射）

**实现层复用（不暴露给 agent）：**
- `electron/ai/document/DocumentSearch.ts` 的 `searchInDirectory` —— 在 creative 的 `search_draft` 工具内部直接调用，不复制全文搜索逻辑

**不复用：**
- `EditProposalTools` —— block-level 抽象，不适用 file-level creative 操作
- `EditProposal` / `BlockEditProposal` —— creative 的审批对象是 `creative_plan` / `creative_write` / `creative_storybible` 等 file-level / plan-level payload
- `DocumentTools`（get_blocks / get_section 等）—— 抽象层是 TipTap block，creative agent 不应感知
- `SnapshotBroker` / `BlockParser` / `BlockEditApplier` —— TipTap 相关，creative 不依赖
- `CreativeArtifactTools.ts`（旧实现，Phase 1 完全替换）

### 6.4 暂不处理的问题

### 6.4 暂不处理的问题

以下内容在当前阶段明确不做：

- Creative -> Edit handoff
- Edit 读取 Creative 资产作为硬依赖
- 统一 proposal 数据结构
- 统一 context builder
- 统一 version system

这些都留待 Creative domain 自身稳定后再设计。

---

## 7. 后续约束

从本设计生效起，新增 Creative 能力时遵循以下约束：

1. 不向 EditAgent 继续灌入 Creative 语义
2. 不把 Creative 新能力实现成 Edit 工具的变体
3. 不要求 Creative 设计与 Edit proposal 模型兼容
4. 尽量复用 shared runtime，而不是复制一套新的 agent 基础设施

---

## 8. 最终结论

当前阶段最合适的方向是：

> `CreativeAgent` 与 `EditAgent` 独立演进，复用同一套 Agent 脚手架。

这会让后续的 Creative 设计可以真正围绕：

- 资产
- 任务
- 编排
- 审查
- 演进

来展开，而不是被现有 Edit 的文档修改心智模型牵着走。

---

## 9. 当前阶段的关键技术决策

下列决策对 Creative domain 的实施具有跨切关系，统一记录：

### 9.1 存储：SQLite

- 工程是 Electron 桌面应用，Postgres 不可行
- 复用已有的 better-sqlite3（checkpointer 已使用）
- DB 路径：`{workspace}/.iwriter/creative.db`
- 详见 `03_概要设计 §9.2`、`04_详细设计 §十三`

### 9.2 Pilot Mode

- 正常模式：L2/L3 mutation tools 经 HITL 审批
- Pilot 模式：L1/L2 自动 apply；L3 强制 HITL（不可被 Pilot 覆盖）
- 通过 `interruptOn` 配置切换，`buildCreativeCapabilities` 接受 `pilotMode: boolean` 参数
- 详见 `04_详细设计 §十一`

### 9.3 无独立 Orchestrator（当前阶段）

- 当前阶段不独立实现 Task Orchestrator
- 流程边界由 deepagents + tool schema + interruptOn HITL 共同保证
- Phase 5+ 版本系统与 Phase 6 自动演进阶段再评估独立 Orchestrator
- 这是渐进式策略（路径 B），与 `03_概要设计 §6` 的「用代码编排流程」原则不冲突——schema 与 HITL 都是代码定义的边界

### 9.4 Project = Workspace

- 一个 workspace 文件夹对应一个 Creative Project
- 无 workspace 时 creative 域禁用
- 详见 `04_详细设计 §十二`

### 9.5 无 LocalShellBackend

- Creative domain 与 Edit domain 在 backend 行为上一致
- 不给 agent 自由文件系统访问
- 所有资产读写通过明确的 StructuredTool
- 这是 `03_概要设计 §15` 第 3 条硬约束「所有资产操作必须经过 tools」在工程层的具体落实

### 9.6 Plan-first 用 interruptOn，不用对话式等待

- Plan-first 通过 `confirm_writing_plan` 工具实现，工具不写文件，仅触发 interruptOn 暂停
- 不采用"agent 输出 plan 文本，等用户回复'继续'"的对话式做法——后者无法保证 agent 真的等待，UI 上也无法区分"等待审批"和"普通对话"
- approve / edit / reject 三种决策由 `CreativeReviewSurface.vue` 提供入口（参考 `EditReviewSurface.vue` 的形态）

### 9.7 storybible.md 与 draft/ 的初始化

- 工具内懒初始化：`read_storybible` / `read_fragments` 在文件不存在时写入最小模板
- 不引入显式的"项目初始化"流程
- system prompt 指引 agent 在每次会话第一个 turn 调用 `get_session_diff` + `read_storybible`，自然完成首次创建

### 9.8 session_log 写入时机

- 每次 streaming run **成功结束**时写入（`AgentEngine._streamLoop` 在 `sendRunDone` 之前）
- run 失败 / 中断 / interrupted 不写，保留上次记录
- 写入内容仅扫描 `storybible.md` + `draft/**/*.md` 的 hash，不扫描整个 workspace
- 保守策略：最多漏检一次 diff，但不会因为崩溃留下错误的"上次状态"基线

### 9.9 旧 builtin skills 的废弃

- 现有 4 个 skills（`character-forge` / `novel-brainstorm` / `storyline-architect` / `worldbook-planner`）按 v1 sections-based design 编写，与 v3 的 storybible/draft 模型不匹配
- Phase 1 全部替换为 3 个新 skills：`scene_structure` / `character_voice` / `deep_pov`
- 后续 Phase 按 04 文档 §9 增补

# 小说创作智能体系统：概要设计（v3）

## 1. 设计目标

1. agent 是创作伙伴，不是执行工具——有 craft 知识，有创作直觉
2. 作者只看到文稿和对话，系统复杂性全部在 agent 内部消化
3. 存储尽可能简单：文件 + git，最小化 SQLite
4. 上下文策略随规模分阶段演进，始终保持"刚好够用"
5. 不自研任何可以用 git 替代的版本控制机制

---

## 2. 总体架构

```
作者
  ↕ 编辑文稿（直接）
  ↕ 对话（触发 agent）

Agent
  → diff 感知（了解变化）
  → 读 StoryBible（理解当前状态）
  → 按需搜索 draft（找具体内容）
  → plan / 写作 / 检查 / 更新 StoryBible

存储层
  storybible.md        ← agent 维护，作者可读可改
  draft/ch*.md         ← 正文，作者主要编辑区
  .git/                ← 版本控制
  .iwriter/creative.db ← 仅存操作状态（proposal / review_finding）
```

---

## 3. 文件结构

```
{workspace}/
  storybible.md          ← agent 维护的项目理解摘要
  draft/
    fragments.md         ← 场景种子、碎片、散乱想法
    ch01-{title}.md      ← 章节文件，作者主要编辑对象
    ch02-{title}.md
    ...
  .git/
  .iwriter/
    creative.db          ← 仅：proposal、review_finding、session_log
```

**原则：**
- `storybible.md` 和 `draft/` 在工作区根目录，作者在文件树里直接看到
- `.iwriter/creative.db` 只存操作性状态数据，不存任何叙述性内容
- 不用 YAML frontmatter 管理元数据，不建立文件→DB 的同步机制

## 4. StoryBible

StoryBible 是 agent 对项目当前状态的理解摘要，是 agent 每次工作的主要上下文输入。

### 4.1 文件格式

普通 Markdown，无 frontmatter，无强制格式。Agent 以 prose + 简单 heading 维护，保持可读性。

```markdown
# StoryBible — {项目名}
_最后更新：{timestamp}_

## 角色

### A（主角）
当前状态：xxx。核心特质：xxx。正经历：xxx。
声音特征：语气简洁，少用形容词，倾向反问。
与 B 的关系：xxx。

### B
...

## 世界观
已确立规则：xxx。
时间线关键事件：xxx。
禁区（绝对不能出现的设定）：xxx。

## 故事当前状态
写到：第二章末，A 刚发现 B 的秘密。
开放伏笔：xxx（第一章埋下）。
未解决冲突：xxx。

## 写作约束
视角：第三人称有限，紧贴 A 的视角。时态：过去时。
基调：压抑但有内在张力，避免煽情。

## 待解决
- B 的动机尚未确定，作者需要决策
- 第三章结构有两个选项，待探索
```

### 4.2 大小控制

目标 2000-4000 token，确保每次能完整读取。超出时：
- 压缩已完成章节的内容（保留关键事件，删除细节）
- 将次要角色合并为简短描述
- 不删除"待解决"和"写作约束"部分

### 4.3 更新策略

| 触发条件 | 更新方式 |
|---|---|
| 对话中确认新设定 | 立即 patch 对应段落 |
| 写完一段内容 | 增量检查，有变化则更新 |
| 累积变化超过约 2000 字 | 触发全面重读 + 重建 |
| 作者标记 git tag（阶段里程碑）| 触发重建 |
| 结构性变化（改核心设定、删章节）| 立即重建相关部分 |

重建不是重写全部，而是重读变化的部分，更新对应条目，全量检查一致性。

## 5. 上下文策略（分阶段）

| 阶段 | 规模 | 策略 |
|---|---|---|
| 早期 | < 2万字 | 全读：StoryBible + 所有 draft 文件 |
| 生长期 | 2-5万字 | 全读 StoryBible + 关键字搜索 draft |
| 稳定期 | > 5万字 | 全读 StoryBible + 语义/关键字搜索 draft |

**早期全读**：规模小，全放进上下文，agent 掌握完整画面，建立初始 StoryBible。

**生长期/稳定期**：StoryBible 是主上下文锚，压缩了项目全貌。Draft 通过搜索按需补充细节。

**搜索约束**：每次写作任务最多 3 次搜索调用，每次返回 top-3 结果（摘要而非全文），避免上下文膨胀。

## 6. Agent 行为模式

### 6.1 会话启动（每次对话开始时）

```
1. 获取 session_diff：文稿自上次会话后的变化摘要
2. 读取完整 StoryBible
3. 必要时对 StoryBible 做增量 patch
4. 理解当前状态，准备参与
```

### 6.2 写作任务执行

```
作者给方向
  → agent 读相关上下文（StoryBible + 按需搜索）
  → plan（说明打算怎么做、有哪些选择）
  → 作者确认或调整
  → 执行写作
  → 一致性检查（后台）
  → 发现问题则提出
  → patch StoryBible（若有新信息）
```

### 6.3 plan 的最小格式

```
我打算这样写：[具体说明]
考量：[为什么，权衡了什么]
备选：[如果有其他方向]
继续吗？
```

短小改动（段落润色、对话调整）可跳过 plan，直接执行。

### 6.4 一致性检查维度

每次写完后后台运行，发现问题按严重程度决定是否提出：

- **高**（必须提出）：视角越界、时间线矛盾、世界规则冲突
- **中**（建议提出）：人物行为与已确立设定不符、伏笔未有回收计划
- **低**（可选提出）：节奏问题、风格偏移、对话声音偏离

## 7. SQLite 设计（最小化）

只存三类操作性数据，**按 Phase 引入**：

```sql
-- Phase 1 引入：会话记录，用于 diff 感知
session_log (
  id, workspace_path, ended_at,
  file_hashes  -- JSON: {relative_path: sha256}
)

-- Phase 2 引入：agent 发现的一致性问题（ConsistencyAgent 落地时）
review_finding (
  id, layer, type,
  location_ref,  -- e.g. "ch02.md:paragraph_hash"
  description, suggestion, severity,
  status,  -- open | resolved | dismissed
  created_at
)

-- Phase 3 引入：跨会话持久化的修改提案（当前 plan-first 用 in-memory interruptOn 即可）
proposal (
  id, target_ref, operation,
  before_snapshot, after_content,
  rationale, risk_level,
  status,  -- pending | approved | rejected | applied
  created_at
)
```

**Phase 1 仅建 `session_log` 一张表**。理由：
- plan-first 的审批通过 deepagents `interruptOn` 在内存中完成，approval 状态不需要跨会话持久化
- ConsistencyAgent 在 Phase 2 才落地，`review_finding` 此时无消费方
- 提早建表会引入未使用的 schema，迁移负担大于收益

**`session_log` 写入时机**：每次 streaming run 成功结束时（在 `ai:run-done` 事件发出之前）写入当前 workspace 内 `storybible.md` + `draft/**/*.md` 的 hash 快照。Run 失败或中断不写，保留上次记录（保守策略，最多漏检一次 diff）。

**Phase 1 diff 口径**：`session_log.file_hashes` 只用于识别新增 / 修改 / 删除了哪些文件，不承诺行级 diff 或段落级 diff。Agent 需要理解变化内容时，根据变更文件清单重读相关文件并总结当前状态。真正的行级 diff、跨版本比较、方向探索分支对比，留到 git 集成或快照持久化阶段。

**DB 路径**：`{workspace}/.iwriter/creative.db`，与 LangGraph checkpointer 的 `{userData}/ai-checkpoint.db` 不冲突——前者 per-workspace（绑定项目），后者全局（跨项目的会话历史）。

不在 SQLite 中存储：角色数据、世界观数据、提纲节点、任何叙述性内容。这些全部在 `storybible.md`。

## 8. Tools 设计

Tools 是 agent 操作文稿和项目状态的唯一合法入口。所有写入文件的操作通过 `interruptOn` HITL 机制审批，不是单独的"提案系统"——审批 UI 与 Edit domain 共用 `DomainAgentCapabilities.interruptOn` 协议。

Creative domain 只复用中断 / 恢复协议，不复用 Edit domain 的 `EditProposal` / block proposal 数据模型。Creative 的审批对象是 file-level / plan-level payload，例如 `creative_plan`、`creative_write`、`creative_storybible`；UI 可借鉴 `EditReviewSurface` 的交互模式，但展示与编辑字段由 creative tools 的 actionRequest 决定。

### 8.0 路径与写入安全

Creative tools 必须把文件访问限制在 workspace 内的两个公开资产区域：

- `{workspace}/storybible.md`
- `{workspace}/draft/**/*.md`

规则：

- 所有 `filename` 都按相对 `draft/` 解析，禁止绝对路径、`..`、`~`、Windows drive prefix
- 解析后必须确认目标路径仍位于允许的根目录内
- `read_chapter` / `write_to_chapter` 只接受 Markdown 文件；缺省扩展名时可以自动补 `.md`
- `write_to_chapter` 的 `insert_at` / `replace_range` 必须带明确 anchor 或 range 参数，缺失则拒绝执行
- StoryBible 的小 patch 不能删除、清空或整段替换；整段替换必须走 `replace_storybible_section` 审批

### 8.1 读取类（L1，无 HITL）

```
read_storybible()
  → 返回完整 storybible.md 内容；不存在则懒创建最小模板

read_chapter(filename)
  → 返回 draft/{filename} 内容

read_fragments()
  → 返回 draft/fragments.md 内容；不存在则懒创建空文件

search_draft(query, limit=3)
  → 关键字搜索 draft/ 下所有 .md，返回摘要片段
  → 实现层复用 electron/ai/document/DocumentSearch 的 searchInDirectory

get_session_diff()
  → 对比当前 storybible.md + draft/**/*.md 的 hash 与 session_log 中上次记录
  → 返回新增 / 修改 / 删除文件清单，不返回行级 diff
```

### 8.2 写入类（按 HITL 分级）

| Tool | 风险 | HITL | 说明 |
|---|---|---|---|
| `add_fragment(content)` | L1 | 无 | 追加到 fragments.md，纯增量 |
| `patch_storybible(section, anchor, content)` | L1 | 无 | 小型 append/upsert patch，不删除、不清空、不替换整段；返回 patch 摘要 |
| `confirm_writing_plan(plan, rationale, alternatives?)` | L2 | approve / edit / reject | 不改文件，仅触发审批；tool result 返回 approved/edited plan |
| `write_to_chapter(filename, content, mode, approved_plan)` | L2 | approve / edit / reject | mode: append / insert_at / replace_range；必须携带批准后的 plan；approved 后由 tool function 直接写盘 |
| `replace_storybible_section(section, content)` | L2 | approve / reject | 整段替换某 section |
| `rebuild_storybible()` | L3 | approve / reject | 全量重读 draft/ 并重建；Pilot 模式不可绕过 |

### 8.3 版本类（Phase 4+ 引入）

包装 git 操作，Phase 1 不实施：

```
git_commit / git_tag / git_branch / git_diff
```

### 8.4 不再单独存在的"提案系统"

原 §8.3 中的 `create_proposal` / `list_proposals` / `apply_proposal` 不作为独立工具：
- "创建提案"= 调用 L2/L3 工具 → interruptOn 自动触发审批
- "列出待审批"= 由 review surface UI 直接读 in-memory 队列（来自 `actionRequests`，并转换成 creative review item）
- "应用提案"= 用户在 review surface 点击 approve → deepagents 自动 resume → tool function 执行

跨会话持久化的 proposal 表是 Phase 3 引入，用于"app 重启后继续审批"的场景。

## 9. Skills 体系

Skills 是 agent 调用的内部能力模块，不暴露给作者。

| Skill | 职责 |
|---|---|
| `scene_structure` | 分析/构建 目标→冲突→转折 结构 |
| `pov_craft` | 视角技法、越界检测 |
| `character_voice` | 角色声音一致性分析与写作 |
| `pacing_sense` | 节奏、张力、留白感知 |
| `dialogue_craft` | 对话真实性、角色辨识度 |
| `foreshadowing_tracker` | 伏笔种植与回收追踪 |
| `reverse_outline` | 从已有正文反向提炼结构 |
| `worldbuilding` | 世界规则一致性维护 |
| `genre_conventions` | 类型规范知识（推理/言情/奇幻/科幻等）|

每增加一个 skill，agent 在对应维度的建议质量提升一个层次。

## 10. 实施路径

实施形态：**单 LLM 实例**，将 04 文档中的 MainAgent / WriterAgent / StateAgent 三个角色合并到同一个 system prompt + 工具集中，不做 sub-agent 编排（与 §6.2 路径 B 一致）。

- [ ] 替换 `LocalShellBackend` 为 `FilesystemBackend(workspace)`，与 Edit domain 一致
- [ ] 建立文件结构：`storybible.md` + `draft/` 在工作区可见（工具内懒创建，不需要单独的初始化流程）
- [ ] 实现 §8.1 全部读取类工具
- [ ] 实现 §8.2 中的 `add_fragment` / `patch_storybible` / `confirm_writing_plan` / `write_to_chapter` / `replace_storybible_section` / `rebuild_storybible`
- [ ] 建立 `creative.db`：**仅 `session_log` 一张表**（proposal/review_finding 推迟到后续 Phase）
- [ ] Plan-first 通过 `confirm_writing_plan` 工具 + `interruptOn` 实现，不走"对话式等待"
- [ ] UI：复用现有 `ProfilePicker` 的 creative 选项；无 workspace 时禁用并加 tooltip

### Phase 2：一致性检查 + 上下文搜索

- [ ] 实现 `search_draft`（FTS 关键字搜索）

### Phase 3：Proposal 系统 + 完整 Skills

## 11. 关键约束

**硬约束（任何阶段不可违反）：**

1. Agent 只通过 tools 修改文件，不直接写文件系统
2. Creative domain 不使用 `LocalShellBackend`
3. `storybible.md` 是 agent 的输出，不是用户填写的表单
4. SQLite 不存叙述性内容，只存操作状态
5. 高风险操作（修改核心设定、删除章节）必须走 proposal-first

**架构原则：**

6. Markdown 文件是数据源，SQLite 是操作状态记录，方向不可逆
7. StoryBible 保持精简（目标 ≤ 4000 token），不随小说膨胀
8. Git 是版本系统，不自研
9. 作者看到的复杂度保持最低
